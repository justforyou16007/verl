0. 先把模型对齐：27B 有没有 Megatron 例子

先说一个需要澄清的事实，免得后面对不上号。仓库里 Qwen3.5-27B 只有 FSDP 脚本，没有 Megatron 脚本：

examples/grpo_trainer/run_qwen3_5_35b_megatron.sh     ← 35B，Megatron（MoE，带 EP/ETP）
examples/grpo_trainer/run_qwen3_5_122b_a10b_megatron.sh
examples/grpo_trainer/run_qwen3_5_397b_megatron.sh

而且 EP / ETP 这两个维度只对 MoE 模型有意义（没有 expert 就没有 expert parallel）。所以这一课的代码链路讲通用的，具体数字用 run_qwen3_5_35b_megatron.sh 里实测过的那组配置，它是同族的 MoE 模型，五个维度全都用上了：

1. 从那一行到 GPU 上的 Megatron：五层

你选中的那一行本身什么都没加载。它只是把「用哪个类、拿什么参数」记下来。真正把 Megatron 拉起来，要穿过五层：

trainer_base.py:508   RayClassWithInitArgs(cls=role_worker_mapping[actor_role], config=...)
                      └─ 只是配方，不执行
          ↓  trainer_base.py:552 起  RayWorkerGroup(...) 真正建 Ray actor
engine_workers.py:485 ActorRolloutRefWorker.__init__      ← 外层：一个进程里管 actor+rollout+ref
          ↓  init_model() 里构造内层
engine_workers.py:688 self.actor = TrainingWorker(actor_training_config)
          ↓  TrainingWorker.__init__:169
engine/base.py:439    EngineRegistry.new(model_type, backend="megatron", ...)
          ↓  按 (device, vendor) 查表
megatron/transformer_impl.py  MegatronEngineWithLMHead.__init__
   └─ 或 mindspeed/transformer_impl.py  MindspeedEngineWithLMHead（NPU 上自动顶替）
          ↓
   _init_device_mesh()  → mpu.initialize_model_parallel(...)   ← 并行度落地点 ①
   _build_tf_config()   → Megatron-Bridge provider_overrides   ← 并行度落地点 ②
   _build_megatron_module() → 真正 new 出被切好的模型
一句话：并行度在两个地方落地——initialize_model_parallel 负责建通信组（谁和谁一组），provider_overrides 负责告诉模型按多少份切权重。两者必须一致，所以 verl 把同一份 engine_config 喂给了它们俩。

2. 第一层：RayClassWithInitArgs 只是「配方」

verl/trainer/ppo/v1/trainer_base.py:508

注意三件事：

  1. 没有 .remote()：这一行不创建任何 Ray actor，只把 (类, 参数) 打包。后面 RayWorkerGroup 创建时才会对每个 rank 调一次。
  2. 传的是整棵配置树，不是切好的 engine 配置。megatron.tensor_model_parallel_size 之类此刻还埋在 config.actor.megatron 里，没人读。
  3. 存进 resource_pool_to_cls：按资源池分组，同一个池里的多个角色会被合并成一个 colocated worker group（这就是 actor / ref / critic 能共卡的原因）。

7. MindSpeed 是怎么挤进来的

MindSpeed 的工作方式是给 Megatron-Core 打猴子补丁（替换 attention、CP 实现、融合算子等）。verl 要保证两件事的顺序正确。

① import 顺序

verl/workers/engine/__init__.py:54 
# Mindspeed must be imported before Megatron to ensure the related monkey patches take effect as expected
try:
    from .mindspeed import MindspeedEngineWithLMHead, MindspeedEngineWithValueHead
    ...
except ImportError as e:
    warnings.warn(f"mindspeed engine is not available: {e!r}", stacklevel=1)
    MindspeedEngineWithLMHead = None

try:
    from .megatron import MegatronEngine, MegatronEngineWithLMHead, MegatronEngineWithValueHead
except ImportError as e:
    warnings.warn(f"megatron engine is not available: {e!r}", stacklevel=1)

两点值得注意：

  • 注释点明 mindspeed 必须先 import。因为 mindspeed/transformer_impl.py 顶部就 from mindspeed.megatron_adaptor import repatch，而 mindspeed.megatron_adaptor 这个模块一被 import 就开始改 Megatron 的类。如果 Megatron 的符号先被绑定进别的模块命名空间，补丁就可能打不上。
  • 全部用 try/except 包住。GPU 机器上没装 mindspeed、NPU 机器上没装某些 CUDA 组件，都只是 warning，不会让 import 整个失败。这也是为什么注册表是「有谁注册谁」而不是静态表。

② repatch 的时机

光 import 还不够。MindSpeed 第一次打补丁时看到的 CP 是默认值 1，而 verl 的 CP 是通过 hydra 配置传的，不走 Megatron 的命令行参数，所以 CP 相关的补丁没注册上。verl 的解法是在建通信组之前再 repatch 一次：

verl/workers/engine/mindspeed/transformer_impl.py:39 
def _mindspeed_repatch(engine_config):
    if repatch is not None:
        from verl.utils.megatron_utils import mapping_string_to_attn_backend
        repatch_config = mapping_string_to_attn_backend(
            dict(engine_config.get("override_transformer_config", {})))
        # flash-attn-npu batch-invariant 会替换 DotProductAttention.forward；
        # use_flash_attn=True 时融合注意力会注册同一个补丁 → "the patch of forward exist"
        if repatch_config.get("use_flash_attn_npu_batch_invariant"):
            repatch_config["use_flash_attn"] = False
        else:
            repatch_config.setdefault("use_flash_attn", True)
        if engine_config.context_parallel_size > 1:
            repatch_config["context_parallel_size"] = engine_config.context_parallel_size
        repatch(repatch_config)


class MindspeedEngineWithLMHead(MegatronEngineWithLMHead):
    def _init_device_mesh(self):
        # repatch must happen before initialize_model_parallel so that
        # initialize_model_parallel_cp_wrapper is in effect when the call is made.
        _mindspeed_repatch(self.engine_config)
        super()._init_device_mesh()       # ← 再去调 mpu.initialize_model_parallel

10. 实例推演：8 卡 TP2·EP8·ETP1

用 run_qwen3_5_35b_megatron.sh 实测过的配置（GPU 分支，单机 8 卡）：

examples/grpo_trainer/run_qwen3_5_35b_megatron.sh:52 
TP=2  PP=1  CP=1  EP=8  ETP=1  GEN_TP=8    n_devices_per_node=8

先算 DP。DP 不在配置里，是 Megatron 用剩下的卡推出来的（EP 不占这个式子，它是在 DP×TP 的平面内重新划分 expert 的）：

DP = world_size / (TP × PP × CP) = 8 / (2 × 1 × 1) = 4

于是非 expert 部分（attention、layernorm、embedding）的卡布局是：

rank01234567
TP rank01010101
DP rank00112233

TP 组（相邻 2 卡）：{0,1} {2,3} {4,5} {6,7}；DP 组（跨 TP 组同 TP rank）：{0,2,4,6} {1,3,5,7}。TP 放在最内层是因为它每层都要 all-reduce，必须用最快的链路（NVLink / HCCS）。

而expert 部分用的是另一套划分：EP=8, ETP=1 表示 8 张卡各自独占一组 expert，每组 expert 的权重不再切分（ETP=1）：

rank01234567
EP rank01234567
ETP rank00000000
这组配置的意思：同一个模型的两部分用了不同的切法。attention 走 TP=2（权重切两半，每层 all-reduce），expert 走 EP=8（每卡独占 1/8 的 expert，不切权重，靠 all-to-all 换 token）。这正是 ETP 存在的理由——如果没有 ETP，expert 的 TP 就只能跟着 attention 的 TP=2，变成 EP×ETP = 8×2 = 16 > 8 卡，放不下。ETP=1 把 expert 的 TP 单独降到 1，让 EP 能吃满 8 张卡。

11. 五个维度各自切的是什么

下表里「verl 的位置」是 verl 代码负责的部分；真正的张量切分发生在 Megatron-Core / Megatron-Bridge 内部（verl 只传参数，不实现切分）。

维度切什么通信verl 配置字段
TP
tensor		 每一层的权重矩阵。attention 按 head 切 QKV，MLP 把 h→4h 按列切、4h→h 按行切；词表也按 vocab 切 每层 2 次 all-reduce，最频繁，必须同节点 tensor_model_parallel_size
PP
pipeline		 按层切。PP=2 时前一半层在 rank 组 A、后一半在 B 只在切分边界 P2P 传 activation，最省带宽，可跨节点 pipeline_model_parallel_size
virtual_pipeline_model_parallel_size（VPP，把层打散成多段交错执行，减少气泡）
CP
context		 切序列长度，权重不切。每卡算一段 token 的 attention attention 要跨段拿 KV，ring / all-gather context_parallel_size
dynamic_context_parallel + max_seqlen_per_dp_cp_rank
EP
expert		 切 MoE 的expert 个数。每卡放 n_experts / EP 个完整 expert token 的 all-to-all（moe_token_dispatcher_type="alltoall"） expert_model_parallel_size
ETP
expert tensor		 在 EP 之上，再把单个 expert 的权重按 TP 的方式切 同 TP，但只在 expert 层内 expert_tensor_parallel_size（null = 跟随 TP）
SP
sequence		 不是独立维度。依附 TP：把 TP 组内 layernorm / dropout 这些没切的部分也按序列切开，省激活显存 把 TP 的 all-reduce 拆成 reduce-scatter + all-gather sequence_parallel（TP=1 时自动关，见 §12）
DP
data		 不切模型，切数据。每组拿不同的 micro-batch 梯度 all-reduce（开 use_distributed_optimizer 时变成 ZeRO-1 式 reduce-scatter + all-gather） 无配置项，由 world/(TP×PP×CP) 推出

12. 四个容易踩的点

① ETP 默认是 null，不是 1。

verl/trainer/config/engine/megatron.yaml:17 
# expert tensor parallel size (null to be same as TP)
expert_tensor_parallel_size: null

null 会原样传给 initialize_model_parallel，由 Megatron 解释为「跟 TP 一样」。所以 MoE 模型如果你只设了 EP=8 而忘了 ETP=1，在 TP=2 下实际需要 EP×ETP=16 张卡，8 卡会直接起不来。

② TP=1 时 sequence_parallel 被静默改成 False。

verl/workers/config/engine.py:227 
if self.tensor_model_parallel_size == 1:
    warnings.warn("set sequence parallel to false as TP size is 1", stacklevel=2)
    self.sequence_parallel = False

这也是 McoreEngineConfig 要把 sequence_parallel 放进 _mutable_fields 的原因（第 182 行）——别的字段都是冻结的，这个要留口子自动纠正。

③ actor 和 ref 的并行度必须一致，原因见 §8 的 mpu.is_initialized()。

④ dynamic CP 会把 DP rank 伪装成 0。

verl/workers/engine/megatron/transformer_impl.py:704 
def get_data_parallel_rank(self):
    if self.engine_config.dynamic_context_parallel:
        # in order to let every dp-cp group has full data to split, we set dp=1
        return 0
    return mpu.get_data_parallel_rank()

这个返回值会被 TrainingWorker.__init__ 用去注册单控制器的数据分派信息：

verl/workers/engine_workers.py:179 
self._register_dispatch_collect_info(
    mesh_name="train",
    dp_rank=self.engine.get_data_parallel_rank(),
    is_collect=self.engine.is_mp_src_rank_with_outputs(),
)

也就是说，并行度不只影响模型怎么切，还决定了单控制器往哪些 rank 发数据、从哪些 rank 收结果。收集端的判定是：

verl/workers/engine/megatron/transformer_impl.py:522 
def is_mp_src_rank_with_outputs(self):
    return (
        mpu.get_tensor_model_parallel_rank() == 0                                        # TP 组的头
        and mpu.get_pipeline_model_parallel_rank() == mpu.get_pipeline_model_parallel_world_size() - 1  # PP 的最后一段（logits 在这里）
        and mpu.get_context_parallel_rank() == 0                                         # CP 组的头
        and (not self.engine_config.dynamic_context_parallel or mpu.get_data_parallel_rank() == 0)
    )

这四个条件连起来读就是：只有「TP 头 + PP 尾 + CP 头」这个 rank 手里有完整可用的输出，单控制器只从它们收数据。

三句话总结
  1. Megatron 不是在 worker 层选的，是在引擎层选的。 worker 类只有两个，和后端无关；EngineRegistry 用 model_type × backend × (device, vendor) 三维键查表，strategy=megatron 在 NPU 上自然命中 MindSpeed 子类。
  2. MindSpeed 是「同一套 Megatron 代码 + 猴子补丁」，不是另一个后端。它的子类只重写 _init_device_mesh（插 repatch）和 to（FP8 搬运），分片代码零改动。
  3. 并行度要落两次：initialize_model_parallel 建通信组（进程全局、只建一次、所以 actor/ref 必须同构），provider_overrides 告诉 Megatron-Bridge 按多少份切权重。TP/PP/CP 决定 DP（相除得到），EP/ETP 则在这个平面内另行划分 expert。
