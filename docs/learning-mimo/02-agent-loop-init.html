第二课：Agent Loop 初始化（以 General 环境为例）

提问：讲一下 agent loop 初始化吧，主要讲 mimo 的。

初始化分四层，从粗到细。前两层是 verl 框架自带的，后两层是 MiMo 写的：

TaskRunnerV1.init_agent_loop_manager()
 └─ ① AgentLoopManagerTQ.create          整个训练只创建一次
     └─ ② 32 个 AgentLoopWorkerTQ（Ray 进程）   每个 worker 一次，读取"名字→类"登记表
          └─ 每来一个 prompt：_run_prompt 启动 n=8 个并发任务

③ 每条轨迹 new 一个 GeneralAgentLoop

prompt 拆成 n 条轨迹

verl/trainer/ppo/v1/agent_loop_tq.py _run_prompt 
async def _run_prompt(self, prompt: dict, sampling_params, trajectory, trace=False):
    uid = prompt["uid"]
    await tq.async_kv_put(key=uid, partition_id=partition_id, tag={"status": "running"})  # pending → running
    n = prompt.pop("__rollout_n__", config.n)            # rollout.n = 8
    for i in range(n):
        tasks.append(asyncio.create_task(
            self._run_agent_loop(run_sampling_params, trajectory=trajectory, session_id=i, **prompt)))
    session_errors = await _settle_session_tasks(tasks)  # 等 8 条全部结束
    status = "failure" if session_errors else "finished"
    await tq.async_kv_put(key=uid, ..., tag={"status": status})   # replay_buffer 轮询的就是这个状态

每条轨迹都 new 一个新的 GeneralAgentLoop。需要跨轨迹共享的东西都放在类变量或模块变量里：模块级线程池 _AGENT_POOL，以及类变量 GeneralAgentLoop._remote_agent_cls。

_as_bool 的坑：${oc.env:FAIL_ON_ENV_SETUP_ERROR,false} 读出来是字符串 "false"，而 bool("false") 的结果是 True。不专门解析的话，第一个 pod 起不来就会让整个训练任务崩溃。

勘误（2026-10-14，学第三课下时发现）：之前说 General 用的是 cc-agent、开启了 antihack，这是照着 yaml 字面意思讲的，和实际运行的代码不一致。
  • GeneralAgentLoop 不经过 mimoagent 的 agent 工厂（agents/factory.py 才会根据 type 选类），而是直接创建 _RemoteToolAgent，它继承的是 DefaultAgent，不是 CCAgent。所以 type: cc-agent 这一行不起作用。
  • agent_kwargs（yaml 里 agent: 下的全部字段）传给 DefaultAgent 时，BaseAgent.__init__ 用 filter_dataclass_kwargs(config_class, kwargs) 只保留 DefaultAgentConfig 认识的字段（base.py:150 附近），type、antihack、enable_subagents、enable_skills、cost_limit 都被丢弃，不会报错，只打一条 warning 日志（Ignoring config keys not accepted by DefaultAgentConfig: [...]，见 mimoagent/utils/dataclass_kwargs.py）。
  • antihack 的拦截器只在 CCAgent.__init__ 里注册（cc/cc_agent.py：self.add_action_interceptor(self.antihack)）；而且 _RemoteToolAgent 整个重写了 execute_action，原版里调用拦截器的那段逻辑也不会执行。所以General 路径下 antihack 实际没有启用。
  • 工具名用的是 Claude Code 风格（Bash/Read/...），这是靠 recipes/general/tools 里原样复制过来的 6 个工具，通过 register_cc_tools() 注册进 mimoagent 默认的工具注册表实现的。所以准确的说法是：General = DefaultAgent 的循环 + Claude Code 命名的工具。
Code 环境走 mimoagent 的工厂，那里的 cc-agent 确实是 CCAgent。

load_mimoagent_config 会拒绝带子 agent 工具的配置。原因是子 agent 会让对话分叉成一棵树，而训练这边只维护一条只追加、不回改的 token 序列，没法表示树。

④ run()：开 pod、组装 harness

a. 取出任务

instance = self._load_instance(extra_info)   # json.loads(extra_info["instance_json"])
# instance = {"dataset_type", "instance_id", "env_task_dir", "docker_image", "problem_statement"}

之所以存成 JSON 字符串，是因为 HuggingFace datasets 会把字典列强制转成固定结构：不同任务的字段会被合成并集，嵌套字段也会被改形状。

b. 每条轨迹起一个环境进程，并创建 pod

env_actor = DatasetEnvActor.options(num_cpus=self.env_num_cpus, ...).remote(   # 0.125 CPU
    instance=instance, instance_id=instance_id, mimoagent_config_path=..., dump_dir=dump_dir)
ok, error = await asyncio.wait_for(env_actor.setup.remote(), timeout=self._env_setup_timeout_or_none)
if not ok:
    return self._failure_output("env_setup_error", str(error), metrics, error_category="setup/failed", ...)

DatasetEnvActor（recipes/general/env_actor.py）持有三样东西：dataset_env（k8s pod，包含 main 和 sidecar 两个容器）、tool_registry（工具在这里执行）、打分逻辑 calculate_reward。setup() 失败会重试 2 次；_create() 负责拉起 pod，如果任务带 MCP 服务（外部工具服务），还会注册这些工具。

为什么 pod 要放在单独的进程里？

  1. 每次工具调用都是阻塞的远程执行，耗时好几秒。几百条轨迹挤在 GPU 节点上的 worker 进程里会把它拖垮。
  2. Write/Edit 先写本地临时文件，再 env.copy_to 拷进 pod，所以工具必须和 pod 客户端在同一个进程。
  3. pod 卡死时可以直接 ray.kill(env_actor)，强行结束这条轨迹。
pod 起不来怎么办：返回 _failure_output，一个"最小但格式完整"的输出，reward 设为 -999，表示基础设施故障。它的注释记录了几次线上事故，解释了为什么 prompt_ids 不能为空、response_logprobs 不能是 None、min_global_steps 必须有值：后处理时只要有一条样本缺字段，就会连累整个 batch，甚至让 64 张卡的训练步崩溃。

c. 向环境要工具定义和模板变量

described = await env_actor.describe.remote()
schema_dicts, schema_objs = self._tool_schemas(described["tool_definitions"])
# described = {
#   "tool_definitions": [{"type": "function", "function": {"name": "Bash", "parameters": {...}}}, ...],
#   "template_vars": {"cwd": "/work/workspace", ...},   # pod 起来后才知道，用来填 {{cwd}}

schema_dicts 渲染进 chat template，让模型在 system prompt 里看到工具列表；schema_objs 是带类型校验的对象，给 tool_parser 解析参数用。MCP 工具里用 oneOf 声明、缺少顶层 type 的参数会先清洗，实在不行就丢掉这个工具。

d. 替换模型

trace = TokenTrace(response_length=self.response_length)   # 这条轨迹的 token 账本
model = _VerlRolloutModel(agent_loop=self, trace=trace,
                          tool_schema_dicts=schema_dicts, tool_schema_objs=schema_objs,

mimoagent 原来用 LitellmModel 发 HTTP 请求。替换成的 _VerlRolloutModel 只需满足两个约定：query(messages) -> dict 和 get_template_vars()。

e. 组装 agent，替换"执行工具"

if GeneralAgentLoop._remote_agent_cls is None:
    GeneralAgentLoop._remote_agent_cls = _build_remote_tool_agent_class()   # 第一次用时才 import mimoagent
agent = GeneralAgentLoop._remote_agent_cls(
    model=model,
    env=_TemplateVarsEnv(template_vars=described["template_vars"], env_actor=env_actor, ...),
    env_actor=env_actor,
    **agent_kwargs)                                # s3k.yaml 里 agent: 下的字段
def execute_action(self, action: dict) -> dict:     # action = {"tool": "Bash", "params": {"command": "ls"}}
    outcome = ray.get(self._env_actor.execute_tool.remote(tool_name, action.get("params", {})))
    kind = outcome["kind"]
    if kind == KIND_OK:              return outcome["result"]
    if kind == KIND_TRANSPORT_ERROR: raise InfraError(...)              # pod 连接断了
    if kind == KIND_LIMITS_EXCEEDED: raise TerminatingException(...)    # 结束轨迹
    if kind == KIND_TOOL_EXCEPTION:  raise NonTerminatingException(...) # 把错误返回给模型，继续

env_actor 返回带标签的字典，而不是直接抛异常：异常跨 Ray 进程会被包装成 RayTaskError，原来的类型就丢了。在这一侧重新抛出对应类型，mimoagent 的控制流程就和原版完全一致。_TemplateVarsEnv 是环境的"替身"，只提供 get_template_vars() 和转发给 env_actor 的 execute()。

启动

exit_status, exit_message = await asyncio.wait_for(
    self.loop.run_in_executor(_agent_pool(self.agent_thread_pool_size), lambda: agent.run(task=task)),
    timeout=self._trajectory_timeout_or_none)        # 1200 秒总时限

结束后的流程：env_actor.calculate_reward 在 sidecar 里打分 → 基础设施类错误把 reward 改成 -999 → _build_output → finally 里清理 pod 并 ray.kill(env_actor)。

小结：桥接设计

文件 docstring 第一句：这是一座"桥"。mimoagent 的循环原封不动地运行，只替换两个点：

被替换的点原来现在目的
调用模型LitellmModel 发 HTTP_VerlRolloutModel.query()直接用 token 调推理服务，同时记录训练需要的 token 和 logprob
执行工具本进程执行转发到 env_actor工具和 pod 客户端在同一个进程
