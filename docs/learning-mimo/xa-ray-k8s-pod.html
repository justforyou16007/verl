插课 A：MiMo 的 agent 执行进程（Ray）与 k8s pod 怎么配合

提问：临时插一节课，我想知道 mimo 的 agent 执行容器（通过 ray）和 k8s 管理的 pod 是怎么配合的。

0. 结论先行

  1. agent 本身不在 pod 里运行。mimoagent 的循环跑在 Ray 的 AgentLoopWorker 进程里（第三课上讲的 T 线程），pod 只是"手脚"：一个执行命令、存放文件的沙箱。
  2. 每条轨迹 = 1 个 DatasetEnvActor（Ray 进程）+ 1 个 pod。actor 是这个 pod 的唯一"遥控器"：负责创建 pod、往 pod 里执行命令和传文件、打分、最后删除 pod。
  3. actor 和 pod 之间没有直接的网络连接。所有操作都经过 k8s 的 API server：创建/查询/删除 pod 用普通 HTTPS 请求；执行命令、传文件用 API server 提供的 exec 通道（WebSocket），效果等同于 kubectl exec。Ray 节点只要能访问 API server 即可，不需要能访问 pod 的 IP。
  4. pod 里有两个容器：main 是模型操作的工作区；sidecar 运行任务的 MCP 服务（外部工具服务）并负责打分。两个容器共享网络（都能用 127.0.0.1 互相访问），但看到的文件不同，这样模型就碰不到数据库和标准答案。

env_actor 怎么连上 k8s 集群

连接凭据是通过环境变量一路传下来的。run_general.sh 把 KUBECONFIG、DOCKER_REGISTRY、K8S_NAMESPACE 等写进 Ray 的 runtime_env.env_vars，所有 Ray 进程（包括 env_actor）启动时都会带上这些变量。之后的传递路径是：

recipes/general/env_actor.py _create 
env_kwargs = dict(self.config.get("environment") or {})        # s3k.yaml 的 environment: 块
env_kwargs["labels"] = {"exp": os.getenv("EXP_NAME", "unknown"), ...}   # 给 pod 打上实验名标签
if os.environ.get("KUBECONFIG") and "kubeconfig" not in env_kwargs:
    env_kwargs["kubeconfig"] = os.environ["KUBECONFIG"]          # 连哪个集群
if _registry := os.environ.get("DOCKER_REGISTRY"):
    env_kwargs["image_prefix"] = _registry                        # 镜像仓库前缀
self.dataset_env = make_dataset_env(self.instance, **env_kwargs)

mimoagent 的 _setup_kubernetes_client 会为每个环境单独创建一份 k8s 客户端配置，而不是用 kubernetes 库的全局默认配置。这样即使一个进程里有多个环境、分别连不同的集群，也不会互相覆盖。

为什么不把 agent 放进 pod 里跑？黑盒 harness（真正的 Claude Code CLI）确实是在 main 容器里运行的，同一套 pod 结构两种用法都支持（见 general_agent/environment.py 的 docstring）。但白盒 RL 要求每次调用模型都经过 verl 的 _VerlRolloutModel，由它直接调用 SGLang 并记录 token。如果把循环放进 pod，pod 就需要能访问 SGLang 推理服务，token 记录也得跨网络传回来。把循环留在训练集群里、pod 只负责执行，两个问题都不存在。

分两层的原因是：pod 层只负责"怎么操作一个 pod"，和具体任务无关，所以可以复用 mimoagent 原有的代码；任务层负责"这类任务要往 pod 里放什么、怎么打分"。dataset_type: "general_agent" 由 register_general_agent_env() 注册进 mimoagent 的 DATASET_REGISTRY，make_dataset_env 就是根据这个字段找到 GeneralAgentEnvironment 的。

工具执行时拿到的是pod 层对象：

result = tool.execute(params, {"env": self.dataset_env.env})   # env_actor._execute_tool_sync
# Bash 工具内部：env.execute(command, cwd=..., timeout=...)
# Write 工具内部：先写本地临时文件，再 env.copy_to(local_path, file_path)

这也是第二课说"工具必须和 pod 客户端在同一个进程"的具体原因：copy_to 读取的是本进程所在机器上的文件路径。

3. pod 长什么样：main + sidecar

pod 的定义（manifest）由两段代码拼出来：mimoagent 的 KubernetesEnvironment._build_pod_body 生成单容器的基础定义，SidecarKubernetesEnvironment._build_pod_body 再往上追加 sidecar 容器和共享卷。最终大致是：

kind: Pod
metadata: {name: mimoagent-3f9a..., labels: {exp: ga_train}}
spec:
  automountServiceAccountToken: false     # pod 里拿不到 k8s 凭据，模型没法反过来操作集群
  hostNetwork: false                      # 有 sidecar 时强制关闭，否则固定端口会和同节点其他 pod 冲突
  restartPolicy: OnFailure
  volumes: [{name: workspace, emptyDir: {}}, {name: system-vol, emptyDir: {}}]
  containers:
  - name: main
    image: <DOCKER_REGISTRY>/<instance.docker_image>
    command: [/bin/bash, -lc], args: [/bin/bash, -lc], stdin: true, tty: true   # 只是保持容器不退出
    resources: {requests: {cpu: "2", memory: 8Gi}, ...}
    volumeMounts: [{name: workspace, mountPath: /work/workspace}]               # 只能看到工作区
  - name: sidecar
    image: 同上
    command: [sleep, infinity]
    volumeMounts:
    - {name: workspace,  mountPath: /work/workspace, readOnly: true}           # 只读看工作区（打分用）
    - {name: system-vol, mountPath: /work/system}                               # 数据库状态，只有这里能看到

两个容器都只是"空转等待"，pod 里没有任何程序主动做事。所有动作都是 env_actor 通过 exec 发进去的命令。

mainsidecar
谁在用模型的工具调用（Bash/Read/Write…）默认都发到这里MCP 服务、verifier、答案文件
能看到的文件只有 /work/workspace（读写）/work/workspace（只读）、/work/system（数据库）、/work/tools
网络同一个 pod 共享网络空间，main 里的程序用 127.0.0.1:39101 就能访问 sidecar 里的 MCP 服务
隔离是"物理上的"：main 容器根本没有挂载 /work/system，模型无论执行什么命令，都不可能绕过 MCP 工具直接改数据库。标准答案（answer_key.json 等）要等到打分时才上传，而且只传到 sidecar。打分时 verifier 再从数据库的最终状态判断任务有没有完成。

多容器时，命令怎么发到指定容器

k8s 的 exec 接口规定：pod 里有多个容器时，必须指明 container=，否则 API server 返回 400。但 mimoagent 原版的 execute/copy_to 发 exec 请求时不带这个参数。MiMo 没有去改写那约 500 行代码，而是用了一个"代理加线程局部变量"的办法：

recipes/general/general_agent/k8s_sidecar.py 
_ROUTE = threading.local()          # 每个线程各自一份的"当前目标容器"

class _ContainerRoutingCoreV1Api:   # 包住真正的 k8s 客户端，其他方法原样转发
    def connect_get_namespaced_pod_exec(self, *args, **kwargs):
        if "container" not in kwargs and getattr(_ROUTE, "container", None):
            kwargs["container"] = _ROUTE.container          # 只在发 exec 请求时补上目标容器
        return self._inner.connect_get_namespaced_pod_exec(*args, **kwargs)

def execute(self, command, cwd="", timeout=None, container=None):
    with self._route(container):         # 设置 _ROUTE.container：没指定就默认 "main"
        return super().execute(command, cwd, timeout)       # 调用原版代码，不做任何修改

为什么必须用"线程局部"变量，而不能直接存在对象上？因为 mimoagent 会用最多 8 个线程并行执行工具调用（tool_parallel_workers=8）。这些调用经 Ray 到达 env_actor 后，每个都由 asyncio.to_thread 放到一个单独的线程里执行，共用同一个环境对象。如果把目标容器存在对象上，线程 A 刚设成 sidecar，线程 B 就可能读到这个值，把命令发错容器。线程局部变量让每个线程各用各的。

几个容易忽略的细节：

  • "ready" 只代表进程起来了，不代表端口已经在监听。所以 sidecar 版的 _container_ready 要求所有容器都 ready（原版只看 main），打分前还会用 _liveness_ok 读 /proc/net/tcp 确认 MCP 端口确实在监听。
  • 上传的源文件必须在 env_actor 所在机器上能读到。env_task_dir 必须放在所有 Ray 节点都能访问的共享文件系统上（environment.py 的 docstring 有说明），因为 env_actor 可能被调度到任何一台机器。
  • 时间预算：ENV_SETUP_TIMEOUT=3600 秒是从 GeneralAgentLoop 这一侧计时的总时限，包括排队、拉镜像、上传、启动 MCP。超时就返回 _failure_output(error_category="setup/failed")，奖励记为 -999。

5. 一次工具调用怎么到达 pod

以模型调用 Bash(command="ls") 为例，跨了 4 个进程/机器：

① AgentLoopWorker，线程 P
   _RemoteToolAgent.execute_action({"tool": "Bash", "params": {"command": "ls"}})
   → ray.get(env_actor.execute_tool.remote("Bash", {"command": "ls"}))     # 阻塞等待
② DatasetEnvActor（async actor，可以同时处理多个请求）
   execute_tool → await asyncio.to_thread(_execute_tool_sync, ...)
   → tool = tool_registry.get("Bash"); tool.execute(params, {"env": dataset_env.env})
   → env.execute("ls", cwd="/work/workspace", timeout=60)       # s3k.yaml 里 Bash 的 timeout: 60
③ SidecarKubernetesEnvironment.execute → 设置 _ROUTE.container="main" → KubernetesEnvironment.execute
   exec_argv = ["timeout", "60", "/bin/bash", "-lc", "cd /work/workspace && ls"]
   resp = stream(v1_api.connect_get_namespaced_pod_exec, pod_name, namespace,
                 command=exec_argv, container="main", stdout=True, stderr=True, ...)
   ── WebSocket ──▶ API server ──▶ kubelet ──▶ main 容器里执行 ──▶ 输出沿原路流回
   单独起一个读取线程不断收 stdout/stderr，直到命令结束或到达截止时间（timeout + 5 秒）
④ 返回 {"output": "README.md\nsrc\n", "returncode": 0, "reason": "ok"}
   → Bash 工具包装成 ToolOutput → env_actor 返回 {"kind": "ok", "result": {...}}
   → 回到 ①，mimoagent 把结果作为 tool 消息加入 messages

execute 的返回值里，reason 字段区分了四种情况，决定这次调用算"模型的问题"还是"基础设施的问题"：

reason含义后续处理
ok命令正常结束（返回码可以不是 0）输出原样交给模型
pod_timeoutpod 里的 timeout 命令杀掉了进程（返回码 124）给模型看"超时"提示，属于模型自己的问题（比如命令太慢）
client_timeout客户端等到截止时间还没结束同上
transport_errorexec 通道打不开，或者断开时没有拿到返回码s3k.yaml 设置了 raise_on_transport_error: true，会直接抛出 TransportError → 见第 8 节

传文件：tar 打包后通过 exec 的标准输入发送

copy_to 在本地把文件打成 tar 包放在内存里，然后对 pod 执行 mkdir -p 目标目录 && head -c <字节数> | tar xmf - -C 目标目录，并把 tar 包通过 exec 的标准输入发过去。head -c 的作用是：读满指定的字节数就结束输入。因为 WebSocket 没办法真正"关闭"标准输入，部分精简镜像（BusyBox）里的 tar 会一直等更多输入，永远不退出。超过阈值的大文件会改为分块传输（copy_file_chunked）。

Write 工具正是用这个方法写文件：文件内容从不出现在命令行里，所以不会有引号转义的问题，也不会受命令行长度限制。

MCP 工具：借 main 容器转一次

env_actor 访问不到 pod 内部的 127.0.0.1，所以 mcp__crm__search 这类工具（recipes/general/mcp_proxy.py 的 McpProxyTool）的做法是：在 main 容器里执行一次性命令 python mcp_bridge.py --call ...，由这个 bridge 去访问 127.0.0.1:39101 上的 sidecar MCP 服务，再把结果以 __MCP_ONESHOT__{json} 的形式打印出来，由 env_actor 从输出里解析出结果。模型只能看到工具定义和调用结果，MCP 服务的地址只出现在框架自己拼出来的命令行里。

6. 打分：在 sidecar 里跑 verifier

agent.run() 结束后，GeneralAgentLoop 调用 env_actor.calculate_reward.remote()，最终执行到 GeneralAgentEnvironment._do_calculate_reward：

1. 检查评审模型的密钥 GA_JUDGE_KEY             缺失 → reward/testbed_corrupted
2. 读 /proc/net/tcp 检查每个 MCP 端口还在监听       已挂 → testbed_corrupted, dead_port
3. 上传 verifier 文件到 sidecar                    run_verify.py、rubrics.json、answer_key.json ...（这时才上传答案）
4. 会话日志 main → env_actor 本地 → sidecar       经 env_actor 中转两次，不用共享卷，避免污染被评分的工作区
5. 把 agent 最后一条回复写成 workspace/answer.md   经 main 写入（sidecar 对工作区只读）；agent 自己写了就不覆盖
6. 在 sidecar 执行 python3 /work/run_verify.py     规则检查 + LLM 评审（GA_JUDGE_*），默认超时 900 秒
7. cat /logs/verifier/reward.json                 解析失败或不在 [0,1] 范围内 → testbed_corrupted
8. 回到 env_actor：REWARD_BINARIZE=true 时，≥ 阈值(1.0) 记 1，否则记 0；原始分数存进 reward_continuous

可以看到，打分也完全是"env_actor 往 pod 里发命令、再读结果文件"这一个模式。被评分的是任务结束时数据库和工作区的最终状态，而不是模型说了什么，这样模型很难靠嘴上说"我做完了"来骗分。

7. 清理：删 pod、杀 actor

recipes/general/agent_loop.py run() 的 finally 
finally:
    model.stopped = True
    await env_actor.cleanup.remote()          # → dataset_env.cleanup() → KubernetesEnvironment.cleanup()
    ray.kill(env_actor, no_restart=True)

KubernetesEnvironment.cleanup() 的做法：先关掉执行命令用的客户端连接（里面可能残留半开的连接），再新建一个客户端专门用来删除：第一次用 Foreground 方式删除，之后改用 Background；每次删除后最多轮询 15 秒，直到查询返回 404，最多尝试 5 次。新客户端用的是这个环境自己的集群配置，而不是全局默认配置，否则可能去另一个集群删除，返回 404 后被误判为"已经删掉了"，真正的 pod 就泄漏了。

如果训练进程整个崩溃了：finally 来不及执行，pod 会残留在集群里。所有 pod 都带有 exp=$EXP_NAME 标签，可以按标签批量清理，例如 kubectl delete pods -l exp=ga_train -n <namespace>。

8. 故障怎么分类（含一个疑似 bug）

RL 训练要区分两类失败：模型做错了（应该给 0 分，让模型学习）和基础设施坏了（应该给 -999，让这条样本不参与训练，第一课 §1 讲过）。下面是 pod 相关故障的分类：

9. 思考题

Q1：一个 pod 要 2 核 CPU、8G 内存，env_actor 却只申请了 0.125 个 CPU，为什么？

两者占用的是不同集群的资源。pod 的 CPU 和内存由 k8s 集群提供，命令真正在那里执行。env_actor 只是一个"遥控器"，大部分时间在等网络返回，CPU 消耗很低。申请 0.125 个 CPU 是 Ray 调度用的"记账值"：同时跑 512 条轨迹（64 个 prompt × 8）时，只需要 64 个逻辑 CPU，不会因为 Ray 认为 CPU 不够而让 env_actor 排队。SPREAD 则让这些 actor 分散到各个节点上，避免集中在某一台机器上。

Q2：为什么 env_actor 的 setup、execute_tool、cleanup 都写成 async def，内部再用 asyncio.to_thread？

Ray 的 actor 默认一次只处理一个请求。写成 async 方法后，它变成"异步 actor"，可以同时处理多个请求；而 k8s 操作都是阻塞的，所以要用 to_thread 放到线程里执行，避免卡住 actor 自己的事件循环。效果是：并行的工具调用能同时执行；建 pod 时间很长时，外面发来的 cleanup 也能及时得到处理（setup 的 docstring 专门提到了这一点）。这和第三课（上）"在事件循环上不能阻塞"是同一个道理，也正是第 3 节需要线程局部变量的原因。

Q3：如果把 sidecar 的 /work/workspace 改成读写挂载，会有什么风险？

verifier 在 sidecar 里运行，打分前还会往里拷文件。如果 sidecar 可以写工作区，打分过程就可能改动被评分的状态，或者在工作区里留下文件，这些文件之后可能被其他步骤读到。设成只读，等于强制规定"打分只能读、不能改"。也正因为如此，answer.md 必须经 main 容器写入（第 6 节第 5 步）。
