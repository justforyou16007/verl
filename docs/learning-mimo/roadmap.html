学习路线：verl 与配套软件栈

写于 2026-11-11。基于分支 mimo-agent-env（65e5da92）；官方 main 已同步到 81464bb6。路径与符号名以此时代码为准，正文尽量写符号名而不是行号——行号改代码就偏，符号名要稳得多。

0. 这份路线按什么组织

你给的目标是三条：掌握 verl 和它的依赖栈、训练出问题能快速定位、能想出优化系统的点子。这三条不是「把代码读完」能换来的，原因在插课 G 里已经完整演示过一遍：

那次的现象是 torch.OutOfMemoryError 抛在一行 .cpu() 上。真正的原因是反向传播里第一次用到某个通信域、建链失败。两者相隔 30 秒和四五层软件。

当时真正起作用的能力，不是「读过哪个文件」，而是三件事：知道算子是异步下发的、所以 Python 栈指向的那一行是无辜的；知道真张量 OOM 一定带 Tried to allocate … reserved in total 这组统计量、没有就不是；知道通信域是惰性创建的、所以「第一次用到」和「显存峰值」会撞在一起。

所以这份路线按能力组织，而不是按模块目录组织。三条目标对应三种能力，它们各自的瓶颈不一样：

你要的真正卡住人的是路线里怎么练
快速定位 不知道每一层会把下一层的错误包装成什么样子。现象离原因远，就会在错误的层里反复找。 第 2 节的「错误伪装表」+ 第 5 节按现象索引的定位路径；阶段 ① 先把测量手段配齐，阶段 ④ 建立对照系用来做二分。
优化 idea 算不出账。说不清一个 step 的时间、显存、通信各自花在哪，优化就只能靠试参数，试出来也不知道为什么。 第 3 节的三本账；阶段 ① 把账记下来，阶段 ⑨ 从账里找「不必要的支出」。
掌握整个栈 栈的边界不清。分不清哪个问题是 verl 的、哪个是 Megatron 的、哪个是 CANN 的，就会去改不该改的地方。 第 2 节的分层表给出每层的归属判据；第 6 节讲清版本约束怎么锁死的。

每个阶段都写了三样东西：要建立的判断力（学完能回答什么问题）、读什么、做什么能验证自己真的会了。只读不做的阶段会很快忘掉，因为这些知识的形态是「判据」，判据必须在真实数据上用过才能内化。

2. 分层与「错误伪装表」

这一节是整份路线里最该先记住的东西。先看分层——注意这个分层不是按目录划的，是按「谁负责把事情做对」划的，因为定位问题时你要回答的正是「这一步谁该负责」：

L7  配置层      hydra 配置组 + dataclass           决定「跑的到底是什么参数」
L6  驱动层      trainer / fit 主循环               决定「按什么顺序做、等谁」
L5  分派层      single_controller                  把一次驱动调用变成 N 次远程调用
L4  数据层      TensorDict + TransferQueue         决定「张量的形状和掩码对不对」
L3  引擎层      Megatron / FSDP + vLLM / SGLang    决定「算得快不快、显存够不够」
L2  通信层      NCCL / HCCL                        决定「卡之间能不能对上」
L1  运行时      CUDA / CANN + 驱动                 决定「算子到底执行了没有」

真正难的不是记住这七层，而是下面这张表。每一层都会把下层的错误改头换面再交给你，这是定位之所以难的根本原因：

层它把下层错误伪装成什么怎么看穿
L1 运行时 算子是异步下发的：错误不在出错的那一行抛出，而是攒到下一个同步点（.cpu()、.item()、打印一个标量）才冒出来。于是 Python 栈指向的那一行通常是无辜的。 看时间戳最早的那条日志，而不是栈顶。昇腾下真正的首发故障可能比 Python 异常早几十秒。想临时关掉这层伪装，CUDA 下设 CUDA_LAUNCH_BLOCKING=1 让下发变同步（会很慢，只用于定位）。
L2 通信层 两种伪装。一是伪装成显存不足：建链、注册通信缓冲失败，被包成 OutOfMemoryError。二是伪装成卡死：某个 rank 没进集合通信，其他 rank 就一起等到超时，报错的是等的那些、不是缺席的那个。 第一种看有没有分配统计量：真张量 OOM 一定带 Tried to allocate … reserved in total by PyTorch，没有就不是显存问题，调 batch 无效。第二种比对各 rank 的最后一条日志，停在不同阶段的那个才是元凶。
L3 引擎层 伪装成「算法不收敛」。权重同步漏了一部分、量化精度掉了、训练和推理走了不同的核，表现出来只是奖励不涨——不报错、不崩。 用训推 log_prob 的差距做判据，仓库里有现成探针（阶段 ⑥）。先量这个数，再去怀疑算法。
L4 数据层 伪装成「模型学坏了」。掩码错位、padding 被当成真 token 参与统计、组内样本串了行，损失曲线看起来只是「有点怪」。 构造极小批次手工核对：2 个 prompt × 2 个样本，把每一步的形状和掩码打出来，和手算对。这类问题靠看曲线永远看不出来。
L5 分派层 几乎不伪装，但几乎没有容错：单个 rank 的异常会原样从 ray.get 冒出来，没有重试、没有部分失败处理。好处是栈比较真实，坏处是一个 rank 挂掉整个作业就停。 直接读 worker 日志，不要只看 driver。driver 看到的是转述。
L6 驱动层 伪装成「性能问题」。某个阶段在等另一个阶段（生成等训练让出显存、训练等数据攒够），表现为吞吐低，但 GPU 其实在空转。 看分阶段计时而不是总时间（阶段 ①）。空转和算得慢，在总时间上长得一样。
L7 配置层 最隐蔽的一种：你以为设了，其实没人读。配置项写错名字或根本没接线，程序照常跑，行为是默认值。 查展平后的配置 + 全仓搜这个键有没有读取方（阶段 ②）。笔记里已经抓到四个这样的项：algorithm.length_penalty、K8S_* 那组、pod_timeout、ray_wait_register_center_timeout。
这张表的用法：遇到问题时不要从「我觉得是哪里」开始，而是从现象落在哪一层开始，然后先用判据排除伪装，再往下走。第 5 节把它整理成了按现象查的形式。

3. 三本账：优化 idea 从哪来

优化点子不是灵感，是算出账之后看到的不合理支出。你在插课 G §13 已经用过这个办法一次：把 stage0 激活显存写成一个公式，发现 PP 被约掉了、真正决定它的是 CP×TP——这个结论不可能靠试参数试出来，只能靠算。

三本账要分开记，因为它们的优化手段互相冲突，不分开就会按下一头翘起另一头。

显存账

一张卡上的显存分给这几样东西，它们的缩放规律完全不同，所以要分项记而不是只看总量：

项随什么变注意
权重÷ (TP×PP×EP)固定支出，和序列长度无关
梯度 + 优化器状态÷ 分布式优化器的切分维度当 DP=1 时它沿别的维度切，要看实际建了什么组
激活∝ 序列长度 ÷ (CP×TPsp)，× min(PP, 微批数)长序列训练的主要支出，也是最容易算错的一项
通信缓冲每个通信域独占一份，惰性创建不走 PyTorch 分配器，所以分配器攥着的空闲缓存它拿不到
推理 KV cache推理引擎按剩余显存自己定共卡时它和训练峰值互相挤

关键区分：reserved（分配器从驱动那里要来的）和 allocated（真正给了张量的）不是一回事。通信库在这两者之外单独向驱动要内存，所以「allocated 离上限很远」并不能说明通信库申请得到——插课 G §12 的结论就卡在这个区别上。

通信账

每个并行维度在每一层引入几次集合通信、每次多少字节、走什么物理链路。走什么链路这一项最容易被忽略，但它的影响是量级上的：节点内走高速互联，跨节点走网络，带宽差一个数量级。

所以「某个并行维度的组是否正好装进一个节点」往往比「这个维度设成几」更要紧。插课 G §11 里 TP×CP=16 是否塞得进一个节点就是那次的分水岭，官方 256K 参考脚本把 TP×CP 刻意凑成正好一个节点也是这个道理。

时间账

一个 step 的时间分解。这本账有现成工具（阶段 ①），记的时候要把三种情况分开，因为它们的优化方向完全不同：

  • 真的在算——优化方向是提高单卡效率（算子、精度、融合核）。判据是 MFU 不低。
  • 在等通信——优化方向是改并行布局或重叠通信。判据是各 rank 耗时接近但 MFU 低。
  • 在等别人——优化方向是改调度（异步、流水、预取）。判据是 rank 之间耗时差异大，或某阶段 GPU 几乎空闲。

第三种最常见也最容易被误判成第一种。区分它们需要分 rank 看，不是看平均值——所以仓库里有个专门算尾部比例和最大最小值的工具函数（阶段 ①）。

4. 九个阶段

顺序的逻辑是：先能看见 → 再能查 → 再懂数据 → 再有对照 → 再懂算法 → 再懂训推 → 再懂底座 → 再能长跑 → 最后做优化。前两个阶段投入最小、回报最快，建议不要跳。

① 先把「看得见」做出来

要建立的判断力：拿到一个训练任务，能说出它的一个 step 时间花在哪、显存峰值由什么决定、哪个 rank 是拖后腿的。

为什么排第一：没有测量，定位靠猜、优化靠赌。插课 G §12 之所以只能停在「候选原因」而给不出结论，就是因为 plog 丢了、而当时没有第二套证据。配齐测量手段之后，同样的问题下次会是可判定的。

profiler——仓库里是「一个分发器 + 五个后端」的结构，都在 verl/utils/profiler/：

后端用来回答什么实现
torch算子级时间去哪了（产出可在浏览器里看的 trace）torch_profile.py
nsys同上，但能同时看到 CPU 下发和 GPU 执行的错位nvtx_profile.py
npu昇腾上的对应物mstx_profile.py
torch_memory显存是被谁占的，以及 OOM 瞬间的现场torch_memory_profile.py
precision_debugger逐层数值对比，查精度precision_debugger_profile.py
对你当下最有用的是 torch_memory。它会注册一个 OOM 观察器（TorchMemoryProfiler._attach_oom_observer，昇腾上走 torch_npu 的对应接口），在分配器报 OOM 的那一刻自动 dump 一份显存快照加 Python 栈，而且刻意不做设备同步——因为那时候流可能已经处于错误状态，同步会把现场冲掉。

这正好补上插课 G 缺的那块证据：下次再出 EI0007，你会同时拿到「分配器视角的显存构成」和「首发故障时间点」，前面那个「是显存不够还是网卡配额不够」的二选一就不用再靠推断。

开关在 verl/trainer/config/ppo_trainer.yaml 的 global_profiler 块，往下传给每个角色（actor / critic / ref / rollout 各自可以覆盖）。有个坑：选哪些步去采样的键名是 global_profiler.steps，但它传到 worker 那层时参数名变成了 profile_steps——搜代码时两个名字都要试，不然会以为没接线。

时间账——计时器在 verl/utils/profiler/performance.py：

  • marked_timer(name, timing_raw)：既记时间，又在 profiler 的时间轴上打一个区间标记。所以 trace 里的区间和指标里的阶段名是对得上的。
  • 已经埋好的阶段名：step、gen、reward、old_log_prob、ref、values、adv、update_critic、update_actor、update_weights、save_checkpoint、testing；异步模式还多出 switch_to_rollout / switch_to_trainer / switch_wait。这三个 switch 就是上面「在等别人」那类支出的直接读数，异步模式下先看它们。
  • topk_reduce_ratio_min_max(timing, k=10)：找拖后腿的 rank。这是时间账里唯一能区分「大家都慢」和「个别慢」的工具，平均值做不到。

指标——verl/trainer/ppo/metric_utils.py 把计时变成可读的数：timing_s/{阶段} 是绝对秒数，timing_per_token_ms/{阶段} 按 token 归一（跨 batch 比较要用这个），perf/throughput 是每 GPU 每秒多少 token。MFU 走 verl/utils/flops_counter.py 的 FlopsCounter.estimate_flops，它按模型架构分别估算，再除以设备峰值得到 perf/mfu/*。

读 MFU 之前先看一眼它怎么算的。flops_counter.py 是按架构写死的估算公式（每个模型族一个函数），你的模型如果走的是兜底分支，这个数只能用来做自己跟自己比较的相对参考，不能当绝对效率。判断方法：在 flops_counter.py 里搜你的架构标识，看有没有专门的估算函数。

要做的：在自己的训练上开一次 torch profiler（挑第 2 到第 3 步，第 1 步含预热不具代表性），再开一次 torch_memory，产出一张基线表：各阶段秒数、每 token 毫秒、吞吐、MFU、显存峰值、最慢 rank 与中位 rank 的比值。这张表是后面所有优化的对照基准——没有它，改完之后你没法证明是改好了还是改坏了。

自测：能回答「这个 step 里占比最大的那一段，是在算、在等通信、还是在等别人」，并说出判断依据。

② 配置层的权威查法

要建立的判断力：给一个配置项名字，五分钟内判断它到底有没有生效。

为什么排第二：投入最小、回报最高。你已经踩了四次「设了但没人读」，这不是知识不足，是缺一套固定查法。

配置是两层拼起来的，这是「静默不生效」的根源：外层是 hydra 的配置组（verl/trainer/config/ 下按角色分的目录：actor、critic、ref、rollout、data、algorithm、model、engine、optim、profiler、reward、transfer_queue），内层是接收它的 dataclass。yaml 里多写一个键，hydra 不一定报错；dataclass 那边没有对应字段，这个值就到不了任何代码。

三步查法：

  1. 看展平后的配置。verl/trainer/config/_generated_ppo_trainer.yaml（以及 _generated_ppo_megatron_trainer.yaml 等变体）是 hydra 把所有配置组合并之后的完整快照，由 scripts/generate_trainer_config.sh 调 scripts/print_cfg.py --cfg job 生成。你的键如果不在这里面，它就不是一个被承认的配置项。想看自己那套覆盖之后的实际值，直接跑 print_cfg.py 带上同样的命令行覆盖。
  2. 搜读取方。在 verl/ 下搜这个键名，确认有代码真的取了它。笔记里那四个未接线项都是卡在这一步——配置里有、生成的 yaml 里也有，但没有任何读取方。
  3. 看是不是被改写了。有些配置会在运行时被程序强制改掉，查法是搜「赋值」而不是「读取」。一个真实例子：verl/trainer/main_ppo.py 的 TaskRunnerV1.run 里把 config.transfer_queue.enable 直接设成 True——所以这一项在 v1 路径上不是可选的，你在 yaml 里关掉它也没用。

还要知道 verl/base_config.py 的 BaseConfig 有个冻结语义：一个字段一旦有值，再赋值就抛 FrozenInstanceError，除非它被列进 _mutable_fields。这是故意的——防止配置在运行中被偷偷改掉。你写代码想改配置时会撞上它，那时要改的是 _mutable_fields，不是绕过它。

要做的：把自己正在用的训练脚本逐项过一遍这三步。按以往命中率，大概率还能再挖出一两个不生效的项。

③ 数据平面

要建立的判断力：能手工追一条样本从文件到 loss 的全程形状变换，并说出每个掩码是在哪一步生成的。

为什么重要：这是精度类问题唯一的定位路径。而且这一层正在换代，不先搞清新旧之分会读错文件。

先弄清一件事：DataProto 已经不在主路径上了。
verl/trainer/config/ppo_trainer.yaml 里 trainer.use_v1: true 是默认值，v1 路径用的是朴素的 TensorDict 加 TransferQueue 的 BatchMeta。DataProto 只在老的 main_ppo_v0.py 路径上还活着。数量上看得很清楚：ray_trainer.py（旧）里有 27 处 DataProto 引用，v1/trainer_sync.py 里是 0 处。

所以正确的读法是：读 verl/protocol.py 学概念，读 verl/trainer/ppo/v1/ 看实际在跑的代码。

protocol.py 里值得学的概念（这些操作在新路径上换了实现，但语义没变，因为它们是数据并行本身的需要）：

  • chunk / concat：按数据并行度切分和合并。切分必须整除，于是有了下面的补齐。
  • pad_dataproto_to_divisor / unpad_dataproto：批大小不能被卡数整除时，把自己开头的几条重新接到尾部凑整，算完再切掉。知道这个机制，才能解释「为什么指标里偶尔有重复样本的痕迹」。
  • union：把另一份数据的键合并进来，键冲突时断言相等。这是「算完 log_prob 再贴回原批次」的实现方式。
  • repeat 的 interleave 开关：同一个 prompt 的多个采样是排成 ABAB 还是 AABB。这个顺序直接决定组内优势算得对不对，是 GRPO 这类按组求基线的算法最容易错的地方。
  • DataProtoFuture：只传 Ray 的对象引用、不把数据拉到 driver。理解它才明白为什么 driver 侧不能随便对数据做操作。

新路径上数据怎么流动：verl/utils/transferqueue_utils.py 的 tqbridge 装饰器在 worker 边界上把元数据和真实张量互相转换，而它是在 verl/single_controller/base/decorator.py 里无条件套到每个 @register 方法上的。含义是：driver 和 worker 之间传的是元数据，worker 自己去分布式存储取张量。所以排查数据问题时，driver 上打印不出真实张量，得在 worker 侧看。

数据集层（verl/utils/dataset/rl_dataset.py）有一个反直觉的事实：RLHFDataset.__getitem__ 不做分词，只返回原始消息，分词已经搬到 agent 循环里去了（因为多轮对话的 token 要按轮次增量拼，数据集这一层看不到对话会怎么长）。它返回的 dummy_tensor 纯粹是为了满足「批次里至少得有一个张量」这个旧约束。

分词只在一个地方还发生：maybe_filter_out_long_prompts 在加载时试算长度，把超长的行直接丢掉（filter_overlong_prompts 默认 True）。它刻意用和 agent 循环一样的方式加载工具定义，好让估算的 token 数和实际一致。

勘误（2026-11-12 画时序图时查出）：本节原先写「真正的截断在 verl/utils/torch_functional.py 的 postprocess_data」，这是错的。那个函数和它的包装 tokenize_and_postprocess_data 全仓没有任何调用方，是 agent loop 化之后留下的死代码（verl/utils/ulysses.py 里有个同名方法，但那是 sharding manager 的，不相干）。

真正的截断在 agent 循环里：prompt 侧是 AgentLoopBase._cap_text_prompt_length，超长就取末尾（左截断）——而多模态 prompt 会直接抛错，因为占位 token 必须和多模态输入严格一一对应，截断会错位；response 侧则是生成后按 response_length 切片。

关于形状和布局，有一个开关的影响面比它的名字大得多：use_remove_padding（默认 True）。它决定交给注意力核的是哪种布局——开则把一个微批里的所有序列首尾相接拼成一条（没有 pad 参与计算，边界靠 cu_seqlens 记录），关则补齐成规整矩阵（pad token 要跟着走完整个前向）。它还连带决定另外四样东西能不能用，详见数据形状与布局变换那张时序图。两个坑：生效值会被 model 配置覆盖 engine 配置（代码注释自认 not elegant），所以两处都得设；以及 CP>1 时它必须为 True，否则启动即报错（见第 5 节）。

一个容易忽略但会毁掉 resume 的点：数据加载器用的是 torchdata 的 StatefulDataLoader，采样器也必须用它配套的 RandomSampler。verl/trainer/ppo/utils.py 里有注释说明原因——标准库的 RandomSampler 恢复不出正确状态。所以自定义数据加载时如果换回标准采样器，训练能跑，但断点恢复之后数据顺序是错的，而且不会报错。

要做的：构造一个 2 prompt × 2 采样的极小批次，把每一步的形状、response_mask、优势打出来，和手算对一遍。这个练习的价值在于：以后任何掩码类问题，你都有一个已知正确的参照。

④ FSDP 作为对照系

要建立的判断力：遇到一个问题，能设计出「换一个后端看还在不在」的二分实验。

为什么需要：定位最有效的手段是二分，而二分需要第二套实现。你现在只有 Megatron 一条路，一旦出问题，「通用逻辑错了」和「Megatron 特有问题」区分不开。FSDP 还有个实际好处——能在很少的卡上跑起来，迭代快。

这个 fork 的结构和上游老版本不同：没有 fsdp_workers.py 或 megatron_workers.py 这种按后端分的 worker 文件。两个后端都实现同一个接口 verl/workers/engine/base.py 的 BaseEngine，由 EngineRegistry 按「模型类型 + 后端 + 设备」三个键查表选出来（插课 F 讲过这个查表），上面统一由 verl/workers/engine_workers.py 驱动。

所以换后端真的只是换一个配置字符串，worker 代码不变——这正是它能当对照系的前提。

读的顺序：先 engine/base.py 的 BaseEngine 看契约有哪些方法（initialize、train_mode / eval_mode、forward_backward_batch、to 做搬运、get_per_tensor_param 系列导出权重给推理侧），再 engine/fsdp/transformer_impl.py 看 FSDP 怎么实现它，最后和 engine/megatron/transformer_impl.py 对照。

FSDP 侧值得理解的几个旋钮，它们的共性是都在拿通信换显存（这也是为什么它们属于显存账而不是时间账）：

配置项作用代价
fsdp_size参数在多少张卡之间切；-1 表示全部切得越散，每次用参数时要聚合的范围越大
reshard_after_forward前向用完是否立刻把参数散回去散回去省显存，但反向要再聚合一次
param_offload / optimizer_offload参数、优化器状态挪到主机内存省显存最多，但每步要来回搬
use_no_sync_for_gradient_accumulation梯度累积期间不做同步，只在最后一次同步累积期间梯度不是全局的，显存要多留一份
ulysses_sequence_parallel_size沿序列切分（对应 Megatron 的 CP）注意力处要额外通信
pad_to_length + pad_to_length_bucket把打包后的长度向上取整到桶的整数倍算一点无用 token，换来形状种类变少，避免核反复重编译和自动调优

最后那一项值得单独说：它优化的不是计算量，而是形状的多样性。动态长度会让底层每遇到新形状就重新编译或重新调优，开销出现在 CPU 侧和首次执行上，从总 FLOPs 看不出来。这是一类很容易被忽略的优化方向——凡是「每步形状都不一样」的地方都值得查一下有没有这种开销。

要做的：拿一个 0.6B 级别的小模型，用 FSDP + vLLM 跑通两步训练（tests/special_e2e/ 下有现成脚本可以照着改）。目标不是训出东西，是建立一个已知能跑通的参照环境。以后怀疑任何问题，先在这里复现一次。

⑤ 算法层

要建立的判断力：看到「奖励不涨」，能分清是算法配置选得不对、还是实现有 bug、还是根本不是算法问题。

好消息：算法层几乎全在一个文件——verl/trainer/ppo/core_algos.py（约 2600 行）。两个注册表、所有优势估计器、所有损失函数、两种 KL、损失聚合都在里面。

结构是「注册表 + 装饰器」：@register_adv_est 把优势估计器登记进 ADV_ESTIMATOR_REGISTRY，@register_policy_loss 把损失登记进 POLICY_LOSS_REGISTRY，配置里的字符串按名字查出函数。登记只靠 import 时的副作用，所以自定义算法必须在 trainer 解析名字之前被 import 到——这是接自己算法时最常见的坑。

目前可选项：14 个优势估计器（gae、grpo、reinforce_plus_plus、rloo、remax、opo、grpo_passk、gpg、gdpo 以及几个向量化版本和 token 基线版本），12 种损失模式（vanilla 是默认的 PPO 截断，另有 gspo 做序列级比值、cispo、geo_mean、dro、clip_cov / kl_cov、sapo、dppo_tv / dppo_kl 等）。选择点只有一处：verl/workers/utils/losses.py 的 ppo_loss 读 actor.policy_loss.loss_mode 查表。

有两个 KL，不要混为一谈——这是算法配置里最常见的误解：
  • 奖励里的 KL（algorithm.use_kl_in_reward）：在奖励上减一个与参考模型的偏离惩罚，由一个控制器调系数（固定的或自适应的）。它改变的是优化目标。
  • 损失里的 KL（actor.use_kl_loss）：直接在损失上加一项。它改变的是梯度。
两个可以同时开，那样惩罚会加两次。另外 kl_penalty 的估计方式有 k1 / k2 / k3 几种（方差和偏差的不同取舍），带 + 后缀（如 k3+）是个技巧：前向用这个估计量的值，反向用无偏的 k2 梯度。看到配置里带加号不要以为是笔误。

第四课已经讲透 prompt-mean 这一种聚合。agg_loss 一共六种（token-mean、token-sum、prompt-mean、seq-mean-token-sum、seq-mean-token-sum-norm、seq-mean-token-mean）。值得补齐，因为聚合方式决定了长回答和短回答谁的权重大，它对训练结果的影响常常比换算法更大，而且完全不报错。

要做的：跑 tests/trainer/ppo/ 下的 CPU 测试（test_core_algos_on_cpu.py 测的就是注册表本身的契约，test_loss_aggregation_on_cpu.py 和 test_prompt_mean_loss_on_cpu.py 测聚合）。这些测试无卡可跑，是最便宜的可执行规格说明——读测试比读实现快，因为测试直接告诉你边界在哪。

⑥ 推理引擎与训推一致

要建立的判断力：能量化训练侧和推理侧的分歧有多大，并判断这个量级是否正常。

这是 agent RL 里最隐蔽的一类问题。训练用 Megatron 算 log_prob，生成用 vLLM 或 SGLang，两者的核、精度、批处理方式都不同，所以一定有差异——问题是多大算正常。差异过大时策略梯度的比值就不再接近 1，PPO 的截断会被频繁触发，表现出来只是「学不动」，不报错。

仓库里有现成的探针：scripts/rollout_logprob_diff.py。它用 vLLM 或 SGLang 跑一遍生成，再用 Megatron 重算 old_log_probs，报告两者的差距，超过 --max-k3-kl 阈值就非零退出（所以它可以直接当门禁用）。

配套的在线诊断在 verl/utils/debug/metrics.py：calculate_log_prob_diff 和 pearson_correlation_coefficient，训练过程中就能看到这个分歧。

建议现在就为自己的模型测一个基线值。有了基线，以后换量化、换引擎版本、改并行布局，都能立刻知道有没有把一致性弄坏——而不是等奖励曲线不对了再回头猜。

要做可复现的对比时，有两个开关：VERL_FULL_DETERMINISM（配合 VERL_SEED）和 VLLM_BATCH_INVARIANT。后者针对的是一个很反直觉的现象：同一条请求，和别的请求一起批处理时，算出的结果和单独跑不完全一样（归约顺序变了）。查训推不一致时这是必须排除的干扰项。

引擎接入方式在 verl/workers/rollout/，枢纽是 replica.py：RolloutMode 三种模式（hybrid 和训练引擎共进程、colocated 同一组卡但独立进程、standalone 独占卡）、RolloutReplica 抽象，注册了 vllm / sglang / trtllm 三个后端。插课 E 已经走过 standalone 那条，另两条可以对照着看。

一个值得知道的实现细节：verl 没有自己写 OpenAI 兼容的路由，而是直接 import vLLM 自己的 api_server 把应用建起来（vllm_async_server.py）。好处是协议细节不会漂，代价是 vLLM 升级时这个接口的签名变化会直接打到 verl——代码里因此有按版本分支的调用。这解释了为什么 vLLM 的版本是硬约束而不是建议。

⑦ 依赖栈的内部

要建立的判断力：给一个卡住不动的训练，能定位到是哪个 rank 卡在哪一行。

到这一步才向下走，是因为前面几个阶段会不断把问题推到这一层，带着具体问题来读比空读有效得多。

Ray——verl 用它做进程编排。要掌握的不是 Ray 的全部，而是四件事：actor 的生命周期和失败语义（verl 这边几乎没有容错，所以 actor 挂了就是作业挂了）、placement group 怎么把 worker 钉到指定的卡上、对象存储什么时候会把数据落盘、以及 dashboard 和日志目录的位置。verl/single_controller/ray/base.py 是 verl 对 Ray 的全部用法，读它比读 Ray 文档更对口。

抓卡死——这是最该先练熟的一项技能，因为它最常见也最容易无从下手。py-spy 已经在测试依赖里（pyproject.toml 的 test 和 cpu extra）。办法是对每个 worker 进程 py-spy dump，看各自停在哪。关键是比对而不是单看：如果 N-1 个 rank 都停在同一个集合通信上、剩下一个停在别处，那停在别处的那个才是元凶——集合通信要求所有成员都到场，缺席者不报错，等待者报超时。

torch.distributed——重点是通信域惰性创建这件事（插课 G 已经踩过）：建一个组的开销和显存占用发生在第一次真正用它的时候，不是声明的时候。于是「反向传播才首次用到的组」和「显存峰值」会撞在一起。verl/utils/distributed.py 里的 warmup_process_groups（你自己加的那个）就是把这个时刻挪到启动阶段。

通信库——NCCL 和 HCCL 的调试主要靠环境变量把日志级别打开，以及理解拓扑探测的结果（哪些链路走高速互联、哪些走网络）。这块插课 G 已经有相当积累，缺的是在正常训练上也看一眼，建立「正常长什么样」的印象——只在出事时看日志，就没有对照。

要做的：在正常训练上做一次 py-spy dump 全量采集，存下来。这是「正常状态」的快照，下次卡死时拿来对比。

⑧ checkpoint 与长稳

要建立的判断力：能存一次、断一次、恢复一次，并验证恢复后指标是连续的。

先避开一个命名陷阱，不然会找错文件：
  • verl/utils/checkpoint/ 是磁盘 checkpoint——存到硬盘、断点恢复。
  • verl/checkpoint_engine/ 不是磁盘 checkpoint，它是训练侧和推理侧之间的权重同步层（发权重、收权重），对应你已经学过的 arch/verl-weight-sync 那张图。
  • 更要命的是：trainer 里的 self.checkpoint_manager 是 CheckpointEngineManager，属于后者（权重同步）。它有 update_weights() / sleep_replicas() 这类方法。trainer 从磁盘 checkpoint 那个模块只 import 了一个 find_latest_ckpt_path。
两套不相干的子系统，名字几乎一样。我已核对过 verl/trainer/ppo/v1/trainer_base.py，确实如此。

磁盘侧的编排者是 verl/utils/checkpoint/checkpoint_handler.py 的 CheckpointHandler，按后端分 FSDPCheckpointManager 和 MegatronCheckpointManager。存什么由 save_contents 控制（默认模型、优化器、额外状态；可选导出 HuggingFace 格式）。

Megatron 侧的目录布局有个设计值得学：根目录下的 ckpt_contents.json 清单由 rank 0 最后写。于是它存在就意味着这份 checkpoint 是完整的——异步保存时这是唯一可靠的完整性信号。自己写工具扫 checkpoint 时应该依赖这个文件，而不是看目录是否存在。

恢复有两个坑：

  • 数据加载器状态按数据并行 rank 存成单独文件，依赖 StatefulDataLoader（阶段 ③ 提过）。
  • 在 epoch 边界上恢复时，数据加载器状态会被刻意跳过（旧 trainer 里有这个判断）。这是有意的，但如果不知道，会以为恢复坏了。

verl/model_merger/ 是把切碎的 checkpoint 合回 HuggingFace 格式的工具（python -m verl.model_merger merge --backend megatron ...），模型很大时支持多进程合并。训练完要把模型拿出去用，走的是这里。

⑨ 从账本到优化

要建立的判断力：提出一个优化点，能先算出预期收益、再用实验验证，并且带测试。

到这一步，三本账已经有真实数据了。优化点子来自账上的不合理支出，常见的几类：

  • 显存账上的「惰性创建撞上峰值」——把通信域的建立挪到启动阶段（你已经做了）。这类优化的特征是不改变任何计算，只改变发生的时刻。
  • 通信账上的「组跨出了节点」——调整并行布局让某个维度的组收进节点内。代价要一起算（插课 G §13 算过，收进节点内要付激活显存的代价）。
  • 时间账上的「在等别人」——异步模式的三个 switch 阶段就是这类支出的读数。
  • 形状多样性——阶段 ④ 的 pad_to_length 那一类，优化的是编译和调优开销，在 FLOPs 账上看不见。

做之前先读官方的现成结论，避免重复发明：docs/perf/ 下有七篇（perf_tuning.rst 覆盖生成调优、序列打包、批大小、Ulysses 序列并行、FSDP 预取和梯度同步；device_tuning.rst 给了 0.5B 到 671B 各档的硬件需求参考；best_practices.rst 是 Qwen3-235B 上 DAPO 的实践；另有 Nsight 和 torch profiler 的使用说明、verl_profiler_system.md 讲 profiler 体系怎么扩展）。docs/advance/ 下还有 25 篇，其中 determinism.md、rollout_trace.rst、one_step_off.md、fully_async.md 和这条路线最相关。

改动要带测试。测试的约定是按文件名后缀分，没有 pytest 标记：*_on_cpu.py 无卡可跑（仓库里有 163 个），其余默认当作需要 GPU，*_on_npu.py 是昇腾专用。你在插课 G §14 加的两个 gloo CPU 测试正好符合这个约定——用 gloo 后端在 CPU 上测分布式逻辑，是这个仓库里验证通信相关改动的标准做法。

要提到上游时，先读仓库根目录的 CLAUDE.md：它要求查重（已有 PR 就不要再开）、不接受纯粹的琐碎改动、并且 PR 描述里必须写明测试命令与结果、以及用了 AI 协助。

5. 故障现象 → 定位路径

这一节是第 2 节那张表的「按现象查」版本。每条的结构是：先做什么（最快排除伪装）→ 再做什么 → 常见归属。

现象定位路径
报 OOM ① 先看有没有分配统计量（Tried to allocate … reserved in total）。没有就不是张量显存问题，调 batch 全是白费——去查通信域建立和网卡资源。
② 有统计量：开 torch_memory profiler 看构成，分清是权重、激活还是碎片。
③ 注意 reserved 和 allocated 的差：差得多说明分配器攥着缓存不还，而通信库拿不到这部分。
卡住不动 ① 对所有 worker py-spy dump，找停的位置和别人不一样的那个 rank。
② 多数 rank 停在集合通信 = 它们在等缺席者，别去查它们。
③ 如果所有 rank 都停在同一处，查这个通信域是不是第一次被使用（惰性创建 + 建链失败）。
④ 全在 Python 逻辑里 = 看驱动层，可能在等数据。
比预期慢 ① 先看分阶段计时，不要看总时间。
② 用 topk_reduce_ratio_min_max 看是不是个别 rank 拖后腿——是的话查那个 rank 的硬件或数据分布，不要调全局参数。
③ 大家都慢：看 MFU。MFU 高 = 真在算，要从算子和精度下手；MFU 低 = 在等，查通信账和 switch 阶段。
④ 异步模式先看三个 switch 阶段的占比。
奖励不涨 / 学不动 ① 先量训推一致性（rollout_logprob_diff.py），这是最容易被忽略又最常见的原因。
② 再查数据平面：极小批次手工核对掩码和优势，特别注意同一 prompt 多采样的排列顺序。
③ 最后才怀疑算法配置：聚合方式、两个 KL 是否重复开、损失模式。
④ 顺序很重要——倒过来查会在算法上浪费很多时间。
某个参数设了没反应 按阶段 ② 的三步：查展平后的 yaml 有没有这个键 → 搜有没有读取方 → 搜有没有被运行时改写。
改了布局开关就启动失败 / 性能突变 ① use_remove_padding 是一组硬约束的中心。关掉它会报错的：Ulysses 序列并行、动态上下文并行、per-token 损失；会被静默关掉的：融合输出头（只打一行 warning，长序列下 logits 显存因此突然变大）。
② CP>1 时它必须为 True：per-token 损失在 CP>1 时由 Megatron-Bridge 自动开启，而它硬性要求 THD 布局，配 False 会直接 raise ValueError。报错信息自己给的两个选项是「用 THD」或「关掉 CP」。
③ 机制：BSHD 下 verl 不给 MoE router 传 padding mask，router 按含 pad 的 B×S 归一化辅助损失，而梯度按真实 token 数除——代码注释说这正是 CP>1 时 grad_norm 暴涨到 ~1e4 的原因。
④ 生效值会被 model 配置覆盖 engine 配置，所以两处都要设，只改一处会让人以为没生效。
偶发失败、重跑就好 ① 分清是资源竞争（显存、端口、网卡配额）还是真随机。
② 用确定性开关（VERL_FULL_DETERMINISM + 固定种子）看还能不能复现：不能复现 = 和随机性有关；仍然偶发 = 资源或时序。
③ 注意外部依赖：这个分支的 agent 环境要起 pod、调 k8s API，那边的超时和断连会表现成偶发（插课 A 已记过一个这样的 bug）。
恢复后指标跳变 ① 查数据加载器状态是否真的恢复了（epoch 边界上会被刻意跳过）。
② 查采样器是不是 StatefulDataLoader 配套的那个。
③ 查 checkpoint 是否完整——Megatron 侧看 ckpt_contents.json 在不在。

6. 依赖栈的版本现实

这一节单独列，因为版本错配会表现成千奇百怪的运行时错误，而真实的版本约束不在你第一眼会去看的那个文件里。

setup.py 不是真实依赖源。它是 fallback，而且已经落后：里面写 vllm>=0.18.0、sglang==0.5.8。真正生效的是 pyproject.toml——那里是 vllm==0.32.0、sglang==0.5.20、统一 torch==2.13.0（cu130）。查版本只认 pyproject.toml 和 uv.lock。

依赖是用一个办法解决「多后端互相冲突」的：一个 lock 文件，每个后端是一个 extra，互斥的后端声明成冲突组，于是一次解析就能把所有组合都算出来，运行时只装其中一个无冲突的组合。可选的后端组合：

extra是什么
fsdp / megatron / veomni / torchtitan四个训练后端。veomni 是 FSDP 引擎的子类，用的是同一套原生栈
vllm / sglang两个推理后端（trtllm 已接入但在依赖上被推迟）
cpu无 GPU 的开发和测试环境，见下一节
ciCI 叠加用

正常跑训练不需要手工安装：uv run --frozen --all-packages --extra megatron --extra vllm python3 -m verl.trainer.main_ppo ... 会按 lock 文件自己把环境准备好，Ray 的 worker 也指向同一个环境。manage_envs.py 管的是 lock 文件之外的事（重新生成 lock、并存多个环境、预热 Docker 缓存）。

Megatron 这条线依赖的外部组件比看起来多：megatron-core、megatron-bridge、transformer-engine、apex、deep-ep（MoE 分发）、flash-linear-attention（Qwen3.5 那个门控线性注意力的核）、megatron-energon、nvidia-modelopt。其中好几个是「不声明自己依赖」被装进来的（在依赖元数据里被显式清空），所以它们的间接依赖得由 verl 这边手工列出——这就是为什么 pyproject.toml 里有那么多解释性注释。升级其中任何一个之前先读那些注释，它们记录的是上一次踩过的坑。

两条互斥的线：CUDA 线要 vLLM 0.32.0，昇腾线（docker/ascend/）要的是另一个版本的 vllm-ascend。这两个版本不可能同时满足，所以 third_party/ 下只保留了一份。注意 docs/learning-mimo/arch/index.html#pins 那张版本钉子表记的是当时把十个外部依赖都 clone 进来的状态，现在 .gitmodules 里只剩 mimoagent-osr 和 uni_agent 两个（commit 947133c6 做的精简），表里的版本号还可以当参考，但别指望能在本地找到对应目录。另外 megatron-bridge 现在是 0.6.2，那张表里写的 0.5.0 已经旧了。

7. 没有卡的时候能做什么

这一节很实际：路线里相当一部分是无卡可做的，不必等机器空出来。

能做怎么做
163 个 CPU 测试cpu extra 里带了纯 CPU 版的 megatron-core（没有 TE 和 apex 也能 import，有纯 torch 的兜底），所以连 verl 对 Megatron 的接线逻辑都能在无卡环境验证。跑法：pytest -s -x --asyncio-mode=auto 指向任意 *_on_cpu.py。
算法层全部tests/trainer/ppo/*_on_cpu.py 是自包含的。阶段 ⑤ 整个可以无卡完成。
配置层全部scripts/print_cfg.py 和 _generated_*.yaml 都不需要卡。阶段 ② 整个可以无卡完成。
数据平面的形状核对分词、掩码拼接、padding 这些都是 CPU 上的张量操作。
一致性自检pytest -s -x tests/special_sanity——里面是许可证头、docstring、API 文档、目录结构镜像、设备 API 用法等元检查，大部分也挂在 pre-commit 上。改代码前先跑一次，省掉来回。
分布式逻辑用 gloo 后端在 CPU 上测，你在插课 G §14 已经这么做过。
关于 CI：.github/workflows/ 下的作业都带 github.repository_owner == 'verl-project' 这个条件，所以在这个 fork 里它们不会执行。本地自测就是唯一的保障，不能指望推上去让 CI 跑。另外这个 fork 的 e2e_ppo_trainer.yml 已经被精简过，FSDP 的端到端作业不在了，Megatron 那几个变体还留着真实作业。

9. 这份路线的边界

把没做到的地方说清楚，免得当成结论用：

  • 没有实际运行验证。这份路线里的代码位置、配置键名、测试约定，来自对当前 checkout 的检索和阅读；use_v1 默认值、checkpoint_manager 的真实类型、CPU 测试数量这三项我单独核对过，其余的符号名和路径没有逐个跑起来确认。
  • 行号基本没写。有意的——符号名比行号稳。需要精确定位时用符号名去搜。
  • 阶段 ⑦ 最弱。Ray 和通信库的内部，这里给的是「该掌握哪几件事」和入口，不是讲解。那部分得带着具体故障去读，空读留不住。
  • 没有排时间。九个阶段的工作量很不均：② 和 ⑤ 可能各一两天，③ 和 ④ 要动手跑，⑦ 可以无限深入。按缺口的优先级走，不必按顺序走完。
  • 第 8 节的提交只读了标题和改动范围，没有逐个读 diff。要依赖其中某一条时，先自己看代码。
如果只能做三件事：阶段 ① 把测量配齐（尤其 torch_memory 的 OOM 自动快照，它直接补上插课 G 缺的证据）、阶段 ② 把配置查法固化成习惯、阶段 ⑥ 为自己的模型测一个训推一致性基线。这三件的共同点是都在建立判据——判据一旦有了，后面的问题从「猜」变成「测」。
