提问：agent 配置 yaml 是在哪个位置加载的？加载的 yaml 来源是什么？我现在要给我的 k8s 集群设置身份，需要创建命名空间、账号和权限。
补充（2026-10-23）：第二次提问澄清了真正关心的问题——pod 的启动配置从哪里来、namespace 有没有约束、kubeconfig 有什么要求，以及如何避免误删生产环境的其他 pod。这部分写在 §9–§16；§0–§8 保留原样，其中的 RBAC 文件和 kubeconfig 生成步骤仍然适用。

0. 结论先行

  1. agent 配置 yaml 有两个入口，都是用 yaml.safe_load 直接读的，不展开 ${VAR} 环境变量：
    • General：config/agent/general/s3k.yaml。路径写在 recipes/general/config/general_agent_loop.yaml 的 mimoagent_config_path 里，每条轨迹读两次：GeneralAgentLoop.__init__ 一次，DatasetEnvActor.__init__ 一次。
    • Code：config/agent/code/mini-*.yaml 四个文件。启动时被复制到 $RUN_DIR/harness.XXXXXX/，训练实际读的是副本；每个 session 在 runner 里按混合策略选一个、读一次。
  2. k8s 身份由三个参数决定：kubeconfig（谁、连哪个集群）、namespace（在哪个命名空间建 pod）、Role（能做什么）。代码需要的权限很少：pods 的 create/get/delete，加上 pods/exec。
  3. 两条路径传 namespace 的方式不一样：General 的启动脚本把 K8S_NAMESPACE 传进了 Ray；Code 的启动脚本没有传，runner 里拿不到这个变量时 pod 会建到 default 命名空间。用专用命名空间时，Code 需要把 namespace 直接写进 yaml（§6）。
  4. 可直接使用的文件放在 docs/learning-mimo/k8s-identity/：mimo-rollout-rbac.yaml（命名空间、账号、权限、令牌）和 make-kubeconfig.sh（生成 kubeconfig）。这两个文件只做过语法检查，还没有在真实集群上执行过。

1. General：agent yaml 从哪来、在哪读

一共三层配置，逐层指向下一个文件：

recipes/general/config/general.yaml                     ← main_ppo 的 --config-name=general
  actor_rollout_ref.rollout.agent.agent_loop_config_path: recipes/general/config/general_agent_loop.yaml
                                ↓  AgentLoopWorker.__init__ 读这个"登记表"（第二课 ②）
recipes/general/config/general_agent_loop.yaml

    _target_: recipes.general.agent_loop.GeneralAgentLoop
    mimoagent_config_path: config/agent/general/s3k.yaml   ← agent 配置 yaml 的路径

config/agent/general/s3k.yaml                           ← 真正的 agent 配置（agent: / environment:）

实际读取发生在两个地方：

recipes/general/agent_loop.py GeneralAgentLoop.__init__ 
self.mimoagent_config_path = self._resolve_config_path(mimoagent_config_path)   # 相对路径 → 绝对路径
self.mimoagent_config = load_mimoagent_config(self.mimoagent_config_path)       # 第一次读：取 agent: 块组装 harness
recipes/general/env_actor.py DatasetEnvActor.__init__

# load_mimoagent_config = open + yaml.safe_load + 两项校验（不允许子 agent 工具；工具列表不能为空）

相对路径怎么解析：_resolve_config_path 调用 verl/utils/import_utils.py 的 resolve_config_path，顺序是：绝对路径直接用 → 相对当前工作目录 → 相对 verl 项目根目录。run_general.sh 启动前会 cd "${GA_TASK_ROOT}"，所以当前目录下找不到 config/agent/general/s3k.yaml，最终落到第三条，解析成仓库里的那个文件。

两个实用的推论
  • 想换一份 agent 配置：改 general_agent_loop.yaml 里的 mimoagent_config_path，写成绝对路径最稳妥。
  • 训练中途改 s3k.yaml 会生效：每条轨迹都会 new 一个 GeneralAgentLoop 和一个 DatasetEnvActor，各自重新读文件。改动会从之后开始的新轨迹起生效，同一个训练步内可能出现新旧配置混用的情况。修改 environment 块（比如 namespace）最好在训练开始前完成。

3. 身份相关的三个参数各从哪里取

结合插课 C §14 的读取链路，三个参数的来源（同一行内越靠左优先级越高）：

参数决定什么来源与优先级
kubeconfig用什么身份、连哪个集群数据行 instance.routing.kubeconfig → yaml environment.kubeconfig → 环境变量 KUBECONFIG（General 的 env_actor 会显式补上；Code 靠客户端库自己查找）→ ~/.kube/config → 集群内服务账号
namespacepod 建在哪个命名空间yaml environment.namespace → 环境变量 K8S_NAMESPACE → default
⚠ kubeconfig 里 context 设置的 namespace 不起作用：代码每次调用都显式传 namespace=self.config.namespace
权限能做哪些操作集群上绑定到 kubeconfig 身份的 Role/ClusterRole

环境变量要在创建 pod 的那个进程里可见：General 是 DatasetEnvActor，Code 是 runner 的 Ray task。它们都由 Ray 启动，能看到的环境变量只有两类：runtime_env.env_vars 里显式传入的，以及当初在这台机器上执行 ray start 时 shell 里已有的。你在提交训练的终端里 export 的变量，如果没有经过 runtime_env 传进去，远端节点上是看不到的。

启动脚本传进 Ray 的 k8s 相关变量
recipes/general/run_general.shKUBECONFIG（必填，脚本开头检查）、K8S_NAMESPACE（默认 default）、DOCKER_REGISTRY，以及不生效的 K8S_TOLERATION_* 等（插课 C §14.5）
recipes/code/run_train.sh只有 KUBECONFIG（可以为空）。没有 K8S_NAMESPACE

4. 创建命名空间、账号和权限

完整清单在 docs/learning-mimo/k8s-identity/mimo-rollout-rbac.yaml，命名空间叫 mimo-rl，账号叫 mimo-rollout，换名字时全文替换即可。下面逐个说明为什么这样写。

4.1 Namespace

apiVersion: v1
kind: Namespace
metadata:
  name: mimo-rl
  labels:
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/warn: baseline

单独建一个命名空间有三个好处：权限可以只授予这一个命名空间；可以用 ResourceQuota 限制总资源；出问题时可以整个命名空间一起清理。

两个 label 是 k8s 内置的 Pod 安全准入（Pod Security Admission）级别，有三档：

  • privileged：不限制。
  • baseline：禁止特权容器、hostNetwork、额外的 Linux capability 等明显危险的配置，但允许以 root 运行。
  • restricted：还要求必须以非 root 运行、丢弃所有 capability 等。

选 baseline 是因为任务镜像默认以 root 运行，General 的权限隔离步骤还要执行 useradd、写 /etc/sudoers.d（插课 A），restricted 会直接拒绝这些 pod。而代码生成的 pod 定义里 hostNetwork: false、没有特权容器、各环境配置的 capabilities 都是空列表，满足 baseline。如果以后哪个环境给 pod 加了 capability，比如调试需要 SYS_PTRACE，要先确认 baseline 是否允许，否则 pod 会被准入控制拒绝，表现为创建时返回 403。

4.2 ServiceAccount：这是"控制器"的身份，不是 pod 的身份

apiVersion: v1
kind: ServiceAccount
metadata: {name: mimo-rollout, namespace: mimo-rl}
automountServiceAccountToken: false

这个账号是给训练集群里的 env_actor / runner 调用 k8s API 用的。任务 pod 本身不使用它：代码生成的 pod 定义里没有 serviceAccountName，并且设置了 automountServiceAccountToken: false，pod 里拿不到任何 k8s 凭据。账号上也设了 automountServiceAccountToken: false，即使以后有人误用它启动 pod，令牌也不会被挂载进去。

4.3 Role：按代码实际调用推出的最小权限

rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["create", "get", "delete"]        # 创建 pod；轮询就绪/确认删除；删除
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["list", "deletecollection"]       # 可选：按标签批量清理残留 pod
- apiGroups: [""]
  resources: ["pods/exec"]
  verbs: ["create", "get"]                  # 执行命令、传文件、打分都靠它

每条权限对应插课 C §2 的接口表：

权限代码中的调用缺了会怎样
pods: createcreate_namespaced_pod每条轨迹 setup 失败，奖励全部 -999
pods: getread_namespaced_pod（就绪轮询、删除确认）永远等不到就绪；删除时无法确认
pods: deletedelete_namespaced_podpod 全部泄漏，直到 namespace 配额耗尽
pods: list, deletecollection训练路径不用；手动 kubectl delete pods -l exp=... 清理时要用只影响清理；去掉它们权限更小，清理交给管理员做
pods/exec: create, getconnect_get_namespaced_pod_exec（WebSocket）pod 能建出来，但第一个工具调用就失败

为什么 pods/exec 要同时给 create 和 get？Python 客户端用的是 WebSocket，发起的是 HTTP GET 请求。较早版本的 API server 按 get 鉴权；较新版本出于安全考虑，对 WebSocket 方式的 exec 也要求 create（和 kubectl 早期用的 SPDY 方式一致）。不确定集群版本时两个都给，不会多出实际权限。

用的是 Role（命名空间级）而不是 ClusterRole（集群级），所以这个身份在 mimo-rl 之外什么也做不了。

4.4 RoleBinding 和令牌 Secret

kind: RoleBinding        # 把 Role 授予 mimo-rollout 账号
...
kind: Secret
metadata:
  name: mimo-rollout-token
  annotations: {kubernetes.io/service-account.name: mimo-rollout}
type: kubernetes.io/service-account-token     # 由 k8s 自动填入一个长期有效的令牌

令牌有两种获取方式，这里选择长期令牌是有意为之：

kubectl create token（有时效的令牌）service-account-token 类型的 Secret（长期令牌）
有效期有上限，由 API server 配置决定，经常是几小时到一天不过期，直到删除这个 Secret
对训练的影响一次训练要跑好几天，令牌过期的那一刻，所有创建 pod、执行命令的操作同时失败没有这个问题
安全性泄漏后影响时间有限泄漏后一直有效，需要手动吊销（删除 Secret）

因为训练进程不会自动刷新令牌，所以选长期令牌，再通过"权限只限一个命名空间"和"文件权限 600"控制风险。

5. 生成 kubeconfig 并验证

5.1 生成

脚本做的事：等待 k8s 往 Secret 里填好令牌 → 取出令牌和集群 CA 证书 → 用 kubectl config set-cluster / set-credentials / set-context 写出一个独立的 kubeconfig（证书内嵌在文件里）→ chmod 600。

6. 接入训练：两条路径分别怎么配

先把 kubeconfig 放到所有 Ray 节点都能读到的共享路径上。env_actor 和 runner 可能被调度到任何一个节点，recipes/code/cluster_precheck.py 的说明里专门提到过这类问题："Shared-storage visibility is per-node"。

6.1 General

# scripts/general/general.env.example 对应的变量
export KUBECONFIG=/shared/path/mimo-rollout.kubeconfig
export K8S_NAMESPACE=mimo-rl          # run_general.sh 会把它传进 Ray

这条路径到这里就配好了。如果更希望写死在配置里，也可以在 config/agent/general/s3k.yaml 的 environment: 块加 namespace: mimo-rl，它的优先级高于环境变量。

6.2 Code

export KUBECONFIG=/shared/path/mimo-rollout.kubeconfig   # run_train.sh 会传进 Ray

namespace 需要额外处理，因为 run_train.sh 不传 K8S_NAMESPACE。二选一：

  • 推荐：写进 yaml。启动前，在 config/agent/code/ 下四个 mini-*.yaml 的 environment: 块里各加一行 namespace: mimo-rl。namespace 是配置类认识的字段，不会被过滤掉；train.sh 复制副本时也只改 model_kwargs，不影响这一行。
  • 或者：在每个 Ray 节点执行 ray start 之前就 export K8S_NAMESPACE=mimo-rl，让 Ray worker 从启动环境里继承它。这种方式依赖集群的启动方式，容易遗漏某个节点。
如果什么都不做：Code 的 pod 会尝试建在 default 命名空间。用本页的 kubeconfig 时，这个身份在 default 里没有权限，每个 session 的 pod 创建都会返回 403，表现为大量 session 失败。反过来，如果用的是集群管理员 kubeconfig，pod 会悄悄建进 default，不受 mimo-rl 的配额和安全策略约束。

6.3 私有镜像仓库

如果任务镜像在私有仓库，需要先在 mimo-rl 里创建拉取凭据，再在 yaml 的 environment: 块里引用它（不要依赖 K8S_IMAGE_PULL_SECRET 环境变量，它没有被任何代码读取，见插课 C §14.5）：

kubectl -n mimo-rl create secret docker-registry regcred \
  --docker-server=registry.example.com --docker-username=... --docker-password=...
# s3k.yaml / mini-*.yaml 的 environment: 块
environment:
  namespace: mimo-rl
  image_pull_secrets: [regcred]
  # 需要调度到带污点的节点时（同样不要依赖 K8S_TOLERATION_* 环境变量）：
  # tolerations:
  #   - {key: dedicated, operator: Equal, value: my-pool, effect: NoSchedule}
  # node_selector: {node-pool: my-pool}

这里的 regcred 是 pod 拉镜像时由 kubelet 使用的，训练进程自己不读它，所以 Role 里不需要 secrets 的读权限。

7. 安全与容量的注意事项

  • kubeconfig 等于这个身份本身。它放在共享文件系统上，所有能读到这个文件的人都能在 mimo-rl 里创建 pod 并执行任意命令。保持 600 权限，必要时放在只有训练账户能读的目录。吊销方法：删除 mimo-rollout-token 这个 Secret，再重新 apply 生成新令牌。
  • exec 权限的含义。pods/exec 允许在命名空间里任何 pod 中执行命令。这也是把训练 pod 放进专用命名空间的原因：不要在 mimo-rl 里放其他业务的 pod。
  • 配额要按并发量估算。General 每个 pod 请求 main 2 核 8Gi + sidecar 0.5 核 1Gi（未单独配置时的默认值）。默认配置下一个训练步有 64 个 prompt × 8 = 512 条轨迹并发，开启 filter_groups 时还会补充更多 prompt。如果给 mimo-rl 设置 ResourceQuota，额度太小的话多出来的 pod 会创建失败（返回 403 forbidden: exceeded quota），这类失败会被记成 setup 失败、奖励 -999，不容易一眼看出是配额问题。
  • 网络出口。General 的打分在 sidecar 里调用 LLM 评审服务（GA_JUDGE_URL）。如果给命名空间加了默认拒绝出站流量的 NetworkPolicy，需要放行到评审服务和镜像仓库的访问，否则打分会失败。
  • API server 压力。每次工具调用都是一次 exec 请求（插课 C §12）。如果是共享集群，提前和集群管理员确认 API server 的限流设置，避免影响其他用户。

8. 思考题

Q1：为什么 kubeconfig 里 context 设置的 namespace 不起作用？

kubectl 会在命令没写 -n 时使用 context 里的 namespace，但这是 kubectl 自己的行为。mimoagent 用的是 Python 客户端，每个 API 调用都显式传入 namespace=self.config.namespace，而这个值来自 yaml 或 K8S_NAMESPACE，默认是 default，从不读取 kubeconfig 里的 context namespace。所以 make-kubeconfig.sh 虽然也写了 namespace，那只是方便你用 kubectl 手动排查，对训练没有影响。

Q2：能不能直接用集群管理员的 kubeconfig，省掉这些配置？

技术上可以，代码不区分身份。但有三个风险：一是 kubeconfig 放在共享文件系统上，等于把集群管理员权限分发到了每个 Ray 节点；二是 Code 路径漏配 namespace 时，pod 会悄悄建进 default，不受任何配额约束，出问题也不会报错；三是训练代码里的 bug（比如按标签批量删除时标签写错）可能误删其他业务的 pod。用专用身份，这些错误都会以"权限不足"的形式立刻暴露出来。

Q3：训练中途令牌被吊销（删除了 Secret），会发生什么？

之后所有 k8s 调用都会返回 401。正在 setup 的轨迹创建 pod 失败 → 奖励 -999；正在执行工具的轨迹，exec 通道打不开 → 先重试 3 次，然后作为传输错误终止（插课 A §8）。已经建好的 pod 也删不掉了，会一直残留到有人用新凭据清理。所以轮换令牌最好在两次训练之间进行。

9. 补充答疑：问题澄清

提问：你误解了我的意思，我的意思是 K8s 加载的 pod 启动的 yaml 配置是从哪里加载的，是否有约束 namespace，kube config 有什么要求，我现在有 k8s 集群，要给这个仓库的训练提前准备 kube config 身份和 namespace 规定，避免误删除生产的其他 pod。
结论
  1. pod 启动配置没有 YAML 文件。pod 定义由代码拼成字典：一部分写死在 _build_pod_body 里，另一部分来自 agent 配置 yaml 的 environment: 块（General 是 s3k.yaml，Code 是 mini-*.yaml），还有少数字段来自数据行（镜像、cwd）。§10
  2. 代码对 namespace 没有任何约束：不校验、不创建，取什么值就往哪里建。唯一能真正约束它的是集群上的 RBAC。§11
  3. kubeconfig 最关键的要求是：只含一个 context，指向训练专用的身份。代码读 kubeconfig 时用的是文件里的 current-context，不能另外指定；而且在没给 kubeconfig 时，会退回到节点上的 ~/.kube/config 或者 pod 自身的服务账号。§12
  4. 代码本身不会删别人的 pod：训练路径只按自己生成的精确 pod 名删除（mimoagent- + 16 位随机十六进制），不存在按标签批量删除。真正的风险在配置和人工操作：用了生产集群的管理员 kubeconfig、pod 落进共享的 default 命名空间、人工清理命令写得太宽。§13
  5. 防护方案：专用命名空间 + 只在该命名空间生效的 Role（§4 已给出，这是决定性的一层）→ 单 context 的专用 kubeconfig 并验证权限边界 → 可选的准入策略，限制这个身份只能删 mimoagent-* → 只在专用命名空间里、按名字前缀和存活时长清理残留 pod。§14，新增文件 k8s-identity/mimo-rollout-guardrails.yaml、k8s-identity/cleanup-stale-pods.sh。

11. namespace 有没有约束

代码层面没有任何约束。KubernetesEnvironmentConfig.namespace 就是一个字符串，代码既不检查它是否合法、是否在允许的列表里，也不会创建它。取值顺序见 §3：yaml environment.namespace → 环境变量 K8S_NAMESPACE → default。创建、查询、执行命令、删除，每个 API 调用都显式传入这个值。

情况结果
namespace 存在，身份有权限pod 正常建在这里
namespace 不存在创建返回 404。404 不在重试列表里（只重试 406/409/429/500/503），直接失败 → setup 失败 → 奖励 -999
身份在这个 namespace 没有权限创建返回 403，同样直接失败
namespace 有 Pod 安全准入级别（§4.1）pod 定义不符合时创建返回 403
namespace 有 ResourceQuota超出配额时创建返回 403（exceeded quota）
Code 路径什么都没配runner 里拿不到 K8S_NAMESPACE（§6.2），落到 default。如果 kubeconfig 是管理员身份，pod 会悄悄建进 default

所以"namespace 规定"只能在集群一侧落实：给训练身份的权限只覆盖专用命名空间。这样即使配置写错了 namespace，结果也是"创建被拒绝"，而不是"建到了不该去的地方"。

12. kubeconfig 有什么要求

代码读取 kubeconfig 的调用是（插课 C §3）：

config.load_kube_config(config_file=kubeconfig, client_configuration=self._kube_configuration)

注意它没有传 context= 参数，所以使用的是文件里的 current-context。由此推出以下要求：

要求原因
只含一个 context、一个集群、一个用户多 context 的文件（比如运维常用的那份，里面同时有测试和生产集群）用哪个，完全取决于 current-context 当时指向谁。有人用 kubectl config use-context 切换一下，训练就会连到另一个集群。§5 的 make-kubeconfig.sh 生成的就是单 context 文件
身份是训练专用的，不是个人或管理员账号权限边界只能靠这个身份的 RBAC 来保证（§11）
不要用冒号拼接多个文件（KUBECONFIG=a:b）客户端会合并多个文件，current-context 取第一个出现的值，结果不直观
所有 Ray 节点都能读到同一路径env_actor / runner 可能被调度到任何节点（§6）
API server 地址从 Ray 节点可达不能是 127.0.0.1 端口转发之类的地址（§5.1）
认证方式不依赖节点上的额外程序，推荐静态令牌云厂商常用的 exec 插件认证（如 aws eks get-token、gke-gcloud-auth-plugin）要求每个 Ray 节点都装有对应程序和凭据，缺一个节点就会在那台机器上失败
令牌在整个训练期间有效训练进程不会刷新令牌，中途过期会让所有 k8s 调用同时失败（§4.4）
context 里的 namespace 不能代替 K8S_NAMESPACE代码从不读它（§8 Q1）
最隐蔽的风险：没给 kubeconfig 时的回退行为。

_setup_kubernetes_client 在 config.kubeconfig 为空时：

default_kubeconfig = os.getenv("KUBECONFIG") or os.path.expanduser("~/.kube/config")
if kubeconfig is None and not os.path.exists(default_kubeconfig) and os.getenv("KUBERNETES_SERVICE_HOST"):
    config.load_incluster_config(...)        # ← 用当前进程所在 pod 的服务账号
else:
    config.load_kube_config(config_file=None, ...)   # ← 交给客户端库按默认位置查找
  • General 的 run_general.sh 强制要求设置 KUBECONFIG，env_actor 还会显式填进去，这条路径比较安全。
  • Code 的 run_train.sh 允许 KUBECONFIG 为空（KUBECONFIG="${KUBECONFIG:-}"），yaml 里也没有 kubeconfig 字段。这时用哪个身份，取决于 runner 落在的那台节点上的状态：如果节点上恰好有某个运维留下的 ~/.kube/config，就会用它——那可能是生产集群的管理员凭据；如果 Ray 本身跑在 k8s 里（比如用 KubeRay 部署在生产集群上），就会用 Ray pod 的服务账号，连到 Ray 所在的那个集群。

所以对 Code 路径：始终显式设置 KUBECONFIG，或者在四个 mini-*.yaml 的 environment: 块里写上 kubeconfig: /共享路径/mimo-rollout.kubeconfig。（KUBECONFIG 为空字符串时客户端库的具体行为，本机未安装该库，没有核实。）

13. 会不会误删生产 pod：全部删除路径

在整个仓库（含两个子模块，不含测试）里搜索所有删除 pod 的调用，只有两处：

删除路径删什么什么时候触发能否删到别人的 pod
KubernetesEnvironment.cleanup()
delete_namespaced_pod(name=self.pod_name, namespace=self.config.namespace)		只按精确的 pod 名删除，名字是本对象自己生成的 mimoagent- + 16 位随机十六进制General：GeneralAgentLoop.run() 的 finally；DatasetEnvActor.setup() 每次重试前和最终失败后
Code：mimoagent_runner._run_sync 的 finally		正常情况下不能（见下方"理论上的唯一例外"）
ray_batch._sweep_namespace
delete_collection_namespaced_pod(label_selector=...)		按标签批量删除，标签是 mimoagent-run=rb-<12位随机hex>，每次运行唯一只在 mimoagent 自己的分布式评测工具结束或被中断时。不在 verl 训练路径上不能：标签每次运行随机生成，生产 pod 不可能带这个标签

训练路径里没有 list 调用，没有按标签删除，没有按名字前缀删除。

理论上的唯一例外：名字冲突

_start_pod 是先生成 self.pod_name、再发创建请求的。如果命名空间里已经有一个同名的 pod，创建会返回 409，重试 10 次后抛出异常；setup 失败后会调用 cleanup()，而这时 self.pod_name 已经设置好了，于是会去删除那个早已存在的同名 pod。

16 位十六进制是 64 位随机数，和一个碰巧叫 mimoagent-xxxxxxxxxxxxxxxx 的生产 pod 撞名的概率可以忽略。这里列出来，是为了说明"代码只删自己的 pod"这个结论成立的前提：没有别的东西用 mimoagent- 前缀命名 pod。专用命名空间可以让这个前提自动成立。

既然代码本身是安全的，误删生产 pod 的风险就来自配置和人工操作：

风险怎么发生后果
kubeconfig 指向生产集群、带管理员权限多 context 文件被切换；Code 路径 KUBECONFIG 为空、落到节点上的 ~/.kube/config（§12）pod 建进生产集群；权限边界完全不存在
pod 落进共享命名空间Code 路径没配 namespace，落到 default（§11）训练 pod 和生产 pod 混在一起，后续人工清理容易误伤
人工清理命令写得太宽训练崩溃后 pod 残留（§10 两个事实），有人在共享命名空间执行 kubectl delete pods --all，或者用 -l app=... 这种通用标签这是最现实的误删场景
按标签清理时标签不可靠Code 的四个 mini-*.yaml 写着 labels: {}，显式传入空字典会覆盖默认的 app: mimoagent，所以 Code 的 pod 没有任何标签；General 的 pod 只有 exp=$EXP_NAME，默认值是很通用的 ga_train想按标签清理时，要么找不到，要么标签太通用可能匹配到别的东西

14. 防误删的分层方案

按"哪一层出错也不会删到生产 pod"来设计，越靠前的层越关键：

第 1 层  专用命名空间 + 命名空间级 Role         ← 决定性的一层：API 层面保证碰不到别的命名空间
第 2 层  单 context 的专用 kubeconfig，验证边界   ← 保证训练确实用的是第 1 层的身份
第 3 层  准入策略：只能创建/删除 mimoagent-*     ← 可选；必须和其他业务共用命名空间时的补救
第 4 层  给训练 pod 打上专属标签                 ← 让人工排查和清理有可靠的依据
第 5 层  只在专用命名空间里、按前缀和时长清理    ← 把人工操作的范围也限定住

14.1 第 1 层：专用命名空间 + Role

直接使用 §4 的 mimo-rollout-rbac.yaml。它为什么能防误删：

  • Role 是命名空间级的，RoleBinding 只在 mimo-rl 里。这个身份对其他任何命名空间都没有任何权限，删除生产命名空间里的 pod 会被 API server 直接拒绝（403），与代码怎么写无关。
  • 令牌只对这一个集群有效，kubeconfig 里也只有这一个集群，不存在"连错集群"。
  • mimo-rl 里约定不放任何其他业务，这样 Role 里的 list/deletecollection（用于批量清理）也就不会伤到别人。

14.2 第 2 层：验证权限边界

在 §5.2 的基础上，重点验证"不能做的事"。把 <prod-ns> 换成你生产业务实际所在的命名空间：

export KC=/shared/path/mimo-rollout.kubeconfig
kubectl --kubeconfig=$KC config get-contexts                        # 期望只有一行
kubectl --kubeconfig=$KC auth can-i delete pods -n <prod-ns>          # 期望 no
kubectl --kubeconfig=$KC auth can-i delete pods -n default           # 期望 no
kubectl --kubeconfig=$KC auth can-i create pods --subresource=exec -n <prod-ns>   # 期望 no
kubectl --kubeconfig=$KC auth can-i delete pods --all-namespaces     # 期望 no
kubectl --kubeconfig=$KC auth can-i --list -n mimo-rl                # 核对只有预期的几条权限

任何一条"期望 no"返回了 yes，说明这个身份还被别的 RoleBinding / ClusterRoleBinding 授予了权限（比如集群里有给所有服务账号授权的宽泛绑定），需要先查清楚再开训练。

14.3 第 3 层（可选）：准入策略限制 pod 名前缀

如果拿不到专用命名空间、只能和其他业务共用，RBAC 就无能为力了：RBAC 不能按标签或名字前缀授权（resourceNames 只能写精确名字，而 pod 名是随机生成的，而且它对 create 不生效）。这时可以用 k8s 1.30 起正式可用的 ValidatingAdmissionPolicy，文件是 k8s-identity/mimo-rollout-guardrails.yaml：

matchConstraints:   pods 的 CREATE / DELETE
matchConditions:    请求者 == system:serviceaccount:mimo-rl:mimo-rollout     ← 只约束训练身份
validations:
  (CREATE 且 object.metadata.name 以 mimoagent- 开头) 或
  (DELETE 且 oldObject.metadata.name 以 mimoagent- 开头)
validationActions: [Deny]

效果：即使这个身份在共享命名空间里有删除权限，也只能删名字以 mimoagent- 开头的 pod；删别的 pod 会被拒绝。管理员和其他业务不受影响。在共享命名空间里使用时，还应该从 Role 中去掉 list 和 deletecollection，不依赖准入策略对批量删除逐项生效。

验证方法（用管理员身份先建一个名字不带前缀的测试 pod）：

kubectl -n mimo-rl run guard-test --image=$IMG --restart=Never --command -- sleep 600   # 管理员身份
kubectl --kubeconfig=$KC -n mimo-rl delete pod guard-test     # 期望被拒绝，提示 mimoagent-*
kubectl -n mimo-rl delete pod guard-test                       # 管理员身份清理

这个策略不覆盖 exec（exec 在 k8s 里是 CONNECT 请求），exec 的范围仍然靠命名空间来限定。文件已通过 YAML 解析检查，还没有在真实集群上 apply 过；需要集群版本 ≥ 1.30。

14.4 第 4 层：给训练 pod 打上专属标签

标签不能防止删除，但能让人工排查和清理有可靠的依据。建议在 yaml 里显式写一个专属标签（下面只是建议，仓库里的文件我没有改）：

# config/agent/general/s3k.yaml 的 environment: 块
labels: {app: mimo-rollout}
#   General 的 env_actor 会合并成 {exp: $EXP_NAME, app: mimo-rollout}

# config/agent/code/mini-*.yaml 的 environment: 块（替换现在的 labels: {}）
labels: {app: mimo-rollout}

yaml 是直接读取的，不展开环境变量，所以这里只能写固定值；按单次运行区分 pod，General 可以依靠自动添加的 exp=$EXP_NAME，并给每次运行起一个不同的 EXP_NAME。

14.5 第 5 层：只在专用命名空间里、按前缀和时长清理

因为 pod 不会自动过期（§10），训练崩溃后需要清理。k8s-identity/cleanup-stale-pods.sh 把清理范围限定成三个条件同时满足：

  • 只看一个命名空间（NS，默认 mimo-rl），并且拒绝在 default 和 kube-system 上运行；
  • 名字以 mimoagent- 开头，且没有处于正在删除的状态；
  • 存活时间超过 MAX_AGE_HOURS（默认 12 小时，远大于单条轨迹的最长合法寿命）。
# 默认只列出，不删除
KC=/shared/path/mimo-rollout.kubeconfig NS=mimo-rl bash docs/learning-mimo/k8s-identity/cleanup-stale-pods.sh
# 确认列表无误后再真正删除
KC=... NS=mimo-rl APPLY=1 bash docs/learning-mimo/k8s-identity/cleanup-stale-pods.sh

我用一个假的 kubectl 在本地测过筛选逻辑：给出"20 小时前的 mimoagent-old、1 小时前的 mimoagent-new、100 小时前的 prod-api-7d9、正在删除的 mimoagent-terminating"四个 pod，脚本只选中了 mimoagent-old；NS=default 时直接拒绝并退出。还没有连真实集群运行过。

手动清理时也遵循同样的原则：永远带 -n mimo-rl，永远不要在共享命名空间里用 --all，按名字前缀或专属标签筛选，先 get 列出确认，再 delete。

7Ray 节点上没有会被误用的 ~/.kube/config（尤其是 Code 路径）逐节点检查，或确认第 6 条已显式指定
8私有镜像、节点污点写在 yaml 里，而不是 K8S_* 环境变量插课 C §14.5、本页 §6.3

16. 补充思考题

Q1：既然代码只按精确名字删除，为什么还说专用命名空间是"决定性的一层"？

"代码只删自己的 pod"是对当前代码的分析结论，它依赖代码不变、配置正确、没有人工操作。专用命名空间 + 命名空间级 Role 是 API server 强制执行的规则：不管代码以后怎么改、配置怎么写错、有人用这个 kubeconfig 手动敲了什么命令，删除其他命名空间的 pod 都会被拒绝。前者是"相信它不会做"，后者是"它做不到"。防误删要依赖后者。

Q2：为什么不在 pod 上加 activeDeadlineSeconds 让它自动过期，而要写清理脚本？

那需要改 mimoagent 的 _build_pod_body（或者真正把 pod_timeout 接上），属于改代码；而且到期后 pod 只是变成 Failed 状态，对象本身仍然留在 API server 里，还是需要删除。清理脚本不改代码、可以先预览，并且能把范围严格限定在专用命名空间和 mimoagent- 前缀上。如果之后决定改代码，两者可以并存：deadline 负责停掉进程、释放节点资源，脚本负责删除对象。

17. 答疑：RBAC 是什么；只建一个低权限用户够不够

提问：第一个问题是：集群的 RBAC 是什么？第二个问题是，我是不是给训练新建一个权限小的用户就可以了？
结论
  1. RBAC 是 k8s 决定"某个身份能不能做某件事"的规则系统，全称 Role-Based Access Control（基于角色的访问控制）。做法是：先定义一个"角色"，写清楚它能对哪些资源做哪些操作；再把这个角色"绑定"给某个身份，并且指定生效范围。
  2. 新建一个低权限身份是对的，而且是最核心的一步，但单靠它不够。还要满足三个条件：权限只在专用命名空间里生效；这个身份没有从别处继承额外权限；训练（以及事后人工清理）确实用的是这个身份。缺任何一条，"权限小"都可能形同虚设。

17.1 RBAC 是什么

先看 k8s 处理一个 API 请求的顺序，RBAC 处在中间一步：

请求（比如"删除 mimo-rl 命名空间里的 pod mimoagent-3f9a"）
  ① 认证：你是谁？        看请求带的令牌或证书 → 得出身份，如 system:serviceaccount:mimo-rl:mimo-rollout
  ② 授权：你能做这件事吗？ ← RBAC 在这里检查
  ③ 准入：这件事合规吗？  Pod 安全级别、ResourceQuota、§14.3 的准入策略在这里检查
  ④ 执行

RBAC 回答的问题可以写成一句话："某个身份，能不能对某个命名空间里的某种资源，执行某个操作"。它由四种对象表达，分成"定义权限"和"授予权限"两类：

只在一个命名空间内整个集群
定义权限（能做什么）RoleClusterRole
授予权限（给谁）RoleBindingClusterRoleBinding

以 mimo-rollout-rbac.yaml 为例，逐个对应：

Role  mimo-rollout（在 mimo-rl 命名空间里）          ← "能做什么"
  rules:
  - resources: [pods]       verbs: [create, get, delete]   对 pod：创建、查看、删除
  - resources: [pods/exec]  verbs: [create, get]           对 pod：执行命令

RoleBinding  mimo-rollout（在 mimo-rl 命名空间里）    ← "给谁、在哪生效"
  subjects: [ServiceAccount mimo-rl/mimo-rollout]          给这个账号
  roleRef:  Role mimo-rollout                               授予上面那组权限
  生效范围 = RoleBinding 所在的命名空间 = mimo-rl

理解 RBAC 有三个要点：

  • 只有"允许"，没有"禁止"。RBAC 的规则全部是允许规则，没写的就是不允许。所以不能写一条"禁止删除生产 pod"的规则；能做的只是"不授予"。一个身份的最终权限，是所有绑定到它的规则加在一起的结果。这也是 17.2 第二个条件的由来。
  • 生效范围由"绑定"决定，不由"角色"决定。同一个 ClusterRole，用 RoleBinding 绑定就只在那一个命名空间生效，用 ClusterRoleBinding 绑定就在全集群生效。防误删的关键就在于用 RoleBinding。
  • 只能按资源类型授权，不能按标签或名字前缀授权。可以授权"删除 pod"，但不能授权"只删除带某个标签的 pod"或"只删除以 mimoagent- 开头的 pod"。（resourceNames 只能写完整的名字，而训练的 pod 名是随机生成的。）这就是为什么必须靠命名空间来隔离，或者用 §14.3 的准入策略补充。

"用户"在 k8s 里是什么

k8s 里没有"用户"这种可以创建的对象。RBAC 里能绑定的身份有三种：

身份是什么怎么创建适合谁
User只是一个名字，来自认证结果（证书里的名字、OIDC 登录的用户名等）不能用 kubectl 创建；要靠签发证书或接入公司的登录系统人
Group同样来自认证结果，比如证书里的组织字段同上一类人
ServiceAccountk8s 里真实存在的对象，属于某个命名空间kubectl create serviceaccount；令牌由 k8s 签发程序

训练是程序在调用 API，所以"给训练新建一个用户"在 k8s 里的标准做法就是建一个 ServiceAccount，再给它签发令牌、做成 kubeconfig——也就是 §4、§5 已经做的事。

17.2 只建一个低权限用户够不够

方向完全正确，这是整个防误删方案的核心（§14 第 1 层）。但"权限小"要真正起作用，必须同时满足下面三个条件：

条件一：权限只在专用命名空间里，而且那里没有别的业务

"权限小"有两个维度：能做的操作少，和生效的范围小。训练必须有"删除 pod"和"在 pod 里执行命令"这两个权限，这两个操作本身无法再缩小。所以只能靠缩小范围：

做法能不能删到生产 pod
低权限账号 + ClusterRoleBinding（全集群生效）能。它可以删除任何命名空间里的任何 pod
低权限账号 + RoleBinding，但放在和生产共用的命名空间能。RBAC 不能按名字或标签区分，这个命名空间里的生产 pod 一样可以删，也一样可以进去执行命令
低权限账号 + RoleBinding + 专用命名空间不能。其他命名空间的请求在第 ② 步就被拒绝

所以准确的说法是：低权限账号 + 专用命名空间，两者缺一不可。如果实在拿不到专用命名空间，就需要 §14.3 的准入策略来补上"只能删 mimoagent-* "这条 RBAC 表达不了的规则。

条件二：这个账号没有从别处继承额外权限

因为 RBAC 的权限是叠加的，集群里如果已经有宽泛的绑定，新账号会自动获得那些权限。常见的情况是：

  • 某个 ClusterRoleBinding 绑定的对象是组 system:serviceaccounts（所有服务账号）或者 system:serviceaccounts:mimo-rl（这个命名空间里的所有服务账号）；
  • 某个绑定给了 system:authenticated（所有通过认证的身份）。

只要存在这样的绑定，你新建的账号就天然带上了那些权限，自己写的 Role 再小也没用。检查方法：

# 看这个账号最终的有效权限（这是所有绑定叠加后的结果）
kubectl --kubeconfig=$KC auth can-i --list -n mimo-rl
kubectl --kubeconfig=$KC auth can-i --list -n <prod-ns>          # 期望只有很少几条通用的只读权限

# 用管理员身份找出绑定给"所有服务账号"或"所有已认证身份"的规则
kubectl get clusterrolebindings,rolebindings -A -o wide | grep -E 'system:(serviceaccounts|authenticated)'

§14.2 列出的那组"期望 no"的检查，就是在验证这一条。

条件三：训练和人工清理确实用的是这个身份

建好了低权限账号，但程序实际用的是别的凭据，等于没建。这个仓库里有几处很容易"悄悄用错身份"：

  • Code 路径允许 KUBECONFIG 为空，这时会回退到 Ray 节点上的 ~/.kube/config，或者 Ray 所在 pod 的服务账号（§12）。必须显式设置。
  • kubeconfig 里有多个 context，用哪个取决于 current-context（§12）。必须是单 context 文件。
  • Code 路径的 namespace 默认是 default（§6.2、§11）。配对了身份但没配 namespace，结果是全部创建失败（这是好的失败方式，至少不会建错地方）。
  • 人工清理时用了管理员 kubeconfig。训练崩溃后，运维习惯性地用自己的管理员凭据去删残留 pod，这时 RBAC 的保护对他不起作用。建议清理也用这份训练 kubeconfig（§14.5 的脚本支持 KC= 参数），这样即使命令写错，也只会影响 mimo-rl。

小结

"给训练新建一个权限小的用户"
  = 建一个 ServiceAccount                               ← §4.2
  + 只用 RoleBinding 授予 pod 的增删查和 exec 权限          ← §4.3（条件一：范围）
  + 放在一个专用、没有其他业务的命名空间                     ← §4.1（条件一：范围）
  + 确认没有宽泛的绑定让它继承额外权限                       ← §14.2、本节（条件二）
  + 训练和人工清理都只用这一份单 context 的 kubeconfig        ← §5、§6、§12（条件三）

前三项写在 mimo-rollout-rbac.yaml 里，apply 一次就完成；后两项需要在你的集群和 Ray 节点上逐项确认。
