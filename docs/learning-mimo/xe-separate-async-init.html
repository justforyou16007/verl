1. 初始化分两段：__init__ 与 init()

先建立全局印象。SeparateAsync 本身代码不多，大部分工作在基类里做，子类只在几个"钩子"上插入自己的逻辑（模板方法模式）：

trainer_cls(config)                    ── 只读配置、检查、建 Python 对象，不碰 GPU
  PPOTrainerSeparateAsync.__init__
    ├ ① 五条前置检查                                          §2
    ├ ② super().__init__  → replay_buffer 等                 §3
    └ ③ 决定 _enable_hybrid_replicas，可选初始化切换状态      §4

trainer.init()                         ── 真正创建 Ray worker、加载模型、起推理服务
  PPOTrainer.init

2. __init__ 前半：五条前置检查

trainer_separate_async.py:56 
train_batch_size     = config.data.train_batch_size
ppo_mini_batch_size  = config.actor_rollout_ref.actor.ppo_mini_batch_size
parameter_sync_step  = config.trainer.v1.separate_async.parameter_sync_step   # 默认 4
assert train_batch_size == parameter_sync_step * ppo_mini_batch_size            # (a)
assert config.actor_rollout_ref.rollout.nnodes > 0                              # (b)
assert config.actor_rollout_ref.rollout.n_gpus_per_node > 0                     # (b)
assert config.actor_rollout_ref.rollout.checkpoint_engine.backend != "naive"    # (c)

    assert config.reward.reward_model.enable_resource_pool                      # (d)
检查为什么
(a) train_batch_size = parameter_sync_step × ppo_mini_batch_size 这个模式里，一个 step 不是"一大批数据做一次更新"，而是连续做 parameter_sync_step 次小更新，每次从 replay_buffer 取一个 mini-batch（基类 step()，trainer_base.py:810 的 for 循环）。做完这几次后才把新权重推给推理服务一次。等式保证"一次小更新 = 一个 mini-batch"，不会再在内部切分。
(b) rollout.nnodes / n_gpus_per_node > 0 推理要有自己的 GPU。在 sync 模式里这两个值可以是 0（推理借用训练的 GPU）；这里必须单独指定，否则独立推理池没机器可用。
(c) 权重同步不能用 naive naive 的意思是"推理引擎和训练在同一个进程、同一块 GPU 上，直接把权重交过去"（checkpoint_engine/base.py:518）。独立推理池在别的 GPU、甚至别的机器上，只能走 nccl / nixl / mooncake 这类跨进程通信。
(d) 奖励模型必须独立资源池 共用 GPU 的奖励模型需要推理"停下来让出显存"才能跑，而独立推理池从不暂停，所以只能给奖励模型单独的 GPU。

4. __init__ 后半：要不要在训练 GPU 上放推理副本

默认关掉的理由写在注释里：hybrid 副本如果不切换，在正常训练时一直睡着，只在 warmup / 验证时有用，却要付出引擎初始化、启动时多一次权重同步、显存预留的代价。

6. 插入点①：worker 换成 DetachActorWorker

基类先决定 actor 用哪个"角色"（trainer_base.py:1062）：

if not self._enable_hybrid_replicas:
    role = Role.Actor                       # 只训练，不带推理引擎
else:
    role = Role.ActorRolloutRef 或 Role.ActorRollout   # 训练 + 推理（+ ref）同进程
self.role_worker_mapping[role] = ray.remote(ActorRolloutRefWorker)
if role == Role.Actor and 需要 ref:
    self.role_worker_mapping[Role.RefPolicy] = ray.remote(ActorRolloutRefWorker)

然后子类把这些映射里的类统统替换（:120）：

super()._init_resource_pool_mgr()
if Role.Actor in mapping:            mapping[Role.Actor] = DetachActorWorker
                                     (有 RefPolicy 的话也换)
elif Role.ActorRolloutRef in mapping: mapping[Role.ActorRolloutRef] = DetachActorWorker
elif Role.ActorRollout in mapping:    mapping[Role.ActorRollout] = DetachActorWorker

为什么要换？ DetachActorWorker 继承 ActorRolloutRefWorker，只多了一个能力：把当前模型参数存一份到 CPU，之后再还原（save_model_to_cpu(n) / restore_model_from_cpu(n) / clear_cpu_model(n)，verl/experimental/separation/engine_workers.py:139）。

用途在 _compute_old_log_prob（:201）：一个 step 里做 4 次小更新，第 2、3、4 次时 actor 已经被前面的小更新改过了。Decoupled PPO 要求这 4 次用同一个 π_old 算 old_log_prob，所以：

local_trigger_step == 0：   当前权重就是 π_old → 存到 CPU 槽位 0 → 直接算
local_trigger_step == k≥1： 当前权重存到槽位 k → 还原槽位 0（π_old）→ 算
                            → 还原槽位 k（当前权重）→ 删掉槽位 k
如果开了 rollout_correction.bypass_mode，就不重算，直接用推理时记录的 logprob，也就用不到这个存取。

(1) 独立推理池

  • 没传 worker_group，所以 LLMServerManager 走 standalone 分支（llm_server.py:501 的 init_standalone()）：自己申请 rollout.nnodes × rollout.n_gpus_per_node 块新 GPU。
  • 副本数 = 推理 GPU 总数 ÷ (TP × DP × PP)。
  • start_rank：副本编号从 hybrid 副本数开始，避免两个管理器起出同名的 Ray actor。
  • 显存比例可以单独设：独立副本的 GPU 不用给训练留空间，可以设得更高。用 deepcopy 是为了不影响 hybrid 副本那份配置。
  • create() 最后还会建一个全局负载均衡器（standalone_server_manager.global_load_balancer），所有生成请求都经过它分发。

(3) 两个权重同步器

checkpoint_manager（基类建）standalone_checkpoint_manager（子类建）
目标hybrid 副本（同进程同 GPU）独立副本（别的 GPU / 机器）
backend强制 naive：直接交过去配置的 nccl / nixl / mooncake：建通信组广播
默认情况副本列表为空，等于没用真正干活的那个

非 naive 的 update_weights（checkpoint_engine/base.py:510）流程：中止进行中的请求并保存 → 释放 KV cache → 建通信组 → actor 发、推理收 → 恢复 KV cache → 继续刚才中止的请求。最后一步就是"partial rollout"：生成到一半的轨迹换了权重接着生成。

(4) 初始模式

  • 开了 hybrid：模式设为 ROLLOUT，并把 hybrid 副本的地址加进独立池的负载均衡器——从此负载均衡器同时向两种副本派请求。
  • 默认：模式固定为 TRAINER，所有 switch_to_rollout / switch_to_trainer / add/remove_replicas_* 一进来就 return，变成空操作。

9. 插入点③：on_init_end 推第一次权重

trainer_separate_async.py:238 
def on_init_end(self):
    self.standalone_checkpoint_manager.update_weights(self.global_steps)
    if self._enable_hybrid_replicas:
        self.checkpoint_manager.update_weights(self.global_steps)

推理服务启动时加载的是 model.path 的原始权重；如果刚才 _load_checkpoint 恢复了训练到一半的 actor，两边就不一致。这里把 actor 当前的权重推一次，并带上 global_steps 作为版本号——之后 replay_buffer 判断"数据有多旧"就靠这个版本号。

顺带：init 之后 main_ppo 拿到的 client

def get_llm_client(self):       # :227
    return self.standalone_server_manager.get_client(client_cls=FullyAsyncLLMServerClient)

TaskRunnerV1.init_agent_loop_manager 用这个 client 构造 agent loop 管理器。FullyAsyncLLMServerClient 的特点是：请求被权重同步中断后会自动续上，agent loop 感觉不到中断。client 连的是独立池的负载均衡器，所以开了 hybrid 时也能自动用上 hybrid 副本。

11. 小结与思考题

  • trainer_cls(config) 只做检查和建 Python 对象；GPU 上的东西全在 trainer.init() 里建。
  • SeparateAsync = 基类全部流程 + 三个钩子：换 worker 类（为了存/取 π_old）、额外起一个独立推理池和一个跨机权重同步器、启动后推一次权重。
  • _enable_hybrid_replicas 决定训练 GPU 上要不要放推理副本，默认不放；开了才有"闲时借 GPU 给推理"的切换逻辑。
  • 前置检查 (b)(c)(d) 都源于同一个事实：推理在别的 GPU 上、从不暂停；(a) 则保证一次小更新正好吃一个 mini-batch。
思考题 1：如果 train_batch_size=256、ppo_mini_batch_size=64，但 parameter_sync_step 保持默认 4，会怎样？换成 parameter_sync_step=1 呢？

256 = 4 × 64，检查通过：每个 step 做 4 次小更新，推一次权重。改成 1 则 256 ≠ 64，__init__ 直接 assert 失败；需要把 mini-batch 也改成 256，变成"一次更新一次同步"，此时 local_trigger_step 永远是 0，DetachActorWorker 的还原逻辑不会触发。

思考题 2：默认配置下 base 的 checkpoint_manager 还有用吗？

副本列表为空，sleep_replicas / update_weights 对它都不起作用；on_init_end 和 switch 方法也都会因为 _enable_hybrid_replicas=False 跳过它。它存在只是因为基类 _setup 对所有模式统一建。

思考题 3：为什么 standalone 副本的编号要从 hybrid 副本数开始？

两个 LLMServerManager 都会以 replica_rank 起名创建 Ray 命名 actor；如果都从 0 开始，开了 hybrid 时会撞名（llm_server.py:446 的注释）。

本篇只读代码得出，没有实际运行验证。下一步可以接着看运行期：on_step_begin / prepare_step / _wait_for_sampleable_and_switch / on_step_end（切换阈值如何自适应、何时推权重）。

12. 追问：standalone 这三行到底在干什么

提问：（选中 trainer_separate_async.py:167-169）standalone 这部分在干吗？

12.1 一句话

self.standalone_server_manager: LLMServerManager = LLMServerManager.create(
    config=standalone_config, start_rank=hybrid_num_replicas
)
这三行是"separate"这个名字的全部含义所在：在训练 GPU 之外的另一批 GPU 上，真正把推理服务进程拉起来——申请 GPU、起 M 个 SGLang/vLLM HTTP 服务、再建一个路由入口，让 agent loop 把生成请求发进去。
§8 里基类建的那个 self.llm_server_manager 默认是空的（create_empty，一个副本都没有）。所以默认配置下，全训练过程中唯一真正提供生成能力的就是这里创建的这一套。

12.2 三个参数

参数值为什么
configstandalone_config（deepcopy 来的）要改 gpu_memory_utilization：独立副本独占 GPU，不用给训练留显存，可以调得更高（rollout.standalone_gpu_memory_utilization）。深拷贝是为了不污染原 config——hybrid 副本和训练共享 GPU，必须用原来那个更保守的比例。

12.3 create() 的三步

verl/workers/rollout/llm_server.py:418 
@classmethod
@auto_await
async def create(cls, *args, **kwargs):
    instance = cls(*args, **kwargs)              # ① __init__：只存配置、选副本类
    await instance._initialize_llm_servers()     # ② 真正起服务（耗时在这里）

注意这是 classmethod + auto_await：构造过程里有大量异步等待（起进程、等 HTTP 端口就绪），不能写在 __init__ 里，所以用 create() 当工厂方法；auto_await 让同步代码也能像普通函数一样调用它。

① 里只做两件事：assert worker_group is not None or rollout.nnodes > 0（就是 §2 检查 (b) 的兜底），以及按 rollout.name 选副本类（get_rollout_replica_class，sglang / vllm / trtllm，开了 PD 分离则选 PD 版本）。

12.5 init_standalone：要 GPU、建 worker、起服务

verl/workers/rollout/replica.py:189

步做什么要点
①每个副本自己建一个 Ray 资源池（placement group）这就是"独立"的实现方式：不经过 trainer 的 resource_pool_manager（那个只圈了训练 GPU），而是直接向 Ray 申请新的 GPU bundle。max_colocate_count=2 允许同一块 GPU 上放两类进程（下面的 worker 和引擎自己的进程）。
②在这些 GPU 上建一组 CheckpointEngineWorker这组 worker 不是推理引擎本身，而是权重同步的接收端（12.7）。注释说明它们与引擎自己的进程共享同一块设备，所以 TPU 这种不能共享设备的平台上 use_gpu=False、不去占卡。
③launch_servers() 起 HTTP 服务后端各自实现（SGLang 版在 async_sglang_server.py:852）。

12.6 一个副本内部长什么样

以 SGLang 为例，launch_servers 的流程：

  1. 问每个 worker 自己在哪个节点、拿到了哪些 CUDA_VISIBLE_DEVICES。
  2. 按节点分组，每个节点起一个 server actor，名字 sglang_server_{replica_rank}_{node_rank}，用 NodeAffinitySchedulingStrategy(soft=False) 硬绑到那个节点，并把该节点的 GPU 列表传进去。
  3. max_concurrency = max_num_seqs + 控制调用预留：多出来的请求在 Ray 层排队，而不是堆进引擎内部。
  4. 多节点副本（如 TP=16 跨两台 8 卡机）先从 node_rank 0 取 master 地址，再并行 launch_server。
  5. 最后把 node_rank 0 的 server 记作这个副本的代表：_server_handle / _server_address。后续 abort_all_requests、resume_generation 这些控制调用也只发给它（SGLang 只有 0 号服务响应控制 RPC）。
这就回答了思考题 3：replica_rank 直接进 Ray 命名 actor 的名字（sglang_server_0_0、worker group 的 name_prefix、资源池名 rollout_pool_0）。Ray 的命名 actor 全局唯一，开了 hybrid 时两套副本都从 0 编号就会撞名——所以 start_rank=hybrid_num_replicas 把独立副本的编号接在 hybrid 副本之后。

回到管理器：拿到所有副本的 _server_address / _server_handle 后，_init_global_load_balancer 用这些地址建路由 actor（global_load_balancer）。get_llm_client() 返回的 client 只持有这个路由的句柄，所以 agent loop 不需要知道有几个副本、在哪台机器上。

12.7 为什么 get_replicas() 对权重同步重要

紧接着的 standalone_checkpoint_manager 传的是 self.standalone_server_manager.get_replicas()，也就是上面这些 RolloutReplica 对象。权重同步时（checkpoint_engine/base.py:510）：

workers = []
for replica in self.replicas:
    workers.extend(replica.workers)        # ← 12.5 步②建的 CheckpointEngineWorker
rollout = RayWorkerGroup(worker_handles=workers, ...)   # 临时拼一个 worker group
... build_process_group(rollout) → actor 发 / rollout 收

也就是说：HTTP 服务负责对外生成，replica.workers 负责对内收权重，两者在同一批 GPU 上。这也解释了 §2 检查 (c) 为什么禁止 naive——naive 直接让 actor 自己换权重（backend == "naive" 时 update_weights 第一行就 return 了），根本不走这个跨进程通信组。
