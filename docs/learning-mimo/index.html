说明

仓库：/home/liu/projects/verl，分支 mimo-oss（基于 verl 0.9.0.dev @ 2781c1e4，MiMo 的改动集中在 commit e2b9fc03）。

  • 采用"总—分"结构：本页记录全景、进度和每课要点；细节在各分篇里，每篇对应一课或一次问答。
  • 学习方式是交互式的，每篇里用紫色框标出当时的提问。
  • 代码位置写成 文件:行号，行号以写笔记时的代码为准，代码更新后可能会偏移。
  • 主线环境是 General（s3k），因为它直接在 verl 的 AgentLoop 里驱动 mimoagent，和"main_ppo → agent loop → harness → actor 更新"这条学习路线最贴合。

学习路线

前面各课是「已经学过什么」，学习路线 是「接下来按什么顺序学、怎么验证学会了」。它按能力组织而不是按模块目录组织，因为目标是三条能力——定位问题、算出优化空间、分清栈的边界。

  • 分层与「错误伪装表」：七层各自会把下层的错误改头换面成什么样，以及看穿它的判据。这是插课 G 那次排查（现象离原因隔 30 秒和四五层）的方法论泛化。
  • 三本账：显存、通信、时间。优化点子来自账上的不合理支出，不是灵感；三本账的优化手段互相冲突，所以必须分开记。
  • 九个阶段：先能看见（测量）→ 再能查（配置）→ 再懂数据 → 再有对照（FSDP）→ 再懂算法 → 再懂训推一致 → 再懂底座 → 再能长跑 → 最后做优化。每阶段都写了要建立的判断力、读什么、做什么能验证。
  • 按现象查的定位路径：OOM、卡死、变慢、学不动、参数无效、偶发失败、恢复后跳变，每条给「先做什么最快排除伪装」。

路线里几个和已有笔记直接接得上的发现：torch_memory profiler 会在 OOM 瞬间自动 dump 快照且刻意不做设备同步（正好补上插课 G §12 缺的那块证据）；scripts/rollout_logprob_diff.py 是现成的训推一致性探针、带阈值门禁；DataProto 已不在默认路径上（trainer.use_v1: true）；verl/checkpoint_engine/ 其实是权重同步、不是磁盘 checkpoint，而 trainer 里的 self.checkpoint_manager 属于前者。

各课要点

第一课：main_ppo → 训练主循环

  • 配置分层：verl 默认配置 < general.yaml < 命令行参数。
  • v1 trainer 里，生成和训练通过 TransferQueue 解耦：trainer 只登记 prompt、发出生成请求，然后由 replay_buffer 轮询状态取回结果。
  • hybrid engine：训练和推理共用 GPU，用睡眠/唤醒轮流占用显存。
  • _step_once：sample → old_log_prob → advantage → update_actor。

问答：白盒 vs 黑盒 harness

  • 黑盒/白盒指的是 agent 循环由谁控制，与模型本身无关。
  • 5 个环境的训练都用白盒；cc-agent 是用 Python 仿写的 Claude Code，不是真正的 Claude Code。
  • 黑盒代码在 mimoagent 的 agents/blackbox/ 和 uni-agent 的 blackbox_recipes/。
  • 黑盒 RL 的难点：网关要把文本请求还原成 token，靠前缀哈希判断能否续接到已有的链上。

第二课：Agent Loop 初始化

  • 四层：manager → worker（读登记表）→ 每条轨迹一个 GeneralAgentLoop → run() 里开 pod、组装 harness。
  • "桥"的设计：mimoagent 循环原样运行，只替换两点——模型换成 _VerlRolloutModel，执行工具转发给 env_actor。
  • pod 放在单独的 DatasetEnvActor 进程：工具必须和 pod 客户端同进程，并且卡死时可以直接 kill。
  • 失败时返回格式完整的 _failure_output（reward=-999），避免连累整个 batch。
  • ⚠ 勘误：General 实际运行的是 DefaultAgent 加 Claude Code 命名的工具；yaml 里的 type: cc-agent 和 antihack 不生效。

第三课（上）：线程与事件循环

  • 异步切到同步用 run_in_executor，同步切回异步用 run_coroutine_threadsafe。
  • 不死锁的三个条件：query 不在 L 上调用；T 等待时 L 空闲；agent.run 用专用线程池。
  • T 和 L 严格轮流执行，所以共享数据不用加锁。
  • 线程杀不掉，超时后靠停止开关加 kill env_actor，让线程自己退出（协作式取消）。
  • generate 在 L 上 await 是挂起而不是占用，真正阻塞等待的是 T。

第三课（下）：harness 执行与 token 记账

  • 模型生成的 token 原样保存，绝不重新渲染；只把新增的环境消息渲染成 token（token 进、token 出）。
  • TokenTrace：prompt 只记一次；之后生成部分 mask=1，环境注入部分 mask=0，logprob 填 0.0。
  • select_delta_messages 用游标取新增消息并丢掉 assistant；多条 tool 消息要一次性渲染。
  • 锚点技巧：在新消息前加一条空 user 消息一起渲染，再切掉锚点，补上 turn_separator。
  • 预算在消息边界检查，超了就抛 ResponseBudgetExhausted，正常结束。
  • 工具调用错误 = FormatError（格式不对），每轮一个布尔值；General 没有生成 token 级的 tool_call_error_mask，Code 和 arvo 有。

插课 A：Ray 环境进程与 k8s pod

  • agent 循环不在 pod 里；每条轨迹 = 1 个 DatasetEnvActor（只占 0.125 CPU）+ 1 个 pod。
  • actor 与 pod 之间没有直接网络连接，全部经过 API server：HTTPS 管理 pod 生命周期，exec（WebSocket）执行命令、用 tar 传文件。
  • pod = main（工作区，模型的工具都发到这里）+ sidecar（MCP 服务、数据库、verifier），共享网络，文件物理隔离；答案在打分时才上传到 sidecar。
  • 多容器 exec 必须指定目标容器：用代理加线程局部变量实现，保证并行的工具调用各自发到正确的容器。
  • ⚠ 疑似 bug：General/arvo 在 rollout 中途 pod 断连时，error_category 带了错误信息后缀，精确匹配不上，奖励记成 0 而不是 -999。

第四课：从奖励到 actor 更新

  • 奖励放在 response 最后一个位置（rm_scores），GRPO 再按行求和还原成标量。
  • GRPO（不除以标准差）：优势 = 奖励 − 组均值，复制到这一行每个生成 token 上；-999 先替换成有效均值再把自身优势置 0，其他行不受影响。
  • prompt-mean：每个 token 权重 1/(P×T_u)，每个 prompt 总权重相同；权重在整个 batch 上算好，所以 batch 不能再切成多个 mini-batch 分别优化。
  • sync + 单次优化 ⇒ ratio≈1，截断不会触发，PPO 退化为带组内基线的策略梯度。
  • token 级通道（工具调用错误、重复、deep_failure_mask、adv_signed 保持总量不变）在 General 均未开启。
  • ⚠ 发现：General 配置的 algorithm.length_penalty 没有任何代码读取，实际不生效。

插课 B：Code 环境与 uni-agent 网关

  • 通过 agent.agent_loop_manager_class 把 verl 的 rollout 管理器整个换掉；trainer 侧（第四课）完全不变。
  • mimoagent 一个字没改：原装模型对象发 HTTP，发给 session 专属 URL，网关假装是 OpenAI 服务。
  • 网关靠消息前缀哈希链判断能否增量续接；匹配失败就开新链，所以一个 session 可能产出多条轨迹（默认只留最长那条）。
  • 网关额外记了 generation_spans（每轮生成的 token 区间）——General 缺的正是这个，所以 Code 能做 token 级工具调用惩罚。
  • 奖励由 runner HTTP POST 回网关，在网关和轨迹会合。
  • 四种 whitebox harness 混训，step-hash 模式保证同组同 harness、跨步轮换。

插课 C：仓库如何调用 k8s API

  • 官方 Python 客户端（kubernetes==36.0.3），只操作 Pod、只用 CoreV1Api；全部集中在 mimoagent 的 environments/kubernetes.py。
  • 训练路径只用 4 个接口：create / read / delete pod，以及 pods/exec（WebSocket）。
  • 每个环境一份独立的 Configuration/ApiClient，避免多集群互相覆盖、删错集群。
  • 执行命令、传文件进出都建在 exec 上：timeout N bash -lc、读线程 + 截止时间、head -c 绕过无法关闭标准输入、≥32MB 分块 + dd seek 幂等 + sha256 校验。
  • 删除以查询返回 404 为准；4 小时连接上限用 detached exec 绕过（只有黑盒 harness 用）。
  • 没有 pod 的 YAML 文件：pod 定义由 agent 配置 yaml 的 environment: 块 → 配置类 → _build_pod_body 拼成字典；kubeconfig 由客户端库读取。
  • ⚠ 发现：General 的 K8S_TOLERATION_* / K8S_NODE_LABEL_* / K8S_IMAGE_PULL_SECRET 没有代码读取，设置了也不生效。

插课 D：agent 配置来源与 k8s 身份

  • General：general_agent_loop.yaml 的 mimoagent_config_path → s3k.yaml，每条轨迹读两次（agent loop 与 env_actor）。
  • Code：MIMOAGENT_HARNESS_SPEC → 启动时复制到 $RUN_DIR/harness.* → runner 每个 session 读选中的 mini-*.yaml 副本。
  • 身份 = kubeconfig + namespace + Role；kubeconfig 里 context 的 namespace 不起作用。
  • 最小权限：pods create/get/delete + pods/exec create/get；命名空间用 PSA baseline；长期令牌 Secret。可用文件在 k8s-identity/（未在真实集群执行过）。
  • ⚠ Code 的 run_train.sh 不传 K8S_NAMESPACE，需把 namespace 写进 mini-*.yaml。
  • pod 启动配置没有 YAML 文件：代码写死部分 + agent yaml 的 environment: + 数据行；代码对 namespace 无约束，只能靠 RBAC。
  • 训练路径只按自己生成的精确 pod 名删除；误删风险来自配置和人工清理。pod_timeout 未使用、无 ownerReferences，残留 pod 不会自动过期；Code 的 pod 没有标签。
  • RBAC = "角色定义能做什么 + 绑定决定给谁、在哪生效"，只有允许没有禁止、权限叠加、不能按名字/标签授权；所以"低权限账号"必须配合专用命名空间，并排查宽泛绑定。
  • 防误删：专用命名空间 + Role（决定性）→ 单 context kubeconfig 并验证边界 → 可选准入策略限定 mimoagent-* → 限定范围的清理脚本（默认只预览）。

插课 E：SeparateAsync 的初始化

  • trainer.v1.trainer_mode 查 TRAINER_REGISTRY 选类，默认 sync → PPOTrainerSync。
  • trainer_cls(config) 只做检查和建对象；GPU 上的东西在 init() = _setup() + on_init_end()。
  • 前置检查：train_batch_size = parameter_sync_step × mini_batch；推理要有自己的 GPU；权重同步不能用 naive；奖励模型要独立池。
  • _enable_hybrid_replicas（= enable_switch，默认 False）决定训练 GPU 上放不放推理副本。
  • 三个钩子：worker 换成 DetachActorWorker（存/取 π_old）；额外起独立推理池 + nccl 等权重同步器；启动后推一次权重。
  • §12：LLMServerManager.create 自己向 Ray 申请新 GPU → 每副本一组 CheckpointEngineWorker（收权重）+ 每节点一个 server actor（对外生成）→ 路由；默认下它是唯一真正提供生成的那套。

插课 F：Megatron / MindSpeed 与五种分片

  • RayClassWithInitArgs 只是「配方」；role_worker_mapping 里只有两个类且与后端无关，选 Megatron 发生在更里面。
  • 五层：外层 ActorRolloutRefWorker（壳）→ 内层 TrainingWorker → EngineRegistry.new → MegatronEngine → initialize() 建模型。
  • actor.strategy=megatron 一个字符串串起整条链：hydra 挂配置组 → self.engine = self.megatron → 注册表 backend 键。
  • MindSpeed 不是独立 backend：配置仍写 megatron，靠 EngineRegistry 的 (device=npu) 键自动顶替；子类只重写 _init_device_mesh（插 repatch）与 to（FP8 搬运），分片代码零改动。
  • 并行度落地两次：mpu.initialize_model_parallel 建通信组（进程全局、只建一次 → actor/ref 必须同构），provider_overrides 经 Megatron-Bridge 决定权重切几份。
  • DP 无配置项，由 world/(TP×PP×CP) 推出；ETP 默认 null（跟随 TP），MoE 上忘设会算出超额卡数。

插课 G：昇腾 EI0007 / QP 建链失败排查

  • 昇腾报错是「Python 异常 + PTA 层 + CANN 层」倒序拼接打印的；本例首发故障（EI0007）比 Python 异常早 30 秒，先找时间戳最早那行。
  • 算子异步下发 → 错误在第一个同步点（.cpu().item()）才被抛出，所以 Python 栈指向的那一行是无辜的。
  • torch.OutOfMemoryError 只是外壳。判据：真正的张量 OOM 一定带 "Tried to allocate … reserved in total by PyTorch" 统计量；没有就不是，调 batch 无效。
  • QP 按链路建、只有走 RoCE 的链路才吃 QP；通信域是惰性创建的，一创建就占 2×HCCL_BUFFSIZE（默认 400 MB/域）的独占显存 —— 于是「首次用到的通信组」和「显存峰值」撞在一起。
  • "资源耗尽"有显存和网卡 QP 配额两种可能，日志分不出来；定性靠 plog 里 CreateOneQp 的上下文。
  • 处理顺序：调小 HCCL_BUFFSIZE → 启动阶段预建链（显存还空时）→ 查 HCCL_INTER_HCCS_DISABLE / HCCL_INTRA_ROCE_ENABLE 是否把 HCCS 推成 RoCE → 多 QP 相关变量（默认本就是 1）。
  • §11（代入真实配置）：TP×PP×CP=64 → DP=1，分布式优化器因此沿 CP 维度切；DP×CP 和 CP 成员相同但是两个独立通信域，前者 forward 用不到、backward 才首次建域建链 —— 这就是失败点，5 行预建链即可挪走。
  • §11 的分水岭：TP×CP=16 是否塞得进一个节点决定 CP / DP×CP 走 HCCS 还是 RoCE（仓库 256K 参考脚本把 TP×CP 刻意凑成正好一个节点）。反向修正：显存实算约 19 GB / 64 GB 并不紧，原"显存挤占"推断被削弱；262K 下单次 SP 通信约 640 MB 已远超默认 200 MB，撤回"先调小 HCCL_BUFFSIZE"。
  • §13：官方 256K 脚本就是推荐配置，但它是 235B/256 卡，能搬的是方法。关键算术：stage0 激活 ≈ 层数 × min(PP, 微批数) × 每 rank token，PP 被约掉 → 真正决定它的是 CP×TP，小 mini batch 可直接压住它。把 CP 收进节点内（TP×CP≤8）要付激活 9.4→21 GB 的代价，且当前没有证据说明必须改。
  • §15（Qwen3.8-27B 262K 推荐配置）：仓库 27B 脚本是 3K 序列 / 单节点 16 卡 / CP=1，262K 没有现成配置。它能给的是环境版本、以及五项该设而未设的参数——其中 mtp_num_layers=0 最要紧（model.mtp.enable 默认已 false 但只关 verl 的 loss 路径，Megatron-Bridge 仍会按 HF config 把 MTP 层建出来）。sequence_parallel 是最大变量：开/关让 stage0 激活在 9.4 ↔ 37.6 GB 之间（§11⑤ 的 19 GB 是假设它开着）。推荐 TP=2 CP=4 PP=8 + ppo_mini_batch_size=4（TP×CP=8 把 CP 收进节点内；微批数≤PP 时首尾层数覆盖该删掉），两种 SP 状态下都装得下。另：最后一段的 lm_head logits 也只看 CP×TP，收进节点内会翻倍到 16.3 GB，use_fused_kernels=True 因此是承重项。风险：GDN + CP>1 + 262K 三者叠加无仓库背书，应先短序列验布局再逐档拉长。
  • §14：两个改动已进分支——warmup_process_groups（distributed.py，通用）+ warmup_megatron_comm_groups（默认开，VERL_MEGATRON_WARMUP_COMM_GROUPS=0 关）+ log_actor_update_memory（默认关，VERL_LOG_ACTOR_UPDATE_MEMORY=1 开，try/finally 保证报错时也留样），附 2 个 gloo CPU 测试。
  • §12（8 卡/节点，plog 已丢）：跨节点确立，但 QP 条数 6–7、显存 19 GB，两个量级都离上限很远 → 更像"单笔分配失败"而非"总量用尽"；候选是 reserved ≠ allocated——HCCL 的 QP 与 CCL buffer 不走 PyTorch 分配器，拿不到分配器攥着的空闲缓存。对策：garbage_collection_threshold:0.8（仓库在更大模型上就这么用），勿与 expandable_segments 同设（昇腾上互斥，且与 RDMA 注册有已知摩擦）。
