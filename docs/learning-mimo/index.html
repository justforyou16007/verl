各课要点

第一课：main_ppo → 训练主循环

  • 配置分层：verl 默认配置 < general.yaml < 命令行参数。
  • v1 trainer 里，生成和训练通过 TransferQueue 解耦：trainer 只登记 prompt、发出生成请求，然后由 replay_buffer 轮询状态取回结果。
  • hybrid engine：训练和推理共用 GPU，用睡眠/唤醒轮流占用显存。
  • _step_once：sample → old_log_prob → advantage → update_actor。

问答：白盒 vs 黑盒 harness

  • 黑盒/白盒指的是 agent 循环由谁控制，与模型本身无关。
  • 5 个环境的训练都用白盒；cc-agent 是用 Python 仿写的 Claude Code，不是真正的 Claude Code。
  • 黑盒代码在 mimoagent 的 agents/blackbox/ 和 uni-agent 的 blackbox_recipes/。
  • 黑盒 RL 的难点：网关要把文本请求还原成 token，靠前缀哈希判断能否续接到已有的链上。

第二课：Agent Loop 初始化

  • 四层：manager → worker（读登记表）→ 每条轨迹一个 GeneralAgentLoop → run() 里开 pod、组装 harness。
  • "桥"的设计：mimoagent 循环原样运行，只替换两点——模型换成 _VerlRolloutModel，执行工具转发给 env_actor。
  • pod 放在单独的 DatasetEnvActor 进程：工具必须和 pod 客户端同进程，并且卡死时可以直接 kill。
  • 失败时返回格式完整的 _failure_output（reward=-999），避免连累整个 batch。
  • ⚠ 勘误：General 实际运行的是 DefaultAgent 加 Claude Code 命名的工具；yaml 里的 type: cc-agent 和 antihack 不生效。

第三课（上）：线程与事件循环

  • 异步切到同步用 run_in_executor，同步切回异步用 run_coroutine_threadsafe。
  • 不死锁的三个条件：query 不在 L 上调用；T 等待时 L 空闲；agent.run 用专用线程池。
  • T 和 L 严格轮流执行，所以共享数据不用加锁。
  • 线程杀不掉，超时后靠停止开关加 kill env_actor，让线程自己退出（协作式取消）。
  • generate 在 L 上 await 是挂起而不是占用，真正阻塞等待的是 T。

第三课（下）：harness 执行与 token 记账

  • 模型生成的 token 原样保存，绝不重新渲染；只把新增的环境消息渲染成 token（token 进、token 出）。
  • TokenTrace：prompt 只记一次；之后生成部分 mask=1，环境注入部分 mask=0，logprob 填 0.0。
  • select_delta_messages 用游标取新增消息并丢掉 assistant；多条 tool 消息要一次性渲染。
  • 锚点技巧：在新消息前加一条空 user 消息一起渲染，再切掉锚点，补上 turn_separator。
  • 预算在消息边界检查，超了就抛 ResponseBudgetExhausted，正常结束。
  • 工具调用错误 = FormatError（格式不对），每轮一个布尔值；General 没有生成 token 级的 tool_call_error_mask，Code 和 arvo 有。

插课 A：Ray 环境进程与 k8s pod

  • agent 循环不在 pod 里；每条轨迹 = 1 个 DatasetEnvActor（只占 0.125 CPU）+ 1 个 pod。
  • actor 与 pod 之间没有直接网络连接，全部经过 API server：HTTPS 管理 pod 生命周期，exec（WebSocket）执行命令、用 tar 传文件。
  • pod = main（工作区，模型的工具都发到这里）+ sidecar（MCP 服务、数据库、verifier），共享网络，文件物理隔离；答案在打分时才上传到 sidecar。
  • 多容器 exec 必须指定目标容器：用代理加线程局部变量实现，保证并行的工具调用各自发到正确的容器。
  • ⚠ 疑似 bug：General/arvo 在 rollout 中途 pod 断连时，error_category 带了错误信息后缀，精确匹配不上，奖励记成 0 而不是 -999。

第四课：从奖励到 actor 更新

  • 奖励放在 response 最后一个位置（rm_scores），GRPO 再按行求和还原成标量。
  • GRPO（不除以标准差）：优势 = 奖励 − 组均值，复制到这一行每个生成 token 上；-999 先替换成有效均值再把自身优势置 0，其他行不受影响。
  • prompt-mean：每个 token 权重 1/(P×T_u)，每个 prompt 总权重相同；权重在整个 batch 上算好，所以 batch 不能再切成多个 mini-batch 分别优化。
  • sync + 单次优化 ⇒ ratio≈1，截断不会触发，PPO 退化为带组内基线的策略梯度。
  • token 级通道（工具调用错误、重复、deep_failure_mask、adv_signed 保持总量不变）在 General 均未开启。
  • ⚠ 发现：General 配置的 algorithm.length_penalty 没有任何代码读取，实际不生效。

插课 B：Code 环境与 uni-agent 网关

  • 通过 agent.agent_loop_manager_class 把 verl 的 rollout 管理器整个换掉；trainer 侧（第四课）完全不变。
  • mimoagent 一个字没改：原装模型对象发 HTTP，发给 session 专属 URL，网关假装是 OpenAI 服务。
  • 网关靠消息前缀哈希链判断能否增量续接；匹配失败就开新链，所以一个 session 可能产出多条轨迹（默认只留最长那条）。
  • 网关额外记了 generation_spans（每轮生成的 token 区间）——General 缺的正是这个，所以 Code 能做 token 级工具调用惩罚。
  • 奖励由 runner HTTP POST 回网关，在网关和轨迹会合。
  • 四种 whitebox harness 混训，step-hash 模式保证同组同 harness、跨步轮换。

插课 C：仓库如何调用 k8s API

  • 官方 Python 客户端（kubernetes==36.0.3），只操作 Pod、只用 CoreV1Api；全部集中在 mimoagent 的 environments/kubernetes.py。
  • 训练路径只用 4 个接口：create / read / delete pod，以及 pods/exec（WebSocket）。
  • 每个环境一份独立的 Configuration/ApiClient，避免多集群互相覆盖、删错集群。
  • 执行命令、传文件进出都建在 exec 上：timeout N bash -lc、读线程 + 截止时间、head -c 绕过无法关闭标准输入、≥32MB 分块 + dd seek 幂等 + sha256 校验。
  • 删除以查询返回 404 为准；4 小时连接上限用 detached exec 绕过（只有黑盒 harness 用）。
