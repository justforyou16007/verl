第三课（上）：线程与事件循环之间的来回切换

提问：下一步讲一下线程和事件循环之间来回切换的细节。

1. 两个世界的规则不一样

verl 的 worker（异步世界）mimoagent（同步世界）
代码风格async def 协程，用 await 等待普通函数，while True 循环，调用一个函数就一直等它返回
谁在执行一个线程（事件循环）轮流执行这个 worker 上所有轨迹的协程。一个协程执行到 await 时主动让出，事件循环再去执行别的协程一个线程从头跑到尾
禁忌不能做阻塞调用。一个协程阻塞住，事件循环就被占住，这个 worker 上的十几条轨迹全部停下不知道什么是 await，model.query() 必须同步返回结果

所以要解决的问题是：同步的 agent.run() 不能在事件循环线程上跑；但它每轮调用的 query()，又需要用异步方式调推理服务。解决办法是两次"换线程"：

  • 异步 → 同步：loop.run_in_executor(pool, fn)，把同步函数交给线程池执行，并返回一个可以 await 的对象。
  • 同步 → 异步：asyncio.run_coroutine_threadsafe(coro, loop)，从别的线程把一个协程交给事件循环执行，并返回一个可以阻塞等待（.result()）的对象。

对应的关键代码：

recipes/general/agent_loop.py run() ——第 ① 步：异步 → 同步 
exit_status, exit_message = await asyncio.wait_for(
    self.loop.run_in_executor(_agent_pool(self.agent_thread_pool_size), lambda: agent.run(task=task)),
    timeout=self._trajectory_timeout_or_none)
_VerlRolloutModel.query ——第 ③ 步：同步 → 异步 
def query(self, messages: list[dict[str, Any]], **kwargs) -> dict[str, Any]:
    future = asyncio.run_coroutine_threadsafe(self._agenerate(messages), self._loop)
    return future.result()
  • self._agenerate(messages)：调用 async 函数只会创建一个协程对象，并不执行。
  • run_coroutine_threadsafe(..., self._loop)：以线程安全的方式把协程投递到 L 的任务队列里。返回的 future 是 concurrent.futures.Future，是给普通线程用的，可以阻塞等待。
  • future.result()：T 在这里阻塞，直到 L 把 _agenerate 执行完。如果协程里抛了异常，.result() 会在 T 上重新抛出同一个异常。
  • self._loop 来自 agent_loop.loop。run() 第一行执行 self.loop = asyncio.get_running_loop()，确保拿到的就是正在执行这个协程的那个事件循环。基类 __init__ 里虽然也设过一次，但在这里重新取一次更稳妥。
_VerlRolloutModel._agenerate ——第 ④ 步，在 L 上执行（摘要） 
async def _agenerate(self, messages):
    if self.stopped:
        raise _RolloutStopped("rollout torn down")          # 停止开关，见第 5 节
    await self._absorb_new_messages(messages)               # 只把新增的消息转成 token（第三课下）
    remaining = self._trace.remaining_budget()
    if remaining <= 1:
        raise ResponseBudgetExhausted(...)                  # token 预算用完
    sampling_params["max_tokens"] = min(self._per_turn_max_tokens, remaining)
    output: TokenOutput = await self._agent_loop.server_manager.generate(
        request_id=self._request_id, prompt_ids=self._trace.token_ids, sampling_params=sampling_params)
    self._trace.append_generated(output.token_ids, output.log_probs)
    content, tool_calls = await self._agent_loop.tool_parser.extract_tool_calls(output.token_ids, ...)
    return self._build_assistant_payload(content, tool_calls)   # {"content": ..., "tool_calls": [...]}

server_manager.generate（verl/workers/rollout/llm_server.py:229）内部是 await server.generate.remote(...)：对 SGLang 服务进程发起 Ray 调用，并用 await 等结果。等待期间 L 是空闲的，可以去执行别的轨迹。

3. 为什么不会死锁

死锁的意思是"A 等 B，B 又在等 A"，谁也走不下去。这套设计能成立，靠的是三个条件：

条件一：query() 永远不在 L 上调用

假设在 L 上调用 query()：L 会卡在 future.result()，而 _agenerate 又必须由 L 来执行，于是 L 在等自己，永远等不到。因为 agent.run() 一定是在 _AGENT_POOL 的线程上跑的，所以 query() 一定在 T 上被调用。

条件二：T 等待期间，L 必须是空闲的

run() 用的是 await run_in_executor(...)，也就是让出 L、不占用它。如果写成 agent.run() 直接调用，或者写成 future.result() 这类阻塞等待，L 就被占住了，第 ④ 步永远不会执行。docstring 里那句 "The loop is free at that moment: the coroutine that started the agent is parked on run_in_executor" 说的就是这一点。

条件三：_agenerate 需要的线程必须能拿到，所以要有专用线程池

_agenerate 渲染 chat template 时用的是 run_in_executor(None, ...)，也就是事件循环的默认线程池。它的大小默认是 min(32, CPU 核数 + 4)。假设 agent.run() 也放进默认线程池：

默认线程池的线程全被 agent.run() 占满（每个要跑十几分钟）
  → 某个 agent 线程调用 query()，等 _agenerate 返回
  → _agenerate 要渲染 chat template，提交到默认线程池 → 没有空闲线程，排队
  → 排队的渲染任务要等某个 agent.run() 结束、让出线程
  → 但所有 agent.run() 都卡在 query() 等 _agenerate 返回
  → 形成循环等待，死锁

所以 _agent_pool 的注释写道："Deliberately NOT the event loop's default executor ... a long-lived agent.run() parked on the default pool would starve it and deadlock the worker." 两个线程池分开以后，渲染任务永远有线程可用。

附带的影响：_AGENT_POOL 大小是 agent_thread_pool_size=64。如果一个 worker 上同时有超过 64 条轨迹，多出来的 agent.run() 只会排队，不会死锁。但 asyncio.wait_for 的计时从提交那一刻就开始了，排队时间也算在 trajectory_timeout 里。按默认配置，64 个 prompt × 8 条 / 32 个 worker ≈ 每个 worker 16 条，不会触发这种情况。

4. 跨线程共享的数据为什么不用加锁

agent.messages 由 T 修改，却在 L 上被 _absorb_new_messages 读取；TokenTrace 和 n_calls 等计数器在 L 上修改，又会被 T 通过 get_template_vars() 读取。这些数据都没有加锁，为什么安全？

因为这两个线程是严格交替运行的，像传递接力棒一样：T 调用 query() 后立刻阻塞在 .result()，这段时间只有 L 在动这些数据；L 设置好结果之后就不再碰它们，下一个动的是 T。同一时刻只有一方在读写，所以不会冲突。

唯一真正并行的地方是第 ⑥ 步：mimoagent 用一个线程池（tool_parallel_workers=8）同时执行多个工具调用。这些线程只做 ray.get(env_actor.execute_tool...)，不碰 TokenTrace，结果由 mimoagent 按调用顺序收集后再追加进 messages（executor.map 会保持顺序）。

同样，execute_action 里的 ray.get 是阻塞调用，但它阻塞的是 P/T 线程，不是 L，所以没问题。如果把同样的 ray.get 写进 _agenerate，就会把 L 卡住，整个 worker 都会停下来。

5. 异常与超时：线程没法被强行杀掉

异常怎么从 L 传到 T

以 token 预算用完为例：_agenerate 在 L 上抛出 ResponseBudgetExhausted → future.result() 在 T 上重新抛出 → mimoagent 的 BaseAgent.query() 把所有异常包装成 ModelQueryError：

third_party/mimoagent-osr/src/mimoagent/agents/base.py:254 
try:
    response = self.model.query(self.messages, **self.get_model_query_kwargs())
except Exception as e:
    raise ModelQueryError(f"{e}\n{traceback.format_exc()}") from e

ModelQueryError 是 TerminatingException 的子类，run() 的循环捕获到它就正常返回 (状态, 消息)，已经生成的那部分轨迹保持完整。

mimoagent 的异常层级（base.py:57-77）：

NonTerminatingException   → 把错误作为 user 消息返回给模型，继续下一轮
  └ FormatError
TerminatingException      → 结束 run()，返回 (类型名, 消息)
  ├ LimitsExceeded
  ├ ModelQueryError       ← query() 里的任何异常都会变成它
  └ InfraError            ← env_actor 不可用、pod 连接断开

超时后，线程怎么停下来

Python 不能强行杀死一个线程。asyncio.wait_for 超时后，只是让 run() 不再等待（抛出 TimeoutError），T 线程上的 agent.run() 其实还在跑。run() 之后走的流程是：

except TimeoutError:
    return self._failure_output("trajectory_timeout", ..., error_category="rollout/seq_timeout")
finally:
    if model is not None:
        model.stopped = True                 # ① 打开停止开关
    await env_actor.cleanup.remote()         # ② 删除 pod
    ray.kill(env_actor, no_restart=True)     # ③ 杀掉环境进程

这时 T 线程成了"孤儿"，它会在下一个检查点自己退出：

  • 如果 T 正在执行工具：ray.get 访问一个已经被杀掉的 actor，抛出 RayError → execute_action 把它转成 InfraError（属于 TerminatingException）→ agent.run() 返回。
  • 如果 T 正卡在 query()：已经投递出去的 _agenerate 不会被取消，它在 L 上继续跑完这一次生成；T 拿到结果后去执行工具 → 进入上一种情况。
  • 如果 T 正要发起下一次 query()：_agenerate 第一行检查到 self.stopped，抛出 _RolloutStopped → 被包装成 ModelQueryError → agent.run() 返回。

最后 T 被归还给 _AGENT_POOL，这个线程就回收了。这种做法叫"协作式取消"：没办法从外部强行终止线程，就在它必经的路上设置"绊线"（停止开关、杀掉 actor），让它走到那里时自己退出。

超时后 run() 返回的是 _failure_output，孤儿线程之后对 TokenTrace 做的任何修改都没人再读，所以不会污染训练数据。代价是：孤儿线程退出之前，最多还会多占用一次推理请求和一个线程池位置。

6. 思考题

Q1：如果去掉 _agenerate 开头的 if self.stopped 检查，会发生什么？

大多数情况下线程仍然会退出：杀掉 env_actor 之后，下一次执行工具就会触发 InfraError。但存在一个时间窗口。finally 里先打开开关，然后要 await env_actor.cleanup.remote() 删除 pod（可能需要几秒到几十秒），之后才 ray.kill。这段时间 env_actor 还活着，T 可能刚好完成一次工具调用，紧接着发起下一次 query()。没有这个开关的话，这次 query 会向推理服务提交一个最长 per_turn_max_tokens=65536 token 的生成请求，白白占用 GPU，结果也没人要。有了开关，它在发请求之前就退出了。

Q2：为什么渲染 chat template 要用 run_in_executor(None, ...) 放到线程池里，而不是在 L 上直接算？

tokenize 一个几万 token 的长对话需要几十到几百毫秒的 CPU 计算，期间 L 被占住，其他轨迹的协程都停下来。放到线程池里，L 可以在等待期间继续处理别的轨迹。正因为用了默认线程池，才有了第 3 节"条件三"的死锁风险。

Q3：env_actor.setup.remote() 在 run() 里用的是 await，而在 execute_action 里用的是 ray.get，为什么不统一？

run() 是协程、运行在 L 上，必须用 await，否则会卡住 L。execute_action 运行在 T 或 P 这种普通线程上，属于同步世界，不能用 await，只能用阻塞的 ray.get。规则就一条：在 L 上用 await，在普通线程上用阻塞调用。

7. 答疑：generate 在 L 上执行，多轮时会不会把 L 卡在等 LLM 回复上？

提问：在 L 事件循环上执行 await server_manager.generate，按理说这部分 rollout 不是应该在 agent.run 流程中吗？而且多轮的情况下会多次调用这一步，这样不会导致 L 卡在 LLM 回复阶段吗？
结论：
  1. 从调用关系看，生成确实是 agent.run 流程里的一步；只是从由哪个线程执行看，这一步交给了 L 去办，T 在原地等结果。
  2. L 在等 LLM 回复时是挂起，不是占着线程等。等待期间 L 会去处理其他轨迹。真正被"卡住等回复"的是 T，所以每条轨迹要占一个 T 线程，但所有轨迹共用一个 L。
  3. 轮数多了，只是 L 上会出现更多段很短的处理，不会出现一段很长的阻塞。

7.1 "属于谁的流程"和"由谁执行"是两回事

按函数调用关系，从上往下一层层调用：

agent.run()                                   ← mimoagent 的循环
 └ step()
    └ BaseAgent.query()
       └ _VerlRolloutModel.query(messages)    ← 到这里为止都在 T 上执行
          └ ═══ 线程切换：run_coroutine_threadsafe ═══
             _agenerate(messages)             ← 从这里开始在 L 上执行
              └ server_manager.generate(...)
                 └ await server.generate.remote(...)  → SGLang

所以生成仍然是 agent.run 每一轮的一部分：agent.run 必须等它返回才能继续。只不过 query() 把"去调推理服务"这件事转交给了 L，自己在 future.result() 上等着。可以这样理解：T 是"发起人"，L 是"代办人"。

步骤属于谁的流程在哪个线程上执行
组装 messages、决定这一轮要查询模型agent.runT
新消息转成 token、调用推理服务、解析工具调用agent.run（通过 query）L（其中 tokenize/decode 再交给 D）
等这一轮的结果agent.runT 阻塞在 future.result()
执行工具agent.runT / P（阻塞在 ray.get）

7.2 await 是"挂起等待"，不占用 L

关键是 _agenerate 执行到 await server.generate.remote(...)（verl/workers/rollout/llm_server.py 的 LLMServerClient.generate）时，具体发生了什么：

  1. server.generate.remote(...)：Ray 把请求发给 SGLang 服务进程。这一步只是"把消息发出去"，立刻返回一个代表未来结果的引用（ObjectRef）。
  2. await 这个引用：_agenerate 在这一行暂停，并登记"结果到了再叫醒我"，然后把 L 的控制权交还给事件循环。
  3. L 去执行其他已经就绪的协程：别的轨迹的 _agenerate、env_actor.setup 的等待、往 TransferQueue 写结果等。
  4. SGLang 生成完毕，结果通过 Ray 传回。事件循环把 _agenerate 重新放回就绪队列，轮到它时从 await 那一行接着往下执行。

也就是说，在 LLM 生成的这几秒到几分钟里，L 没有任何一刻是专门为这条轨迹空等的。真正在"等"的是两样东西：GPU 上的 SGLang 在算，以及 T 线程在 future.result() 上睡眠。

用三条轨迹 A、B、C 画一下时间线（▓ 表示 L 在执行代码）：

时间 ───────────────────────────────────────────────────────────────▶
L   : ▓A派发 ▓B派发 ▓C派发 ·········(空闲/处理别的)········ ▓A解析返回 ··· ▓C解析返回 ··· ▓B解析返回
S   :        ══════ A 生成 ══════════════════════════
             ══════ B 生成 ════════════════════════════════════════════════
             ══════ C 生成 ════════════════════════════════
T_A : 阻塞在 result() ································ 醒来 → 执行工具(ray.get) → 下一轮 query
T_B : 阻塞在 result() ·················································· 醒来 → ...
T_C : 阻塞在 result() ········································ 醒来 → ...

SGLang 会把同时到达的多个请求合并成一批一起计算（连续批处理），所以 A、B、C 的生成在 GPU 上是并行的。L 每次只花很短时间做"派发"和"解析返回"两段处理。

7.3 L 每一轮实际花多少时间

以 _agenerate 为例，真正在 L 上执行的只有：

  • select_delta_messages 找出新增消息、拼 sampling_params：微秒级。
  • await self._load_balancer.acquire_server.remote(request_id)：问负载均衡器该用哪台 SGLang 服务器，也是挂起等待。request_id 固定是这条轨迹的 rollout_uid，所以每一轮都会路由到同一台服务器，可以复用前几轮已经算过的前缀缓存。
  • 用正则从解码后的文本里提取工具调用、组装返回的 dict：毫秒级。

耗 CPU 的部分都交给了默认线程池 D，不在 L 上执行：

verl/experimental/agent_loop/tool_parser.py:352（qwen3_coder 解析器） 
text = await loop.run_in_executor(None, self.tokenizer.decode, responses_ids)   # 解码几万 token 交给 D
recipes/general/agent_loop.py render_first_prompt 
return await asyncio.get_running_loop().run_in_executor(None, lambda: render_ids(...))   # 渲染 chat template 交给 D

所以每轮占用 L 的时间大约是毫秒级，而一次生成要几秒到几分钟。轮数越多，L 上只是多了更多这样的小片段，轮流穿插在各条轨迹之间，不会连成一段长时间阻塞。

7.4 那为什么不让 T 自己直接调用推理服务？

技术上可以在 T 里写 ray.get(server.generate.remote(...))，不经过 L。不这么做的原因是复用 verl 现成的异步代码：

  • LLMServerClient.generate 和 _acquire_server 都是 async def，负载均衡、粘性路由、权重版本号（min/max_global_steps）都在里面处理；tool_parser.extract_tool_calls 也是 async def。
  • verl 自带的 single_turn_agent_loop.py:67 和 tool_agent_loop.py:235 也都是 await self.server_manager.generate(...)。MiMo 走同一条路，就不用另外维护一份同步版本的客户端。
  • T 反正都要阻塞等结果，是阻塞在 ray.get 还是阻塞在 future.result()，对线程占用来说没有区别。

7.5 什么情况下 L 才会真的被卡住

只要在 L 上执行的代码里出现同步阻塞或者长时间的 CPU 计算，L 就会被卡住。例如：

  • 在协程里写 ray.get(...)、time.sleep(...)、同步的 HTTP 请求；
  • 直接在协程里调用 tokenizer.decode 解码几万 token，或者对很长的文本跑复杂的正则。

症状是：这个 worker 上的所有轨迹同时变慢甚至停住，推理服务的并发请求数明显下降。排查时可以用 py-spy dump --pid <worker 进程号> 看主线程的调用栈：如果主线程长时间停在某个非 select/epoll 的函数上，那个函数就是卡住 L 的元凶。
