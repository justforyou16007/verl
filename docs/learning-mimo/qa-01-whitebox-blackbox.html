问答：白盒 vs 黑盒 harness

总览← 第一课：main_ppo → 训练主循环第二课：Agent Loop 初始化 →

问答：mimoagent 是白盒 agent RL 吗？仓库里有黑盒 RL 吗？

提问：mimo agent 这里是白盒 agent RL 吧？这个仓库有黑盒 RL 优化部分吗？

结论：是的，5 个环境的训练用的都是白盒 harness。黑盒代码存在，但没有接进本仓库任何一个训练脚本。

"黑盒/白盒"说的是 agent 框架，不是模型

模型始终是"白盒"：权重在我们手里，用 PPO/GRPO 求梯度更新。区别在于驱动模型多轮调用工具的那段循环代码（harness）由谁控制：

白盒 harness黑盒 harness
循环代码我们自己的 Python 代码（mimoagent 的 cc-agent、codex-agent 等）第三方程序，比如真正的 claude 命令行、Codex CLI，装在沙箱里运行
怎么调用模型直接调推理服务，拿到 token id只发 HTTP 请求（OpenAI/Anthropic 接口格式），内容是整段对话文本
训练侧能看到什么每轮模型生成了哪些 token、哪些 token 是工具返回的，一清二楚只看到文本请求，需要自己还原成 token 序列

依据：训练配置全是白盒

config/agent/code/mini-bash.yaml        type: bashonly-agent
config/agent/code/mini-claude-code.yaml type: cc-agent
config/agent/code/mini-codex.yaml       type: codex-agent
config/agent/code/mini-mimocode.yaml    type: mimocode-agent
config/agent/general/s3k.yaml           type: cc-agent
config/agent/design/webdev.yaml         type: webdev-agent
cc-agent 不是真正的 Claude Code，而是 mimoagent 用 Python 重写的"仿 Claude Code"：工具集和提示词风格一样，但循环由我们控制。所以配置文件名叫 mini-claude-code。
补充（勘误）：s3k.yaml 虽然也写了 type: cc-agent，但 General 环境实际运行的是 DefaultAgent 加上 Claude Code 命名的工具，这一行不生效。详见第二课勘误。白盒的结论不受影响。
recipes/code/__init__.py 
"""The four-whitebox code recipe: verl -> Uni-Agent -> MimoAgent.

"Whitebox" is the distinction that matters: all four arms drive their tools
in-process through the Gateway, so the policy's own tokens are what call them.
The blackbox harnesses that run a real CLI inside the pod are a different
mechanism and are not part of this mix.
"""

选白盒的理由：执行的每次工具调用，都是从策略模型自己生成的 token 解析出来的。这和 MiMo 的"工具调用级别奖励分配"直接相关：工具调用出错时，能准确定位到是哪段 token 产生的这次调用，再对它加惩罚。黑盒程序可能改写、截断、重新拼接对话历史，这种对应关系就不可靠了。

黑盒代码在哪里

① mimoagent 的黑盒适配器：third_party/mimoagent-osr/src/mimoagent/agents/blackbox/，共 14 个（claude-code、codex、opencode、kimi-code……），会在任务容器里安装并运行真正的命令行程序，主要用于评测。本仓库的衔接代码给它们留了一个分支：

recipes/code/mimoagent_runner.py 
_MODEL_BACKED_AGENT_TYPES = {"default", "bashonly-agent", "mimocode-agent", "cc-agent", "codex-agent"}
...
    if agent_type in _MODEL_BACKED_AGENT_TYPES:     # 白盒：创建真正的模型对象，由我们的循环调用
        return get_model(config=model_config)

② uni-agent 的黑盒 RL 示例：third_party/uni_agent/examples/blackbox_recipes/claude_code/，用真正的 Claude Code 做 RL 训练的完整示例：

runner 创建沙箱 → 把 claude 程序挂载进去
  → 在沙箱里执行 claude -p <任务>，ANTHROPIC_BASE_URL 指向 uni-agent 网关
  → claude 每轮把完整对话以文本发给网关
  → 网关：文本 → token → SGLang 生成 → 记录 token 和 logprob → 把文本回复返回给 claude
  → 任务结束后在同一沙箱里打分 → 奖励发给网关 → 轨迹写入 TransferQueue

黑盒 RL 难在哪：网关要把文本还原成 token

RL 训练需要知道"模型在每个位置生成了哪个 token、概率是多少"，还需要 response_mask 来区分哪些 token 是模型生成的（要算梯度）、哪些是工具返回的（不算梯度）。网关（uni_agent/gateway/session/session.py）因此要做两件事：

  1. 用 chat template 把对话编码成 token（codec.py）；
  2. 给每条消息算哈希（_compute_message_hash），检查新请求的前缀是否和已记录的某条"链"（ChainState）一致（_is_chain_prefix_hash_match）。一致就把新增的 token 接到这条链后面；不一致说明 Claude Code 压缩或改写了历史，只能另开一条新链。所以一次会话可能产出多条轨迹，这正是 key 里有 index 的原因。
训练路径harness是否经过网关本仓库用来训练
General / Cyber / Visual白盒（mimoagent 原生循环）否，直接用 verl AgentLoop✅
Code白盒（4 种 harness 混合）是，经过 uni-agent 网关✅
黑盒 Claude Code 等真正的命令行程序是，必须经过网关❌ 只在子模块示例里 / 用于评测
