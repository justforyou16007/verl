说明

仓库 /home/liu/projects/verl，分支 mimo-agent-env，revision f4becf6e。

怎么用这些图：图本身只回答「有哪些环节、顺序是什么」。每个模块干什么、内部怎么做变换、有哪些坑，全部写在图下面的参考卡片里，卡片标题用 ①②③ 与图中的环节一一对应，可以直接按编号查。 卡片最后一行是该模块的源码位置（文件 + 行号区间）。
编号对应关系：图上每个节点都带号，与下方卡片标题的号一一对应，已用脚本逐页核对（9 页全部对齐）。带 ′ 的（如 ②′ ④′）是同一环节下的细节层或替代路径。
卡片的写法：每张卡片按「触发（什么时候、由谁调起）→ 为什么（这一步要解决什么问题、为什么是这个顺序）→ 怎么做（实际代码与变换）」组织，不只写「做了什么」。
  • 采用总—分结构：先看初始化和训练两张主干图，再按需要点进对应的子模块图。
  • 所有图都是单文件 HTML，离线可看，右上角可切 Live / Still 控制动效，支持搜索与聚焦。
  • 与硬件、分片相关的部分做成了可交互的 2D / 3D 动画，维度名和形状全部取自真实的 init_device_mesh 调用。
  • 不在本仓库的子模块（vLLM、SGLang、Megatron-LM、Ascend 全套）已按匹配版本 clone 进 third_party/ 并登记为 git submodule，版本绑定到具体 commit，见版本钉子。

跨栈时序图

上面那组图回答「谁是谁的一部分」，按模块切分。这一组回答「谁先调谁、谁等谁、跨栈边界落在哪」，按时间轴组织，泳道从左到右大致就是软件栈从上到下：启动进程 → Ray → driver → worker → 通信库 → Megatron → 推理引擎 → 硬件。

橙色箭头是跨出 verl 的调用，也就是出问题时责任可能不在 verl 的地方；虚线是为腾显存或防故障刻意加的动作；绿色竖条是真正阻塞的同步点。

图回答什么
初始化总时序从启动脚本到 ready to fit 的 18 步：先认硬件 → 起 Ray → 要资源定地址 → 建通信域 → 建模型 → 起推理引擎 → 首次权重同步
训练一步总时序一个 step 的九个阶段，含异步下发与同步点的分界；三种 trainer 模式的差别只在钩子落点
子流程：worker 启动与通信域建立昇腾三处补丁时机为何必须排对；惰性建链为什么会撞上显存峰值，预热为什么只选四个组
子流程：一次生成请求生成为什么不走 HTTP；路由与粘滞表如何服务前缀缓存；KV cache 在一步里的进出
子流程：数据的形状与布局变换use_remove_padding 这一个开关如何决定整条路的布局；三种布局依次出现与逆变换；微批划分为何不改形状却决定快慢
子流程：actor 更新集合通信的三类归属（verl 显式 / Megatron 隐式 / 优化器内部）；四个同步点与异步错误的落点；打包与切分的形状变化
子流程：权重同步两条路共卡传显存句柄 vs 分离部署集合通信广播；导出为何写成生成器；中间那道栅栏的必要性
子流程：推理 PD 分离部署一个副本 = 1 prefill + N decode 怎么在单节点内编排；vLLM 串行两段 vs SGLang 并发扇出两种接力；KV 走 NIXL / Mooncake；非对称 TP 下权重同步为何仍成立；当前 MVP 限制（昇腾上不可用）
子流程：1F1B 流水线调度PP=3、4 个微批按 Megatron 真实收发配对逐拍画出 warmup / 稳态 / cooldown；气泡占比与「首段攥得最多」的显存规律；配对收发为何会卡死；梯度归约落在哪段气泡里；更正：微批数要乘采样数 n
几个与直觉相反、容易把图画错的事实（都已在图上标出）：
  • 生成不走 HTTP：vLLM 与 SGLang 都是 Ray RPC 到 server actor，再在同一进程里调引擎。那个 OpenAI 兼容端口是给外部客户端的。只有 TRT-LLM 生成、以及 SGLang 的权重同步控制面才真的走 HTTP。
  • 首次与每步的权重同步默认都不是集合通信广播：hybrid 的后端在代码里被硬编码成 naive，走同卡 CUDA IPC，配置里写 nccl 也不生效；只有 separate_async 会另建一套用真实后端。
  • hybrid 模式的推理引擎没有自己的 placement group，申请的加速器数是零，靠节点亲和性共享训练 actor 的可见设备。
  • 优势计算不调任何外部库：driver 上纯 PyTorch CPU 张量，没有 Megatron、没有设备、没有集合通信。
  • use_remove_padding 的生效值会被 model 配置覆盖 engine 配置（代码注释自认 not elegant），所以两处都要设；而 CP>1 时它必须为 True，否则启动即 raise ValueError——per-token 损失在 CP>1 时由 Megatron-Bridge 自动开启，它硬性要求 THD 布局。
  • verl 从不自己发流水线收发和梯度归约：一次 forward_backward_func 调用全包；verl 只在启动时把归约钩子装进 Megatron 的配置。
  • 路由器是 verl 自己写的 Python，不是 sglang_router 或 vLLM 的路由进程。
  • ppo_mini_batch_size 的单位是 prompt，不是序列：_update_actor 先乘 rollout.n，worker 再除以 DP，然后才切微批。所以流水线里的微批数 m = ppo_mini_batch_size × n ÷ DP ÷ 每微批序列数——插课 G §13 / §15 漏乘了 n，见 1F1B 图的更正卡片。

初始化

初始化总分图

  • 主干 ①–⑥：启动与 Ray 集群 → TaskRunner 与选型 → 数据面 → 资源池与 WorkerGroup → 引擎与模型 → 就绪与首推权重。
  • 每条泳道是该阶段内部的真实调用顺序；_setup() 十九步的编号写在箭头上（「第 N 步」），不要和卡片编号混淆。
  • 两条非默认部署路径单独画出：④′ 非共卡（Role.Actor + 独立 RefPolicy，生成全交给 standalone 副本）和 ④″ PD 分离（1 prefill + N decode，副本 world_size 被放大）。
  • 还画了 v0 旧版路径，以及 separate_async 的额外初始化（DetachActorWorker、第二套服务与检查点管理器）。

single-controller 分派

  • 一次 driver 调用的六步闭包，以及八种 Dispatch 模式的切分语义。
  • 实际在用的是「字典模式」ND mesh 分派：按 dp_size 切，同一 dp 组共享一个 ObjectRef。
  • 共卡机制：WorkerDict 只跑一次 Worker.__init__，角色方法加前缀再在 driver 侧剥掉。

训练

训练主循环与三模式

  • 主干是与模式无关的一个 global step；下面三条泳道是同一个钩子在三种模式下的不同动作。
  • 标清了容易记错的两个顺序：存检查点在 on_step_end 之前，校验在之后。
  • 生成侧单独一行——它在另一个进程里持续跑，只通过 TransferQueue 与主干相连。

训练步九阶段

  • _step_once 的九个阶段画成 driver ↔ worker ↔ TQ 的消息往返，阶段名就是 timing_s/* 指标名。
  • 解释了为什么 compute_log_prob 的返回值只被断言长度：结果其实写回了 TQ。
  • 一个 global step ≠ 一次更新：外层还有 parameter_sync_step 循环（Decoupled PPO）。

权重同步

  • 默认的 naive 同卡路径时序：先只恢复 weights 显存，逐张量 full_tensor()，填 IPC 字节桶，最后 barrier 再重建 KV cache。
  • 显存峰值只有「一个完整张量 + 一个字节桶」，不是整个模型。
  • 非 naive 的六种检查点引擎（nccl / hccl / nixl / mooncake / kimi / delta_sharded）各自的搬运机制。

子模块

推理副本与路由

  • 生成请求根本不走 HTTP，是一次打到 node-rank-0 server actor 的 Ray RPC。
  • 副本几何：一个副本 = 一个 TP×DP×PP 组，可跨节点，每节点一个 server actor。
  • 三种 RolloutMode（HYBRID / COLOCATED / STANDALONE）在显存与权重同步上的区别。

vLLM / SGLang 内部

  • vLLM v0.32.0：Ray actor（AsyncLLM 前端）→ EngineCoreProc → 每 TP rank 一个 worker 子进程，executor 后端是 mp 而不是 external_launcher。
  • SGLang v0.5.20：verl 绕过 launch_server，直接用 Engine._launch_subprocesses；这一版没有 VerlEngine。
  • 睡眠 / 唤醒之所以可行，是因为权重和 KV cache 分别挂在 CuMem 分配器的不同标签下。

NPU 补丁分层

  • 一句话看懂昇腾策略：未改动的 Megatron 问「你是 CUDA 张量吗」，Ascend 层给 Tensor.type 套包装器，把 npu 改写成 cuda。
  • verl 自己的 NPU 代码只有 155 行，真正的替换由 MindSpeed / MegatronAdaptor 的 256 个补丁点在底下完成。
  • 推理侧没有 NPU 专属模块，vllm-ascend 靠 vLLM 的 platform plugin 入口点挂进去。

模型初始化与设备放置

  • 主干 ①–⑥ 是训练侧与推理侧共有的六个阶段：定并行组 → 分层 → 建空层 → 读权重并切分 → 包装定量 → 就位。
  • 两条泳道对照同一阶段的不同做法。最大的差异在读权重：Megatron 侧每个 TP rank 都读整张张量、只有 tp0 用得上、再 scatter；推理侧每 rank 自读自切、没有 scatter。
  • 第四条泳道代入 Qwen3.8-27B 的真实 config.json 算具体形状。
  • 这个模型有三个特别之处：hybrid 注意力（64 层 = 16 full + 48 linear）、1 层 MTP、以及 head_dim=256 × 24 头 = 6144 ≠ hidden 5120。

分片动画

并行与分片动画（2D / 3D）

  • ① FSDP 参数分片：("fsdp",) 一维全分片 vs ("ddp","fsdp") 二维 HSDP，可调 world_size / fsdp_size。
  • ② Ulysses：("dp","sp")，演示 batch 按 dp 切、序列按 sp 切；sp 在内层所以连续 rank 构成一个 Ulysses 组。

已知坑与死代码

读代码时容易被带偏的地方，各图的卡片里都标了，这里汇总：

  • PD 分离的传输后端：初始化总分图卡片里列的「nixl / mooncake / ascend / mori / fake」是配置白名单，不是实际可用的集合——vLLM 的 PD 副本只接受 nixl 与 mooncake，其余抛 NotImplementedError；而且两个 PD 副本类都断言不在 NPU 上，昇腾上这条路当前不可用。详见 PD 分离时序图。
  • 没有 register center：MASTER_ADDR / PORT 由一个钉在 PG 0 bundle 0 上的 Ray task 返回；ray_wait_register_center_timeout 被接收但从未使用。
  • worker 里的 LOCAL_WORLD_SIZE 恒为 1：WorkerGroup 注入的是 RAY_LOCAL_WORLD_SIZE，要真实值得读那个。
  • FusedWorker 全套没有调用方：实际在跑的是被注释标成 deprecated 的 WorkerDict 路径。
  • DISABLE_WORKER_INIT 被写两次、从未被读，所以角色子 worker 其实跑完了完整的 __init__。
  • Dispatch.RANK_ZERO 注册了枚举但注册表里没有函数，全仓无人使用。
  • rollout 侧死代码：HFRollout / NaiveRollout 在 ABCMeta 下无法实例化；rollout/schemas.py 只被测试引用；rollout/tokenizer.py 无人导入。
  • rollout.mode 只有 async 可达，sync 直接抛错。
  • 容错几乎没有：没有 max_restarts / 重试 / 部分失败处理，单 rank 异常直接从 ray.get 冒出来。
  • 待确认：fit() 在最后一步传 prefetch_next_batch=False，sync 模式下生产者/消费者是一步一批、没有缓冲，最后一步 sample 可能无数据可取。读过的代码里没有能排除这一点的逻辑，记作疑问而不是结论。
关于图里那个「节点索引」面板：它是 Viewer 自带的侧栏组件（「要点与索引」那个开关下面），默认是 hidden 的，不属于本页写的内容，也没有 schema 开关能关掉它。 嫌它多余就把侧栏收起来即可；真要从 HTML 里删掉，就得在 archify 产出之后再后处理一遍，那会让它自带的校验收据失效。
