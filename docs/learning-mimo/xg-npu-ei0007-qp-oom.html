插课 G：昇腾 EI0007 / QP 建链失败被包成 OutOfMemoryError

提问：昇腾 NPU 上 verl + Megatron 训练报 torch.OutOfMemoryError，底下跟着 Resource_Error(EI0007): Failed to allocate resource qp with info CreateOneQp，当前算子是 HcclReduceScatter。帮我看下这个报错。另外有一份 AI 给的回答，建议调小 batch、加 recompute 层数、设 PYTORCH_NPU_ALLOC_CONF、把 HCCL_RDMA_QPS_PER_CONNECTION 设成 1，这些对不对。

写于 2026-11-11。本页区分"日志里直接写了的"和"我据此推断的"，推断处都标了【推断】，不要当成已证实的结论去改生产配置。

0. 结论

  1. 这不是张量显存不够。真正的首发故障是 HCCL 在建通信链路时创建 QP 失败（EI0007，21:45:39）。torch.OutOfMemoryError 只是 torch_npu 把这个底层错误包了一层后挑的异常类型，所以先不要去调 batch size。
  2. Python 栈里那行 gated_delta_net.py:584 是无辜的。它是 30 秒后第一个碰到设备同步点的地方，错误在那里才被抛出来。日志自己也写了 "the stacktrace may be inaccurate"。
  3. "资源耗尽"有两种可能：设备显存（HBM）不够装 QP 上下文和通信域缓存，或者网卡的 QP 配额用完。这份日志区分不了。第 7 节给了一条命令去定性，第 8 节给了按顺序做的四件事。
  4. 【推断】时间点更像前者：挂在 0/151 的第一个训练步、挂在 backward 里、挂在那个通信域第一次用到的集合通信上——也就是 HCCL 来要显存的时刻正好是整个 run 里显存最紧的时刻。

1. 这段日志要倒着读

日志末尾那四块东西不是一条链上的四个环节，而是按时间倒序堆在一起的。把时间戳抽出来排一下就清楚了：

时刻日志里的那一行它说明什么
21:45:39.089 Resource_Error(EI0007): Failed to allocate resource qp with info CreateOneQp. Reason: Resources are exhausted. 首发故障。HCCL 要创建一个 QP（RDMA 连接的一端），申请资源失败。
紧接着 TraceBack: Getting socket times out ... 可能是不同 rank 行为不一致 ... 搜索 EI0006 下游噪音。这个 rank 的链路没建起来，握手的 socket 自然就等超时了。这段"不同 rank 行为不一致"是 HCCL 对建链超时的通用提示文案，不是在说你的 rank 调了不同的集合通信算子。
21:46:09（+30s） ERR00100 PTA call acl api failed（PID 1764, Device 4, RankID 12） PTA = PyTorch Adapter，即 torch_npu。它发现自己调的 ACL 接口返回了错误。比首发故障晚了 30 秒。
同时 torch.OutOfMemoryError: The Inner error is reported as above ... the current working operator name is HcclReduceScatter. Python 层抛出的异常。它明说自己是"上面那个 inner error"的外壳，并指出真正出问题的算子是 HcclReduceScatter。
读法：昇腾的报错是"Python 异常 + PTA 层 + CANN 层"三层拼接打印的，顺序和发生顺序相反。永远先找时间戳最早的那一行，那才是首发故障。而且 30 秒这个间隔本身就在告诉你：异常抛出的位置和故障发生的位置没有因果关系。

2. Python 栈为什么指错了地方

栈底是这两行：

  File "/Megatron-LM/megatron/core/ssm/gated_delta_net.py", line 312, in forward
    cu_seqlens_q = self._resolve_cu_seqlens(
  File "/Megatron-LM/megatron/core/ssm/gated_delta_net.py", line 584, in _resolve_cu_seqlens
    total_cu = cu_seqlens[-1].cpu().item()

关键是 .cpu().item() 这个动作：它要把一个设备上的值搬到主机再读出来，必须等设备把排在前面的任务都做完。NPU 上算子是异步下发的——Python 这边 return 了不代表设备那边算完了。所以真实顺序是：

  1. 某个 HcclReduceScatter 被下发到设备队列，Python 继续往下跑；
  2. 设备上执行它时建链失败（21:45:39），错误被记在设备侧，但 Python 还不知道；
  3. Python 一路跑到 .cpu()，这是第一个必须"问设备你好了吗"的地方；
  4. 设备回答"我出错了"，于是异常在 .cpu() 这一行被抛出（21:46:09）。

所以 gated_delta_net.py:584 只是第一个同步点，不是故障点。日志自己写了这件事：

Since the operator is called asynchronously, the stacktrace may be inaccurate.
If you want to get the accurate stacktrace, please set ASCEND_LAUNCH_BLOCKING=1.
顺带一个真实的性能问题：看完整栈能发现 _resolve_cu_seqlens 是在 backward 里的重算 forward 中被调到的（random.py:621 backward → ctx.run_function → transformer_block.py:533 custom_forward → ... → gated_delta_net.py:312）。也就是说每一层重算都会做一次设备→主机同步。这会把流水线打断，是独立于本次报错的性能损耗；同时它也解释了为什么异步错误恰好落在这里——这是代码里同步点最密的地方。

3. 为什么叫 OutOfMemoryError 却不是张量显存不够

这是最容易被带跑偏的一点。异常类型是错误翻译层挑的，不是 PyTorch 显存分配器报的。判据很简单——真正的张量 OOM 长这样：

NPU out of memory. Tried to allocate 2.00 GiB (NPU 4; 60.97 GiB total capacity;
55.12 GiB already allocated; 1.03 GiB free; 58.20 GiB reserved in total by PyTorch)

它一定会报出申请的大小、设备号、已分配/已保留的统计量——因为这些数字就在分配器自己手里。而这次的报错里一个这样的数字都没有，只有一句 "The Inner error is reported as above"。

可以自己验的判据：报错里有没有 "Tried to allocate … already allocated … reserved in total by PyTorch"。有，是张量显存不够，去调 batch / recompute；没有，就是别的东西在报 OOM，调 batch 是白费的。这次是后者。

4. QP 是什么，谁在消耗它

QP = Queue Pair，RDMA 连接的一端（一个发送队列 + 一个接收队列）。两个 rank 要通过 RoCE/RDMA 通信，各自要有一个 QP，配对之后才算"链路建好"。CreateOneQp 就是在建这一个端点。

要理解它什么时候被创建、创建要花什么，得先知道 HCCL 的三个事实：

  1. 按通信域组织。一个"通信域"对应一组参与通信的卡（Megatron 里就是 TP 组、PP 组、CP 组、DP 组、DP×CP 组、embedding 组……）。资源是按通信域为单位管理的，各通信域互不复用。
  2. 通信域是惰性创建的。torch_npu 和 NCCL 一样，new_group() 的时候只登记一个 process group 对象，直到这个组第一次真的做集合通信，才去创建底层 HCCL 通信域、建链、分配缓存。
  3. 通信域一创建就占显存。按昇腾官方文档：每个通信域会创建 CCL_In / CCL_Out 两块缓存，各 HCCL_BUFFSIZE 大小（默认 200 MB），合计每个通信域 2×200 MB = 400 MB，而且这块内存 HCCL 独占，不与业务内存复用。文档明确写了："若集群中通信域较多，占用量增多，可能影响模型数据正常存放，此时可调小该变量"。

把这三条串起来："第一次用到某个通信组"这件事，会在那个瞬间同时触发"建链（要 QP）"和"分配几百 MB 显存（要 HBM）"。这就是本次报错的现场。

这个 job 大概有几个活跃通信域

配置是 PP=4、CP=4、TP 没给（默认 1）、EP=ETP=1、use_distributed_optimizer=True、cp_comm_type=all_gather。训练 rank 上真正会发生集合通信的组：

通信域大小谁在用按默认 BUFFSIZE 占用
TP1TP=1，不产生通信0
CP4cp_comm_type=all_gather，attention 的 KV all-gather400 MB
PP4流水线 send/recv（也是插课 F提到的 NPU p2p 补丁所在之处）400 MB
DP?数据并行400 MB
DP×CPDP×4分布式优化器的梯度 reduce-scatter / 参数 all-gather400 MB
embeddingPP 首尾共享 embedding 的梯度 all-reduce400 MB

也就是每张卡约 2 GB 的 HBM 被 HCCL 独占，模型一个字节都用不到。64 GB 的卡上这是 3% 多——不致命，但它是在最糟的时刻才被拿走的（见第 6 节）。

5. 两种稀缺资源，日志分不出来

Reason: Resources are exhausted 这句话很笼统，底下可能是两件完全不同的事，处理方向正好相反：

(a) 设备显存不够(b) 网卡 QP 配额用完
机制QP 的上下文、收发队列、通信域的 CCL buffer 都要占设备内存。HBM 快满时，这笔申请就失败。每张卡支持的 RDMA 连接数有硬上限。链路数超了就建不出新 QP。
和规模的关系和活跃通信域个数 × HCCL_BUFFSIZE 成正比，和当时模型占了多少显存强相关。和走 RoCE 的链路条数成正比。走 HCCS（机内/超节点内）的链路不吃 QP。
典型触发时机显存峰值期（backward 中段）。初始化或首次建链期，和模型显存无关。
对应的处理调小 HCCL_BUFFSIZE；把建链提前到显存还空的时候。检查有没有把本该走 HCCS 的链路强行改成 RoCE；检查多 QP 是否被打开。
注意一个常见的错误推论：有人会说"32 卡规模大，HCCL 要为每一对 rank 建 QP，基数巨大"。不对。QP 是按链路建的，而且只有走 RoCE 的链路才需要 QP；同一个通信域里一个 rank 也只和它的邻居建链，不是和所有 peer 两两建链。集群卡数本身不构成 QP 压力，拓扑把多少链路甩到 RoCE 上才构成压力。

按 rank 布局算一下自己的 RDMA 链路数

Megatron 默认 rank 排布顺序是 tp-cp-ep-dp-pp，即 rank = tp + cp·TP + dp·(TP·CP) + pp·(TP·CP·DP)。【推断，要用你真实的 trainer.nnodes 复核】如果训练侧也是 4 节点 × 8 卡 = 32 卡，那么 TP=1、CP=4 → DP=2：

  • rank 0–7 是 PP stage 0，8–15 是 stage 1 …… 正好一个节点一个 stage；
  • CP 组和 DP 组都在节点内（走 HCCS，不吃 QP）；
  • 只有 PP 跨节点，每个 rank 两个 PP 邻居 → 走 RoCE 的链路很少；
  • 报错的 RankID 12 落在 PP stage 1、dp=1、cp=0。

这个布局下 QP 需求本来是很低的。所以如果定性结果是 (b)，那说明有东西把机内/超节点内的链路也推到 RoCE 上去了——第 8 节第三步专门查这个。

6. 时间点是最强的证据

日志里有一行很容易被跳过：

Training Progress:   0%|          | 0/151 [3:31:33<?, ?it/s]

它说明：跑了 3 小时 31 分，第一个训练步都还没完成（separate_async 模式下这段时间都花在 agent rollout 上），然后在 _update_actor 里挂了。这个时间点排除了一类原因、指向了另一类：

  • 排除"集群 QP 配额天生不够这个拓扑"。如果是那样，故障会出现在初始化阶段或第一次权重同步时，而不是 3.5 小时后的第一次 backward。
  • 指向"首次用到的通信域 + 显存峰值撞在了一起"。失败的是 ReduceScatter；配了 use_distributed_optimizer=True，梯度 reduce-scatter 走 DP×CP 组；这个组在 forward 阶段用不到，backward 才是它第一次被用到。按第 4 节第 2 条，第一次用到 = 这一刻才建链、才分配那 400 MB。
  • 而这一刻的显存状态是：param_offload=True 的权重刚从 CPU 搬回设备、激活值和梯度都活着——整个 run 里显存最紧的时刻。HCCL 偏偏在这时候来要几百 MB 它独占的显存。

这条链能解释日志里每一行，而且解释了为什么异常被标成 OOM 却找不到分配器统计量。但它仍然是【推断】，下一节是定性的办法。

7. 一条命令定性

决定性证据在设备侧 plog 里——EI0007 那条记录的上下文会打出 HCCL 到底在申请什么、申请多大。到出错的那个节点（172.16.29.213）上，PID 是 1764：

# plog 路径：$ASCEND_PROCESS_LOG_PATH，未设置时默认 ~/ascend/log/debug/plog/
grep -rn "CreateOneQp\|EI0007" ${ASCEND_PROCESS_LOG_PATH:-~/ascend/log}/ | head

# 找到行号后看前后各 50 行，重点看申请的是什么资源
grep -rn -B50 -A20 "CreateOneQp" ${ASCEND_PROCESS_LOG_PATH:-~/ascend/log}/debug/plog/plog_1764_*.log
上下文里看到判定去做
显存申请失败、devMem / Malloc / 某个字节数不够(a) 显存第 8 节 步骤 1、2

同一份 plog 里还有两个有用的东西：

  • grep ccl buffer / BUFFSIZE：看实际生效的每通信域缓存大小，验证第 4 节的算术。
  • grep 通信域创建记录（CommInit 之类）的时间戳：如果它们集中出现在 21:45 附近而不是启动阶段，就直接证实了"惰性建链撞上显存峰值"这条推断。
一定要跨节点比时间戳。这个 rank 建链失败会让它的 peer 全部 socket 等超时，于是别的节点会报一堆 EI0006 / 超时。只有全集群最早的那条错误才是源头，不然很容易去修一个受害者。

8. 按顺序能做的四件事

步骤 1：调小 HCCL_BUFFSIZE（一行，先做这个）

export HCCL_BUFFSIZE=100   # 默认 200，单位 MB；每个通信域占 2×该值

直接命中 (a)：把每个通信域的独占显存从 400 MB 降到 200 MB，按第 4 节的 5 个活跃域算，每张卡让出约 1 GB；更重要的是让那笔失败的申请本身变小一半。这是官方文档为"通信域较多、挤占模型显存"给的处理方式。

代价和下限：如果单次集合通信的数据量超过这个缓存，通信会变慢。文档给的参考下限是 micro_batch × seq_len × hidden × dtype字节数 / 1MB（取最大的那个集合通信算）。改完要看一眼 step 时间，别用通信变慢换来一个跑得动但巨慢的 job。仓库里已有调过它的先例：tests/special_npu/nightly_ci_ascend/run_grpo_qwen3_30b_veomni_fsdp.sh:30 设的是 610（往大调的方向，为了通信性能）。

步骤 2：把建链提前到显存还空的时候（结构性修法）

既然问题的本质是"惰性建链把资源申请推到了显存峰值"，那正面的解法就是在启动阶段、权重还没加载的时候，主动把每个通信组都用一次，让 HCCL 在 HBM 几乎全空时把缓存和 QP 占住——之后这些资源一直留着，不会在 backward 里再申请一次。

落点在 verl/workers/engine/megatron/transformer_impl.py:277 的 mpu.initialize_model_parallel(...) 之后：对 TP 组、CP 组、DP 组、DP×CP 组各做一次极小的 all_reduce（一个 int8 标量就够），PP 组做一轮 p2p。代价是启动时多几百毫秒。

这个做法在昇腾社区的万卡实践里是标准手段（"TP 组初始化时主动建链、DP 组懒加载"的取舍讨论，以及 HCCL 性能测试工具用 -w 预热迭代把首轮建链开销排除在统计外，都是同一件事）。本仓库目前没有做这个预建链——_mindspeed_repatch（verl/workers/engine/mindspeed/transformer_impl.py:39）只打补丁，不触发通信。要的话可以写成一个小 patch。

步骤 3：查有没有东西把 HCCS 链路推成了 RoCE（命中 (b) 才做）

在出错的 worker 进程里（不是提交机上）查这几个变量：

env | grep -E 'HCCL_(INTER_HCCS|INTRA_ROCE|INTRA_PCIE|RDMA|BUFFSIZE|OP_EXPANSION)'

两个最该怀疑的，本仓库里就各有一处在设——都是为了绕别的 bug：

变量仓库里的出处后果
HCCL_INTER_HCCS_DISABLE=TRUEtests/special_npu/nightly_ci_ascend/run_grpo_glm52_top16_megatron_npu_multinode.sh:6（绕 hcomm issue 1083）超节点内本可走 HCCS 的跨节点链路改走 RoCE，QP 需求成倍上升
HCCL_INTRA_ROCE_ENABLE=1verl/checkpoint_engine/README.md:52（CANN ≥ 8.5.0 + kimi checkpoint engine）Server/超节点内的卡间通信改走 RoCE，机内链路也开始吃 QP（默认值是 0）

如果启动脚本从这些地方抄过来了其中任何一个，它就是 (b) 的头号嫌疑。还要注意 Ray worker 的环境变量有三个来源：提交进程继承、PPO_RAY_RUNTIME_ENV（verl/trainer/constants_ppo.py:113）、以及脚本里传的 ray_kwargs.ray_init.runtime_env.env_vars——只在提交机上 echo 一下是不够的。

步骤 4：多 QP 只在真被打开时才要管

  • HCCL_RDMA_QPS_PER_CONNECTION：默认就是 1，取值 [1,32]，官方建议不超过 8。所以"把它设成 1"在默认情况下是个空操作，只有当有人显式调大过才需要改回来。
  • 但它的优先级链是：hccn_tool -s multi_qp 管理面配置 > NSLB > HCCL_RDMA_QP_PORT_CONFIG_PATH > 这个环境变量。也就是说环境变量没设，多 QP 仍可能是开着的——要用 hccn_tool 查管理面配置才算查全。
  • HCCL_MULTI_QP_THRESHOLD（默认 512，单位 KB，范围 [1,8192]）：它控制多 QP 场景下每个 QP 至少要分担多少数据，影响的是"已创建的 QP 里有几个真的承载载荷"。在多 QP 没开的情况下调它没有任何作用，不要当成第一手段。

9. 那份 AI 回答里反掉的五条

那份回答把两种互不相干的资源（通信资源 / 张量显存）混在一起开药，有五条是无效甚至反向的。逐条给依据：

它的建议问题
recompute_num_layers 从 1 调到 2，"用计算换内存" 方向反了。recompute_method=uniform 时这个值是分组大小：层按 N 个一组做检查点，重算时一整组的中间激活同时在显存里。N=1 是把每层单独重算，已经是这组参数里最省显存的配置。调到 2 省下的是"少存一半的层边界输入"（每个只有 b×s×h，很小），换来的是"重算时峰值多一层的内部激活"（注意力分数、MLP 中间量，大一个量级）。净效果是峰值变高。
开 use_dynamic_bsz=True 来"更精细地控制内存" 它降不下来。dynamic bsz 是把多条序列按 token 预算打包进一个 micro-batch，从不切分单条序列——代码里有硬断言：assert max_token_len >= max_seq_len（verl/utils/seqlen_balancing.py:384）。而现在 ppo_micro_batch_size_per_gpu=1，每个 micro-batch 已经就是一条序列，已经到底了，dynamic bsz 只能往里装更多，不能更少。（它真正的好处是均衡各 rank 负载，那是另一回事。）

"32 卡规模大 → HCCL 要为每对 rank 建 QP → 基数巨大" 机制说错了。见第 5 节：QP 按链路建，且只有走 RoCE 的链路才要 QP，同一通信域内也不是两两建链。按第 5 节的布局推演，这个配置下跨节点的只有 PP，RDMA 链路很少。卡数不是原因，拓扑把多少链路甩给 RoCE 才是。
"首要步骤：export HCCL_RDMA_QPS_PER_CONNECTION=1" 默认值就是 1，通常是空操作（见第 8 节步骤 4）。把空操作放在"最直接的解决方法"的位置，会让人以为已经处理过了。

它说对的部分：首发故障是 QP 而不是张量显存、Python 栈因异步而不可信、ASCEND_LAUNCH_BLOCKING=1 只在调试时开完就关。

① DP = 1，这是第一个要注意的事

TP × PP × CP = 4 × 4 × 4 = 64，正好等于训练卡数，所以

DP = 64 / (4 × 4 × 4) = 1

三个后果：

  1. 纯 DP 维度上没有任何集合通信（组大小 1）。所以失败的那个 ReduceScatter 不可能是"DP 梯度规约"。
  2. 但 use_distributed_optimizer=True 并没有因此失效。Megatron 的分布式优化器切分用的是 get_data_parallel_group(with_context_parallel=True)，在 DP=1、CP=4 时这个组的大小是 4——也就是说优化器状态和梯度是沿着 CP 维度切的，梯度 reduce-scatter 走的是 DP×CP 组。
  3. 没有 DP 就没法用数据并行摊微批：ppo_mini_batch_size 有多大，就有多少个 micro-batch 串着过流水线。

② 失败的是哪个通信域：DP×CP，它和 CP 成员相同但是另一个通信域

这是这一节里最有价值的一点。DP×CP 组（DP=1 时）的成员和 CP 组完全一样，都是那 4 张卡。很容易以为"CP 组在 forward 已经用过了，链路早就建好了"。但不是：

Megatron 调 new_group() 把它们建成两个不同的 process group 对象（_DATA_PARALLEL_GROUP_WITH_CP 和 _CONTEXT_PARALLEL_GROUP）。按第 4 节第 2 条，HCCL 通信域是跟着 process group 惰性创建的——成员相同不等于复用通信域。于是：
  • CP 组：forward 第一次做 KV all-gather 时建域、建链、分配 2×HCCL_BUFFSIZE。此时显存还不算紧。
  • DP×CP 组：forward 全程用不到它，backward 里梯度 reduce-scatter 才是它的第一次使用 → 在显存峰值那一刻从零开始建域、建链、再要一份 2×HCCL_BUFFSIZE。

这和日志完全吻合：失败的算子是 HcclReduceScatter、失败动作是 CreateOneQp（建链，不是传数据）、失败时刻在 backward。第 6 节那条推断到这里基本可以当成结论了，而且它给出了一个很窄的修法：不用做全量预建链，只要在启动阶段对 DP×CP 这一个组打一次极小的 all_reduce，就能把它的建域时刻从"backward 显存峰值"挪到"权重还没加载"。

# 落点：verl/workers/engine/megatron/transformer_impl.py:277
#       mpu.initialize_model_parallel(...) 之后
import torch
from megatron.core import parallel_state as mpu

g = mpu.get_data_parallel_group(with_context_parallel=True)
if torch.distributed.get_world_size(group=g) > 1:
    warm = torch.ones(1, dtype=torch.int8, device=torch.npu.current_device())
    torch.distributed.all_reduce(warm, group=g)   # 这一下就把通信域和链路建起来了

⑦ 两个被真实数字卡住的旋钮

(一) HCCL_BUFFSIZE 在 262K 下不该盲目调小 —— 这条推翻第 8 节步骤 1。

也就是说默认的 200 MB 已经远低于单次 SP 集合通信的数据量，这些通信本来就在被切块传。再调小会让每层两次的 SP 通信更碎——而 262K 下这是整个 step 里最热的通信路径。所以在这个配置上，HCCL_BUFFSIZE 是一个真实的两难，不是免费的"省显存"旋钮：往小省 HBM、往大省时间。等第 3 步定性结果出来、确认是显存不足了再权衡，并且改完一定要看 step 时间。

(二) num_key_value_heads = 4 把 TP 锁在 ≤ 4。

  • 降 TP 到 2（TP×CP = 8，8 卡节点刚好装下），那么 PP = 64/(2×4) = 8。代价：SP 区间的 token 从 16384 翻到 32768，每层存的激活翻倍到 335 MB；而 PP=8 时 stage 0 要攒 8 个微批、每段 8 层 → 8 × 8 × 335 MB ≈ 21 GB，比现在的 9.4 GB 更费显存。不是白捡的。
  • 升 TP 到 8：不行，4 个 KV 头切不成 8 份（除非复制 KV，仓库的模型初始化地图里专门点了这个坑）。
  • 学参考脚本的思路：加大 CP、减小 TP，但 64 卡的总量限制了 TP×PP×CP=64 的组合空间，每一种都要连带重算显存，别只看通信。

DP×CP 组（同样这 4 张卡，但是独立通信域）                          ← 跨节点

§11④ 的分叉到此收敛：TP×CP = 16 > 8，所以 CP 组和 DP×CP 组都跨节点、都走 RoCE、都需要 QP。加上 §11② 的"DP×CP 是 backward 才首次使用的独立通信域"，"在 backward 里第一次为跨节点的 DP×CP 组建链，建链时创建 QP 失败"这条链现在是完整自洽的，不再需要标【推断】。

12.2 但有个矛盾要先说清楚：两个"量级"都不像

链条自洽不等于原因找到了。把两种稀缺资源（§5 的 a / b）各自的量算出来，两个都不像是"用光了"：

算出来是多少离上限有多远
(b) QP / RDMA 链路条数每 rank：CP ≈2 条、DP×CP ≈2 条、PP 2 条、embedding ≤1 条 → 约 6–7 个 QP远低于网卡能支持的数量。除非多 QP 被打开（×4 或 ×8 也才 24–56），单纯"条数触顶"解释不了
(a) 显存§11⑤ 实算 stage 0 单卡 allocated ≈ 19 GB64 GB 卡上还剩 ~45 GB。也不像
于是方向要修一下：报错写的是 Resources are exhausted，但更可能是 "这一笔分配没成功" 而不是 "这类资源的总数用光了"。把这两件事分开想，就只剩一个解释口子——HCCL 要向设备申请 QP 所需的那块内存时拿不到，而设备上的空闲显存并没有真的被模型用掉。那它在谁手里？

12.3 答案的候选：PyTorch 分配器"保留"着，但没"占用"

这是第 3 节判据的另一面。PyTorch 的缓存分配器有两个数：

指标含义谁能用
memory_allocated当前活着的张量真正占的字节模型
memory_reserved分配器向设备要来、并且一直攥着的字节（含张量释放后仍留在缓存里的块）只有 PyTorch 自己

而 HCCL 的 QP 上下文和每通信域 2×HCCL_BUFFSIZE 的 CCL buffer 不走 PyTorch 分配器，它直接向设备要。两者抢的是同一块 HBM，但 HCCL 看不到也拿不到 PyTorch 已经 reserved 的那部分。所以完全可能出现：

allocated  ≈ 19 GB   （模型真正在用）
reserved   ≈ 55 GB   （分配器攥着，其中 36 GB 是空闲缓存块）
设备剩余    ≈  9 GB   ← HCCL 只能从这里拿

这个配置里有三件事专门把 reserved 推高：

  1. 262K 的变长序列。每个 micro-batch 的真实长度都不同，分配器要不断为不同大小的块开新段，释放后又留在缓存里 → 碎片化严重。
  2. param_offload=True + optimizer_offload=True 的反复搬运。每次 H2D 都要新块，offload 后块被释放但段仍被 reserved。仓库在 offload 路径上确实调了 empty_cache()（verl/utils/megatron_utils.py:724、752），但那是在 offload 之后，不是在 backward 之前。
  3. 3.5 小时的 rollout 期间，训练进程并不是全程干净的：初始权重同步、log_prob 计算（log_prob_micro_batch_size_per_gpu=1，262K 一条）都在这个进程里留下过大块。
这个解释能同时说通三件事：① 为什么异常被标成 OutOfMemoryError（它确实是内存问题）；② 为什么报错里没有分配器统计量（因为不是分配器报的，是 HCCL 报的，见第 3 节）；③ 为什么 allocated 只有 19 GB 也会失败。
但它仍然是候选，不是结论——12.7 给了替代 plog 的验证办法。

12.5 更正第 9 节关于 max_split_size_mb 的一句话

我在第 9 节写过"max_split_size_mb 设小往往让碎片更严重"。这句话是错的，撤回。官方语义是：大于该值的块不再被拆分，目的恰恰是把大块完整留着给后续的大请求，从而减少碎片（取值下限 >20 MB）。仓库里两个方向都有人用（NPU 1024、CUDA 256），该设多少是跟负载有关的，没有一个普适方向。

但第 9 节那一条的结论不变，只是理由要换成机制那条：调 PyTorch 怎么切自己已经攥住的块，不会把 HBM 还给 HCCL。真正能还回去的只有三种动作——empty_cache()（手动释放已保留的段）、garbage_collection_threshold（到阈值自动释放）、expandable_segments（一开始就少保留）。max_split_size_mb 不属于这三种，所以它治不了本病。

13.2 核心算术：stage 0 的激活只取决于 CP×TP，和 PP 无关

选并行度时最容易算错的就是这一步。把 stage 0 存下来的激活写成公式：

stage0 激活 ≈ (stage0 的层数) × min(PP, 微批数) × (262144 / (CP × TP_sp)) × 5120 × 2 B
                 ↑ 约 64/PP                                   ↑ 开 SP 时 TP_sp=TP，TP=1 时 SP 被强制关掉 → TP_sp=1

注意前两项：层数约 64/PP，在手微批数是 min(PP, 微批数)。微批数足够多时这两项相乘约等于 64，PP 被约掉了——

① 加大 PP 并不会减少 stage 0 的激活。每段层数变少了，但同时在手的微批数变多了，正好抵消。
② 真正决定激活大小的是 CP × TP（开 SP 时），因为它决定每个 rank 实际持有多少 token。
③ 微批数少于 PP 时，min() 生效，小 mini batch 直接压住 stage 0 的显存——这就是 235B 脚本第 4 条在做的事。

代入你现在的配置（CP×TP = 16 → 每 rank 16384 token → 每层 168 MB，stage 0 有 14 层）：

  • 微批数 ≥ 4：14 × 4 × 168 MB = 9.4 GB（§11⑤ 那个数）
  • 微批数 = 2：14 × 2 × 168 MB = 4.7 GB

13.4 但按 §12 的结论，现在还不该动并行度

重排并行度是这几个办法里最贵的一个：要重新验证收敛、重新调 batch、重新测 step 时间。而 §12.2 算出来的两个量——QP 条数 6~7、显存 19 GB/64 GB——都离上限很远，也就是说目前没有证据表明这个布局的通信或显存真的超了。在这种情况下换布局是赌，不是修。

合理的顺序是：先上 §12.7 的 1～3 步（预建链 + garbage_collection_threshold + 内存埋点，全部是低成本、可回退的），拿到内存埋点的真实数字。只有在埋点显示显存确实见底、或者排查最终指向跨节点链路资源时，再把 TP×CP 收进节点内才是有依据的决定。这张表届时直接用。

另外两条和并行度无关、可以顺手对齐的：13.1 第 9 条（预转 mcore 权重 + use_dist_checkpointing，省启动时间）和 ulimit -n 32768（连接数多的场景）。

关键是 device free 这一项来自 mem_get_info()，是设备自己的视角。通信域的 QP 和 CCL buffer 是直接向设备要的、不走 PyTorch 分配器，所以决定 HCCL 能不能成功的是这个数，而不是 total − allocated。另外埋点整体包在 try/except 里：它被放在 finally 中、可能在设备已经出错的状态下执行，探针绝不能成为训练失败的原因。
