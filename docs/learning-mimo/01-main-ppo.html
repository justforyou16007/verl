第一课：从 main_ppo 到训练主循环

0. 主线选择

这个分支在 verl 之上加了 5 个训练环境（Code / Cyber / General / Visual / Music）。它们驱动 agent 的方式分两类：

  • Cyber、General、Visual：沿用 verl 的 AgentLoop 机制，在 recipes/{arvo,general,design}/agent_loop.py 里直接调用 mimoagent 这个 agent 框架（harness）。
  • Code：把 verl 的 agent loop 管理器整个换成 uni-agent，走另一条路。

"main_ppo → agent loop 初始化 → harness 执行 → actor 更新"这条学习路线，和 General（s3k）环境最贴合，所以以它为主线。

2. main_ppo.py 入口

verl/trainer/main_ppo.py 
@hydra.main(config_path="config", config_name="ppo_trainer", version_base=None)
def main(config):
    auto_set_device(config)
    validate_config(...)
    if config.trainer.use_v1:            # ppo_trainer.yaml:230 默认就是 true
        run_ppo(config, task_runner_class=TaskRunnerV1)

run_ppo 先启动 Ray（分布式框架，负责把任务分配到多台机器、多张卡上），再创建一个远程的 TaskRunnerV1，等它跑完：

runner = task_runner_class.remote()       # 在 Ray 集群里创建一个独立进程
ray.get(runner.run.remote(config))        # 让它执行 run，主进程在这里等待
def run(self, config):
    trainer_cls = get_trainer_cls(config.trainer.v1.trainer_mode)  # "sync" → PPOTrainerSync
    tq.init(config.transfer_queue)          # ① 启动 TransferQueue
    self.trainer = trainer_cls(config=config)
    self.trainer.init()                     # ② 创建模型、推理服务等全部组件
    self.init_agent_loop_manager()          # ③ 创建 agent loop 管理器（第二课）
    self.trainer.fit(self.agent_loop_manager)  # ④ 进入训练主循环
TransferQueue（代码里简写为 tq）：可以把它看成一个全局共享的字典。
  • key：prompt 的 key 是 uid；轨迹的 key 是 {uid}_{session_id}_{index}。session_id 取 0 到 n-1，表示同一个 prompt 的第几次采样；index 表示这次采样产出的第几条轨迹。
  • tag：一个小字典，如 {"status": "running", "global_steps": 3}，用来记录状态。
  • value：真正的数据，如 prompt_ids、response_ids、response_mask、reward。
为什么要这个中间层：生成轨迹的一方（agent loop worker）和训练的一方（trainer）是不同的进程，彼此不直接调用，而是都读写这个"字典"，这样双方可以各跑各的。

hybrid_engine: true 的意思是训练模型和推理服务共用同一批 GPU。显存放不下两份，所以要轮流占用：生成时推理服务"醒来"，加载权重和 KV cache（推理时缓存的中间结果）；训练时推理服务"睡眠"，把显存让给 Megatron。PPOTrainerSync 的钩子就是做这个切换：

verl/trainer/ppo/v1/trainer_sync.py 
def on_sample_end(self):   # 轨迹采完 → 推理服务睡眠，释放显存
    self.checkpoint_manager.sleep_replicas()

def on_step_end(self):     # 训练完一步 → 新权重推给推理服务，并唤醒它
    self.checkpoint_manager.update_weights(self.global_steps)

actor_rollout_wg 里的 wg 是 worker group 的缩写，代表"所有 GPU 上训练进程的集合"。调用 wg.xxx()，就是让所有卡同时执行 xxx。

4. fit() → step() → _step_once()

def step(self, metrics, timing_raw, *, prefetch_next_batch=True):
    if prefetch_next_batch:
        self._add_batch_to_generate()      # A. 把一批 prompt 交给 agent loop，不等结果
    for trigger_idx in range(self.parameter_sync_step):   # sync 模式下为 1
        batch = self._step_once(...)       # B. 取出生成好的结果，然后训练

A. 交出 prompt

trainer_base.py:1609 
def _submit_batch_to_rollout(self, batch: TensorDict) -> int:
    tags = [{"is_prompt": True, "status": "pending", "global_steps": self.global_steps} ...]
    tq.kv_batch_put(keys=list(batch["uid"]), partition_id="train", tags=tags)  # 登记"这些 prompt 等待处理"
    self.agent_loop_manager.generate_sequences(batch)   # 分发给各个 worker 后立刻返回

batch 是 TensorDict（可以理解成"每个字段是一列、每一行是一个样本"的字典）。General 环境里比较重要的列有：

  • raw_prompt：对话消息列表
  • agent_name：用哪个 agent loop，如 mimo_swe_agent
  • extra_info.instance_json：任务描述（docker 镜像、题面等）
  • uid：_fetch_one_gen_batch 给每个 prompt 生成的唯一 id。同一个 prompt 的 n 次采样共享这个 uid，GRPO 靠它分组

B. _step_once：完整的 PPO 流程

batch, _ = self.replay_buffer.sample(...)    # 1. 阻塞等待，直到有足够多完整的组
batch = self._balance_batch(batch)            # 3. 按序列长度在各张卡之间均衡分配
batch = self._compute_old_log_prob(batch)     # 4. 用当前模型重新算每个 token 的对数概率
batch = self._compute_advantage(batch)        # 7. 根据奖励算优势（MiMo 改动最多的地方）
batch = self._update_actor(batch)             # 9. 计算 loss，反向传播，更新参数

这里的 batch 是 KVBatchMeta，只包含 partition_id、keys、tags，相当于一张"取货单"。真正的数据还在 TransferQueue 里，各个计算步骤需要时再去取。

replay_buffer.sample 不停轮询每个 prompt 的 status（pending 已登记未开始 / running 正在跑 / finished n 条都成功 / failure 至少一条失败），凑够 train_batch_size 个结束的组后才返回。开了 filter_groups 时，奖励全部相同的组会被丢掉，再补新的 prompt（replay_buffer.py:100 的表：sync 模式下"丢 k 个，补 2k 个"）。
